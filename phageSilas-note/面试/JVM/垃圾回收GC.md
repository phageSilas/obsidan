在了解了JVM的栈和堆之后，探讨垃圾回收（Garbage Collection, 简称GC）是极其顺理成章的。因为**堆是存放对象的大本营，自然也就是垃圾回收的主战场**；而**栈，则是寻找垃圾回收线索的起点**。
![[image-11.png]]


在C/C++中，程序员需要手动分配和释放内存（`malloc`/`free` 或 `new`/`delete`），稍有不慎就会导致内存泄漏。而Java最吸引人的特性之一，就是把这个脏活累活交给了JVM的垃圾收集器（GC）来自动完成。

---

## 1. 可达性分析算法在程序运行的当前时刻，肯定还活着的、绝对不能被回收的对象,即GC ROOT。
![[image-4.png]]

主要包括以下几类（结合我们之前讲的内存区域来看会非常清晰）：

- **① 虚拟机栈（栈帧中的局部变量）引用的对象：**
    
    - _例子：_ 你在方法里写了一句 `A a = new A();`。只要这个方法还没执行完，栈帧里的局部变量 `a` 就还在，它指向的堆里的那个 `new A()` 对象就绝对不能被回收。所以，当前所有活动线程的栈帧里的局部变量，都是 GC Root。
        
- **② 方法区中类静态属性引用的对象：**
    
    - _例子：_ `public static Object myStaticObj = new Object();`。静态变量属于类级别，只要类还在，它引用的对象就必须活着。
        
- **③ 方法区中常量引用的对象：**
    
    - _例子：_ `public static final String MY_CONSTANT = "hello";`。常量引用的对象同样作为根节点。
        
- **④ 本地方法栈中 JNI（即一般说的 Native 方法）引用的对象：**
    
    - Java调用C/C++底层代码时引用的对象。
        
- **⑤ JVM 内部的引用：**
    
    - 比如基本数据类型对应的 Class 对象，一些常驻的异常对象（如 `NullPointerException`），以及系统类加载器等。
        
- **⑥ 所有被同步锁（`synchronized` 关键字）持有的对象。**
    

**总结一下 GC Root 的本质：** 它们通常存放在**栈**（局部变量、Native方法）或者**方法区**（静态变量、常量）中，而不是堆里。GC的过程，本质上就是从栈和方法区出发，去堆里面“查户口”的过程。

## 2. 常见的垃圾回收算法

在面试场景下，我们需要收起那些通俗的比喻，转而使用更加严谨、标准化的 **JVM 规范术语**来描述垃圾回收（GC）算法。面试官主要考察你对算法**执行过程、优缺点以及适用场景**的精确掌握。

### 1. 标记-清除算法 (Mark-Sweep)

这是最基础的垃圾收集算法，后续的算法都是基于其缺点进行改进的。它分为“标记”和“清除”两个阶段。

- **执行过程：**
    
    - **标记阶段 (Mark)：** 基于**可达性分析算法 (Reachability Analysis)**，从 GC Roots 触发，遍历对象图，将所有能访问到的对象打上存活标记。
        
    - **清除阶段 (Sweep)：** 遍历整个堆内存，将未被标记的对象所占用的内存空间直接回收，加入到**空闲列表 (Free List)** 中。
        
- **专业缺点描述（面试必说）：**
    
    1. **执行效率不稳定：** 标记和清除的耗时会随着对象数量的增加而线性增长。如果堆中存在大量且极其细小的垃圾对象，清理效率极低。
        
    2. **内存碎片化 (Memory Fragmentation)：** 这是最致命的缺点。清除阶段只是简单地释放空间，不会移动存活对象，导致可用内存不连续。这会引发严重后果：当程序后续需要分配大对象（如大数组）时，即使总可用内存足够，也找不到足够大的**连续内存区域**，从而被迫提前触发一次 Full GC。
        

### 2. 标记-复制算法 (Mark-Copy)
![[dc7e9d94-36d0-465e-9738-6283634dfb46.png]]


为了解决标记-清除算法的碎片化问题和效率问题，复制算法应运而生。它目前是各大垃圾收集器**新生代 (Young Generation)** 的标配算法。

- **半区复制理论：** 最初始的设计是将内存按容量平分为大小相等的两块（A和B）。每次只使用A，当A用完了，就把A中存活的对象按顺序复制到B中，然后将A空间一次性清空。这种设计的缺点是**空间利用率仅为 50%**，空间浪费极大。
    
- **Appel 式空间分配（HotSpot 虚拟机的标准实现）：**
    
    基于“新生代对象朝生夕死（存活率极低）”的特点，HotSpot 并没有采用 1:1 的划分，而是将新生代划分为三块：
    
    - 一个较大的 **Eden 区**。
        
    - 两个较小的 **Survivor 区**，通常分别命名为 **Survivor From 区** 和 **Survivor To 区**。
        
    - 默认比例为 `Eden : From : To = 8 : 1 : 1`。
        
- **执行过程（重点）：**
    
    1. 日常分配阶段，新对象仅在 Eden 区和 From 区分配内存。此时 To 区是空的。
        
    2. 发生 Minor GC 时，收集器将 Eden 区和 From 区中仍然存活的对象，一次性**连续复制**到 To 区中。
        
    3. 清空 Eden 区和 From 区的所有数据。
        
    4. **角色翻转 (Role Swap)：** 原来的 To 区变成新的 From 区，原来的 From 区变成新的 To 区。始终保持 To 区为空，等待下一次 GC。
        
- **优点：** 实现了**顺序分配 (Sequential Allocation)**，只需移动堆顶指针即可（**指针碰撞 Bump-the-Pointer**），**吞吐量高**，且**彻底消除内存碎片**。
    
- **缺点及解决方案：** 如果某次 GC 后存活对象超过了 To 区的容量（10%），会触发**空间分配担保机制 (Handle Promotion)**，依赖老年代进行内存兜底，直接将放不下的对象晋升至老年代,。
![[image-6.png]]


 

### 3. 标记-整理算法 (Mark-Compact / Mark-Sweep-Compact)

由于老年代 (Old Generation) 中的对象生命周期长、存活率高，如果使用复制算法，不仅复制开销极大，而且需要极大的额外空间进行担保。因此老年代通常采用标记-整理算法。

![[image-7.png]]


- **执行过程：**
    
    - **标记阶段：** 与“标记-清除”算法完全一致，识别出存活对象。
        
    - **整理阶段 (Compact)：** 让所有存活的对象都向内存空间的一端移动（滑动），在移动过程中**更新所有的引用地址**，然后直接清理掉边界以外的所有内存。
        
- **面试核心考点（Trade-off 权衡）：**
    
    - **优点：** 彻底解决了内存碎片问题，后续分配内存时可以使用高效的“指针碰撞”。
        
    - **缺点：** 移动存活对象并更新引用的操作极其耗时。在这个阶段，必须暂停所有用户线程，这种停顿在 JVM 术语中被称为 **Stop-The-World (STW)**。整理算法的 STW 停顿时间远高于清除算法，属于用“延迟”换“吞吐量”的策略（如 Parallel Old 收集器）。
![[image-8.png]]


### 4. 分代收集理论 (Generational Collection)

严格来说，这并不是一个具体的执行算法，而是一套指导 JVM 内存管理的**系统性设计方法论**。它是目前绝大多数商用垃圾收集器（如 CMS、G1、ParNew）的理论基石。

![[01.png]]

- **三大假说（面试加分项）：**
    
    1. **弱分代假说 (Weak Generational Hypothesis)：** 绝大多数对象都是朝生夕死的。
        
    2. **强分代假说 (Strong Generational Hypothesis)：** 熬过越多次垃圾收集过程的对象，就越难以消亡。
        
    3. **跨代引用假说 (Intergenerational Reference Hypothesis)：** 跨代引用（老年代对象引用新生代对象）相对于同代引用来说仅占极少数。（引申：JVM 通过引入**记忆集 Remembered Set / 卡表 Card Table** 来解决跨代引用的扫描问题，避免在 Minor GC 时全堆扫描）。
        
- **算法协同应用：**
    
    基于上述理论，JVM 将 Java 堆划分为不同的区域（新生代、老年代）。
    
    - **新生代：** 每次 GC 都有大批对象死去，存活对象极少，因此采用**标记-复制算法**，只需付出少量存活对象的复制成本即可高效回收。
        
    - **老年代：** 对象存活率高，没有额外空间为其进行分配担保，因此必须采用**标记-清除**或**标记-整理**算法来进行管理。

# 垃圾回收器
在 JVM 的技术演进中，**垃圾收集器（Garbage Collector, 简称 GC 收集器）**是垃圾回收算法的具体落地实现。面试中，面试官通常会让你结合**分代模型**、**STW（Stop-The-World）时间**、**吞吐量与低延迟的权衡**来介绍主流的收集器。

我们可以将常用的垃圾收集器分为三大发展阶段：**经典分代收集器**、**现代分区收集器（G1）** 以及 **前沿低延迟收集器（ZGC）**。

---

## 一、 经典分代收集器（配对使用）

在 Java 8 及以前，收集器通常是严格区分新生代和老年代的，需要组合搭配使用。

### 1. Serial / Serial Old 收集器（单线程串行）

- **应用区域：** Serial 用于新生代（复制算法）；Serial Old 用于老年代（标记-整理）。
    
- **核心特点：** 它是最基础、历史最悠久的收集器。它是**单线程**的，在进行垃圾收集时，必须暂停其他所有工作线程（**STW**），直到它收集结束。
    
- **适用场景：** 客户端模式（Client Mode）下的虚拟机，或内存资源受限的嵌入式设备。
    

### 2. ParNew 收集器（多线程并行）

- **应用区域：** 新生代（复制算法）。
    
- **核心特点：** 它是 Serial 收集器的**多线程并行版本**。除了使用多线程进行垃圾收集外，其控制参数、对象分配规则、回收策略等与 Serial 完全一致。
    
- **适用场景：** 在 Java 8 时代，它是配合 **CMS** 收集器作为新生代回收的首选。
    

### 3. Parallel Scavenge / Parallel Old 收集器（吞吐量优先）

- **应用区域：** Parallel Scavenge 用于新生代（复制算法）；Parallel Old 用于老年代（标记-整理）。
    
- **核心特点：** 这是 **Java 8 的默认垃圾收集器组合**。它的核心关注点是**吞吐量（Throughput）**（吞吐量 = 运行用户代码时间 / 处理器总消耗时间）。它具备自适应调节策略（`-XX:+UseAdaptiveSizePolicy`），虚拟机会根据系统运行情况动态调整内存参数以提供最合适的吞吐量。
    
- **适用场景：** 适合在后台运算而不需要太多交互的分析任务、大批处理型的科学计算系统。
    

### 4. CMS 收集器 (Concurrent Mark Sweep)

- **应用区域：** 老年代（标记-清除算法）。
    
- **核心特点：** 它是 JVM 历史上第一款真正意义上的**并发（Concurrent）收集器**，实现了让垃圾收集线程与用户线程同时工作。它的核心目标是**获取最短回收停顿时间（低延迟）**。
    
- **工作流程（高频考点）：**
    
    1. **初始标记 (Initial Mark)：** 仅仅标记 GC Roots 能直接关联到的对象，速度极快，**需要 STW**。
        
    2. **并发标记 (Concurrent Mark)：** 从 GC Roots 开始遍历整个对象图，耗时最长，但**无需 STW**（与用户线程并发运行）。
        
    3. **重新标记 (Remark)：** 修正并发标记期间因用户程序继续运作而导致标记产生变动的那一部分对象，**需要 STW**。
        
    4. **并发清除 (Concurrent Sweep)：** 清理删除掉标记阶段判断已经死亡的对象，**无需 STW**。
        
- **致命缺点：**
    
    1. 采用“标记-清除”算法，会产生大量的**内存碎片**。
        
    2. 无法处理**浮动垃圾（Floating Garbage）**（并发清除期间用户线程新产生的垃圾），可能导致 _Concurrent Mode Failure_，从而被迫降级退化为 Serial Old 触发 Full GC。
        

---

## 二、 现代分区收集器：G1 (Garbage-First)

G1 是一款面向服务端应用的垃圾收集器，自 **Java 9 开始成为 JVM 的默认垃圾收集器**，旨在彻底替换 CMS。

- **内存布局颠覆：** G1 彻底取消了传统物理连续的新生代和老年代划分。它将整个 Java 堆划分为数千个大小相等的独立区域——**Region**。
    
- **逻辑分代：** 每个 Region 可以在逻辑上扮演 Eden、Survivor 或老年代（Old）。此外，还增加了一类特殊的 **Humongous Region**，用来专门存储大对象（超过 Region 大小 50% 的对象）。
    
- **核心原理（Garbage-First）：** G1 会跟踪各个 Region 里面垃圾“价值”（即回收所能获得的空间大小以及回收所需时间的经验值）在后台维护一个优先级列表。每次根据用户设定的**最大 GC 停顿时间目标**（`-XX:MaxGCPauseMillis`，默认 200ms），优先回收价值最大的 Region，这也是它名字 “垃圾优先” 的由来。
    
- **回收算法：** 空间整合，从整体来看是基于“标记-整理”算法，从两个 Region 之间来看是基于“标记-复制”算法。因此，G1 **不会产生内存碎片**。
    

---

## 三、 前沿低延迟收集器：ZGC (Z Garbage Collector)

ZGC 是 JDK 11 引入、JDK 15 生产成熟，并且在 **Java 21 中被广泛推崇的主流前沿垃圾收集器**。

- **核心目标：** 在尽可能对吞吐量影响不大的前提下，实现在**任意堆内存大小下，都可以将 GC 停顿时间（STW）控制在 10 毫秒以内（甚至 1 毫秒内）**。
    
- **动态 Region：** 同样基于 Region 布局，但 ZGC 的 Region（页面）具有动态性——可以动态创建和销毁，以及动态改变大小（分为小、中、大三类页面）。
    
- **核心黑科技（面试杀手锏）：**
    
    1. **染色指针 (Colored Pointers)：** ZGC 将对象的引用指针高几位（通常是 42~45 位）提取出来，用来直接存储该对象当前的 GC 状态（如 Marked0、Marked1、Remapped 等）。这使得 JVM 仅通过指针本身就能知道对象的存活状态。
        
    2. **读屏障 (Load Barrier)：** 当用户线程从堆中读取一个对象引用时，读屏障会触发，它会检查染色指针。如果发现对象正在被 GC 线程移动，读屏障会利用**自愈（Self-Healing）机制**，直接根据转发表找到并返回对象移动后的新地址，并更新原引用。
        
- **最大特征：** **并发标记与并发整理**。正是因为染色指针与读屏障的配合，ZGC 在移动存活对象（整理阶段）时，用户线程可以并发运行，不需要停顿。它的 STW 时间几乎只取决于初始标记等极少数与堆大小无关的阶段。

|---|---|---|---|---|
|**Parallel Scavenge/Old**|新生代/老年代|复制 / 标记-整理|**吞吐量优先**|后台计算、大批处理、Java 8 默认|
