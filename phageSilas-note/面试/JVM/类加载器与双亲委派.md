在Java的运行机制中，如果把JVM比作一个精密运作的工厂，那么类加载器（ClassLoader）就是这个工厂的“物流采购部门”。它的职责是将你写好的 Java 代码编译成的 `.class` 字节码文件，从硬盘、网络或其他来源，搬运并加载到 JVM 的内存空间（方法区）中，让 JVM 能够认识并执行这些类。

了解类加载器以及它背后的**双亲委派机制**，是深入理解Java底层原理、解决 `ClassNotFoundException` / `NoClassDefFoundError` 以及掌握高级框架底层的必经之路。

## 1. Java 中的类加载器层级结构

在标准 JDK（以 Java 8 为例）中，类加载器并不是只有一个，而是分为一个由上至下的层级结构（它们之间是**父子组合关系**，而非继承关系）：

1. **启动类加载器（Bootstrap ClassLoader）：**
    
    - **地位：** 最顶层的老大，由 C++ 语言实现（在 Java 代码中获取它会返回 `null`）。
        
    - **职责：** 负责加载 JVM 运行所需的最核心的类库，比如存放在 `<JAVA_HOME>/jre/lib` 目录下的 `rt.jar`（包含了 `java.lang.String`、`java.util.*` 等大家最常用的类）。
        
2. **扩展类加载器（Extension ClassLoader）：**
    
    - **地位：** 老二，由 Java 语言实现。
        
    - **职责：** 负责加载 Java 的扩展类库，存放在 `<JAVA_HOME>/jre/lib/ext` 目录下，或者由系统变量 `java.ext.dirs` 指定的目录中的类。
        
3. **应用程序类加载器（Application ClassLoader / System ClassLoader）：**
    
    - **地位：** 老三，由 Java 语言实现。
        
    - **职责：** 负责加载用户类路径（`ClassPath`）上所指定的类库。简单来说，**你自己在项目中写的 Java 类，以及你通过 Maven 引入的第三方 Jar 包，绝大多数都是由它来加载的。**
        
4. **自定义类加载器（Custom ClassLoader）：**
    
    - **地位：** 基层，由开发者继承 `java.lang.ClassLoader` 实现。
        
    - **职责：** 用于实现特殊的加载逻辑，比如从网络下载字节码、对加密的字节码进行解密后再加载，或者实现像 Tomcat 那样的应用级别隔离。

## 2. 什么是“双亲委派机制” (Parent Delegation Model)？
![[image-19.png]]

首先要澄清一个常见的翻译误区：**“双亲”并不是指“父亲和母亲”，而是指“父辈”或“上级”。** 英文原文是 _Parent Delegation Model_，翻译成“父委派机制”其实更准确。

**它的核心工作流程可以用 16 个字概括：向上委托，向下查找。**

当一个类加载器收到加载某个类（比如 `com.user.MyClass`）的请求时，它会按照以下步骤执行：

1. **向上委托：** 它自己绝对不会立刻去加载这个类，而是把这个请求**委派给它的父类加载器**去完成。
    
2. **层层递交：** 每一个层次的类加载器都是如此，因此所有的加载请求最终都会一直往上送，传送到最顶层的**启动类加载器（Bootstrap ClassLoader）**。
    
3. **向下查找：** 只有当父类加载器反馈说：“我在我的地盘（管辖目录）里找不到这个类，我加载不了”（抛出 `ClassNotFoundException` 异常）时，子类加载器才会尝试自己去加载。
    

### 💡 场景推演：加载 `java.lang.String` vs 加载 `com.user.MyClass`

- **加载 `java.lang.String`：** App -> Ext -> Bootstrap。Bootstrap 一看，这是核心类库，归我管！直接加载成功。下面的类加载器连插手的机会都没有。
    
- **加载你写的 `com.user.MyClass`：** App -> Ext -> Bootstrap。Bootstrap 找了一圈说：“这不是核心类，退回”。Ext 找了一圈说：“这不是扩展类，退回”。最后回到 App 加载器，App 在你的项目中找到了它，由 App 亲自加载成功。

## 3. 为什么要设计双亲委派机制？

Java 的设计者之所以大费周章地搞这么一套踢皮球的机制，主要有两个根本目的：

1. **沙箱安全机制（最核心原因）：** 保护 Java 核心 API 不被恶意篡改。
    
    - 假设黑客（或者不懂事的你）自己写了一个类，名字也叫 `java.lang.String`，里面包含了一段清空硬盘的恶意代码。
        
    - 如果没有双亲委派，应用程序类加载器直接把它加载了，系统中就会有两个不同的 `String` 类，天下大乱。
        
    - 有了双亲委派，加载请求会被一路送到 Bootstrap。Bootstrap 会在核心库中加载**官方正版的 `String` 类**，而你写的那个伪造的 `String` 类永远都不会被加载。
        
2. **避免类的重复加载：** 父类加载器已经加载过的类，子类加载器没有必要再加载一次，保证了在 JVM 内部同一个类全局的唯一性。

## 4. 打破双亲委派机制（面试进阶点）

双亲委派机制虽然好，但它并非绝对的铁律。在某些特殊场景下，我们需要主动“破坏”它：

- **Tomcat 的类隔离：** Tomcat 作为 Web 容器，可能同时部署了应用 A（依赖 Spring 4）和应用 B（依赖 Spring 5）。如果严格遵守双亲委派，只能加载一个版本的 Spring，会导致冲突。因此 Tomcat 实现了自定义的 `WebappClassLoader`，**优先加载自己 WebApp 目录下的类**，打破了双亲委派，实现了应用隔离。
    
- **SPI 机制（如 JDBC）：** Java 核心包（由 Bootstrap 加载）中定义了数据库驱动的接口 `java.sql.Driver`，但具体的实现代码（如 MySQL 驱动）是由各大厂商提供并在 ClassPath 下的。Bootstrap 加载器是看不见 ClassPath 下的类的。为了解决这个“老子需要调用儿子辖区里的代码”的尴尬局面，Java 引入了 **线程上下文类加载器（Thread Context ClassLoader）**，实现了逆向调用。
