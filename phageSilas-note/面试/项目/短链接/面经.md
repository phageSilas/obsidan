# 第一家
## 1.短链接怎么生成的？
整体思路是：拿到原始长链接 → 哈希计算 → Base62 编码 → 得到一个短码。
具体来说，我们用的哈希算法是 MurmurHash。选它而不是 MD5 或 SHA，主要是因为它是一个非加密型哈希，速度快、碰撞率低，更适合短链接这种对性能敏感的场景。这个算法会把输入的字符串映射成一个 32 位的整数。
然后我们把这个整数转成 Base62 编码——也就是用 0-9、A-Z、a-z 这 62 个字符来表示。这样每个字符能表示 62 种状态，比纯数字或纯十六进制要紧凑得多，6 位就能表示几百亿的组合，足够用了。
但这里有个问题：如果两个不同用户同时对同一个长链接创建短链接，生成的后缀可能就是一样的。所以我们做了一步处理——生成哈希之前，会在原始 URL 后面拼上一个随机 UUID，这样输入就不一样了，极大降低了碰撞概率。
另外，生成的短链接还会和域名拼接成完整的短 URL，缓存到 Redis 里，这样后续访问时直接走缓存，不用每次都查库。
## 2.怎么确保短链接的唯一？
第一层：布隆过滤器预判。 在往数据库插入之前，先用布隆过滤器检查这个短链接是否已经存在。布隆过滤器是一种空间效率极高的概率型数据结构，它可能误判（说存在但实际不存在），但不会漏判（说不存在就真的不存在）。这里我们初始化时设了 1 亿的预期容量和千分之一的误判率。如果布隆过滤器说"没重复"，我们就可以放心去插入。
第二层：数据库唯一索引兜底。 短链接表里有一个联合唯一索引，建在"完整短 URL + 删除时间戳"上。即使布隆过滤器误判了、让一个重复的短链接漏过去，数据库也会直接抛 DuplicateKeyException，保证不会写入重复数据。这时候我们会把这个短链接加进布隆过滤器，然后提示用户"生成重复，请重试"。

## 3.布隆过滤器的原理？有什么缺点？短链接存满了怎么扩容？占用多少空间？
### 原理
布隆过滤器本质上就是一个很长的二进制位数组 + 多个哈希函数。
具体流程是：当我们要标记"某个短链接已存在"的时候，会把这个短链接用多个不同的哈希函数各算一遍，得到几个位置，然后把位数组里这几个位置都标成 1。查询的时候也一样——用同样的哈希函数算出那几个位置，如果所有位置都是 1，就认为"可能存在"；如果有任何一个位置是 0，就说明"一定不存在"。
这里的关键在于"可能存在"这四个字。它不会漏判，但会误判——因为不同元素经过哈希后可能映射到相同的位置，A 元素把某些位标成了 1，B 元素来查的时候发现这些位也是 1，就被误判为存在了。
我们项目里给它初始化的时候，设了两个参数：预期元素数量 1 亿，误判率千分之一。在这两个参数下，Redisson 底层会自动算出需要多大的位数组和多少个哈希函数。
### 缺点
第一，不支持删除。 这是最经典的问题了。布隆过滤器不能随便把某一位改成 0，因为那一位可能同时被多个元素共用，你改了一个，别的元素就查不到了。我们在项目里也确实没做删除——短链接就算被删了，布隆过滤器的记录也还在，不过这个误判只是多查一次数据库，影响不大。
第二，有误判率。 千分之一的意思是一千次查询里大约有一次会误判。我们项目里用数据库唯一索引兜底，所以即使误判了也不会导致数据重复，只是多了一次无效的数据库写入。
第三，不能枚举。 你没法知道布隆过滤器里到底存了哪些元素，它只能回答"是不是可能存在"。
还有一个实际遇到的坑：Redisson 的 tryInit 方法，如果 Redis 里已经存在这个 key，它是 no-op 的，什么都不会做，也不会覆盖。 这意味着如果你想重新初始化或者扩容，必须先手动把 Redis 里的 key 删掉，不然调 tryInit 是无效的。

### 短链接存满了怎么扩容？
坦白说，我们项目里没有做自动扩容机制。布隆过滤器创建的时候就固定了容量，位数组大小和哈希函数数量都是初始化时算好的。
如果真的需要扩容，思路一般有几种：
最直接的是：删除旧 key，重新建一个更大的，然后全量扫描数据库重建数据。启动时或定时任务把数据库里所有存活的短链接重新加入新的布隆过滤器。但这个过程对大表来说会比较耗时。
更优雅的做法是多级布隆过滤器：旧的满了就新建一个，查询的时候先查新过滤器再查旧的。不过这样会线性增加查询开销。
还有一种思路是用可扩展布隆过滤器（Scalable Bloom Filter），它内部维护一个布隆过滤器列表，满了就追加新的，查询时遍历所有。但 Redisson 没有原生支持，需要自己实现。
如果要我现在做改进的话，我可能会在监控层面加一个告警——当布隆过滤器的元素数量接近初始化容量时，提前通知人工介入迁移，而不是等到满了才发现。

位数组大小大约是 14.4 亿位，换算下来就是 1.44 × 10⁹ / 8 ≈ 1.8 亿字节，约 172 MB。哈希函数需要大约 10 个。
也就是说，用 172 MB 的 Redis 内存，就能索引 1 亿个短链接。对比一下，如果全存 Redis 的字符串 key，1 亿个每个就算只占几十字节，也是好几个 GB 起步。所以布隆过滤器的空间优势非常明显——内存占用量跟存的元素数量成正比，跟元素本身的大小无关，一个几字节的短码和一个几千字节的长 URL，在布隆过滤器里占用的位是一样的。

## ==4.短链接监控消息队列的消息幂等？消息队列顺序性？==
### 消息幂等
我们的做法是借助 Redis 来实现消费幂等。整体思路分三步：
第一，消息到达消费者时，先拿消息的唯一标识去 Redis 里做检查——用的是 Redis 的 SETNX 命令，也就是"不存在才写入"的原子操作。如果写入成功，说明这条消息是第一次来，可以继续处理；如果写入失败，说明已经有人在处理了，就不重复消费。
第二，处理过程中还有一层状态标记。我们用 Redis 里的值来区分两种状态：值是 "0" 表示正在处理中，值是 "1" 表示已完成。这样如果消息重试到达时发现已经标记为 "1"，就直接跳过，避免重复入库。
第三，异常处理也很关键。如果消息处理到一半抛出异常，我们会主动删除这个幂等标识，让 RocketMQ 的重试机制能够重新投递这条消息；如果处理成功，就标记为 "1"。这样既保证了"至少处理一次"，又通过幂等判断保证了"实际生效一次"。
另外有个小细节，这套幂等标识设置了 2 分钟的过期时间。为什么是 2 分钟呢？因为正常的统计写入操作基本在秒级完成，2 分钟已经是很宽裕的兜底时间了——如果 2 分钟还没处理完，说明可能出了严重问题，这个标识自然过期也没关系，RocketMQ 可以重新投递。

### 队列顺序性
这个要坦诚说，我们项目里没有对消息顺序性做严格的保证。
原因在于我们的场景——短链接访问统计，它的数据特点是什么？PV、UV、地区、浏览器、操作系统这些维度的统计，本质上是在做累加。比如今天这条短链接来了 10 次访问，不管消息到达的顺序是 1→2→3 还是 3→2→1，最终累加出来的结果是一样的。所以我们追求的是"最终一致性"，而不是严格的顺序性。
如果非要保证顺序性，RocketMQ 本身是支持顺序消息的——可以把同一个短链接的消息都发到同一个 MessageQueue 里，这样消费者按单线程消费就能保证顺序。但代价是吞吐量会下降，而且消费失败后的重试机制也会打断顺序。对于我们这种统计场景来说，用顺序消息的代价大于收益，就没必要了。
所以总结一下：我们的设计思路是用幂等保证数据不重复、不丢失，用最终一致性接受短时间的统计延迟，而不是强依赖消息顺序。
## 5.短链接表的分表怎么做的？分表下怎么扩容？
### 分表
我们这个项目用的是 ShardingSphere 5.x 来做分表，核心策略就是基于分片键的取模哈希。
以短链接主表 为例：我们选的分片键是分组标识。为什么选分组标识 而不是短链接本身？因为在实际业务中，用户查询和管理短链接都是按"分组"维度来操作的——比如用户打开某个分组，看到的是这个分组下所有的短链接。用分组标识做分片键，意味着同一个分组的所有短链接会落在同一张物理表里，这样按分组查询时只需访问一张表，避免了跨表查询的性能问题。
具体配置上，ShardingSphere 用的是 HASH_MOD 算法，分片数量是 16，也就是分组标识的哈希值对 16 取模，结果 0 就落到 t_link_0，结果 1 落到 t_link_1，以此类推，总共 16 张表。

### 扩容
这个必须坦诚说，用 HASH_MOD 取模分片有一个天然的缺陷——扩容很麻烦。
因为一旦分片数变了，比如从 16 扩到 32，原来的 hash("abc") % 16 = 5 这条数据，在新算法下可能变成 hash("abc") % 32 = 21，路由完全变了。这意味着扩容时需要进行全量数据迁移，把所有历史数据按新规则重新分配到新表里，这个过程涉及数据双写、一致性校验、灰度切换等，成本非常高。
但我们当时为什么还是选了 HASH_MOD 呢？有两个考虑：
第一，这是一个面向学习的项目，16 张表对于演示分表机制已经足够了，不需要在项目里演示完整的动态扩容流程。
第二，在生产实践中，一个常用且务实的做法是翻倍扩容。比如从 16 扩到 32，算法虽然变了，但数据迁移有规律可循——原来 t_link_0 的数据只会流向新的 t_link_0 和 t_link_16，因为 n % 16 和 n % 32 的关系是有确定性的：如果 n % 16 = 0，那么 n % 32 只能是 0 或 16。这样我们可以"一拆二"地迁移，每张旧表的数据只散列到两张新表中，迁移范围是可控的。
如果让我重新设计，我可能会考虑两种改进方向：一是在分片键里引入时间维度，比如按月份分表，这样新月份自动落到新表，天然免迁移；二是用一致性哈希，避免取模算法在节点变化时的大面积重分布。不过这两个方案也各有代价——时间分片会导致冷热数据不均，一致性哈希在 ShardingSphere 里需要自定义算法，复杂度会高一些。
所以整体思路就是：用取模哈希实现快速路由，用分组标识保障查询亲和性，扩容靠翻倍策略做可控迁移——在当前项目规模下，这是一个合理的折中。

## 6.redis中短链接的过期时间如何设置？一段时间内redis缓存的短链接太多导致redis内存满了怎么办？淘汰哪些短链接？内存淘汰和过期删除的策略？

### 过期时间
我们项目里对缓存的过期时间是分两种情况处理的，核心逻辑就在创建短链接时。
第一种，如果用户创建短链接时设置了有效期——比如这条链接只在 7 天内有效——那我们缓存的 TTL 就是从现在到有效期结束的剩余毫秒数。也就是说，链接本身过期了，缓存也跟着自动过期，不会残留无效数据。
第二种，如果是永久有效的短链接，我们给了一个默认的缓存过期时间，大概是 30 天。为什么不设置成"永不过期"呢？因为 Redis 内存是有限资源，永久有效的话，冷数据会一直占着内存不放。
另外项目里还有一个"空值缓存"——当用户访问一个不存在的短链接时，我们会往 Redis 里写一个标记，过期时间设成 30 分钟。目的是防止有人恶意构造大量不存在的短链接来穿透缓存打到数据库上。

### 内存满了怎么办
坦诚说，我们项目里目前没有做专门的缓存淘汰策略配置，更多是依赖 Redis 自身的机制。但这个问题确实值得讨论，我分几个层面来说。
首先，我们项目里 Redis 存的短链接缓存，每条数据是什么体量？就是一个 key 是完整短链接、value 是原始 URL，外加一个 TTL。一条记录大概也就几百字节，假设一条 500 字节，一百万条也才 500MB 左右。对于单机 Redis 来说，内存压力并没有想象中那么大。真正占内存的其实是那些没有 TTL 的、或者 TTL 很长的 key 持续堆积。
那如果确实内存满了，Redis 会怎么做？这就涉及两个概念：过期删除和内存淘汰，它们不是一回事。
过期删除是 Redis 对已经设置了 TTL 的 key 的清理机制，有两种方式配合使用：一种是惰性删除，就是每次访问一个 key 时顺带检查是否过期，过期了就删；另一种是定期删除，Redis 每隔一段时间随机抽一批 key 检查，把过期的清理掉。这样既不会因为轮询所有 key 而阻塞主线程，也不会让过期 key 长期赖着不走。
内存淘汰是当 Redis 内存使用达到 maxmemory 上限时触发的策略。Redis 提供了好几种淘汰策略，我觉得跟我们场景相关的主要是两种：一个是 volatile-lru，只从设置了 TTL 的 key 里淘汰最近最少使用的；另一个是 allkeys-lru，从所有 key 里淘汰最近最少使用的。

### 淘汰哪些短链接
如果要我来选淘汰策略，我会倾向于 allkeys-lru。原因很简单——短链接的访问有明显的热点效应。一条营销活动链接可能在活动期间被疯狂点击，但活动一结束就很少有人访问了。LRU 算法天然会把那些"很久没人点"的冷门链接缓存淘汰掉，而保留高频访问的热门链接在内存里。
就算某个冷门链接的缓存被淘汰了也没关系——下次有人点击时，会触发缓存回源，从数据库里查出来再写回 Redis，代价就是一次缓存穿透的开销，但我们前面有布隆过滤器挡着，不会真的每次都打到数据库。
如果不用 LRU 而用 TTL 优先淘汰（volatile-ttl），可能会误伤一些 TTL 设置得比较短但实际还很热的链接，反而不如 LRU 贴合业务。当然，TTL 短本身说明这条链接有效期短，淘汰了影响也不大，所以两种策略在这个场景下都能接受。
总结一下：我们项目的设计思路是靠 TTL 做第一层自然淘汰，靠布隆过滤器兜底防穿透，内存淘汰策略交给 Redis 的 LRU 来保证热点数据优先留在内存里。如果重新做，我可能会明确在配置里指定 allkeys-lru，而不是依赖默认策略，这样行为更可控。

## 短链接跳转原理
### 第一步：浏览器发起请求
用户输入 http://short.domain/abc123 ，浏览器发出一个 HTTP GET 请求，打到短链接系统的服务器。
### 第二步：拼装完整短链接
服务器从路径里提取出短码 abc123，拼上域名得到完整短链接 short.domain/abc123。后续一切查询都以这个完整短链接为钥匙。
### 第三步：Redis 缓存查询——快速路径
用 short-link:goto:short.domain/abc123 这个 key 去 Redis 里查。如果命中，value 就是原始长 URL。直接拿这个 URL 发一个 302 重定向响应给浏览器，外加异步发一条统计消息给 RocketMQ 做后续入库。
绝大多数正常访问在这一步就结束了，走的是纯内存操作，几十毫秒完成。
### 第四步：缓存未命中——多级兜底
如果 Redis 没命中，不能直接查数据库——可能有人恶意构造不存在短链接来做穿透攻击。所以先过三道防线：
布隆过滤器：问"这个短链接存在吗？"说"不存在"就直接返回 notfound 页面
空值缓存：之前确认过不存在的短链接，30 分钟内直接返回 notfound
分布式锁 + 双重判定：加锁后立即再查一次 Redis 和空值缓存，防止在排队等锁期间缓存已被其他线程补上
### 第五步：数据库回源
防不住才查库。先查 t_link_goto 表，用完整短链接查出 gid。再拿 gid 查 t_link 表，查出原始 URL、有效期、启用状态等完整信 息。
### 第六步：校验与重定向
校验短链接是否有效——没被删除、没被禁用、没过期。任一不通过就写空值缓存、跳 notfound。通过的话，先把原始 URL 写回 Redis 重建缓存，然后对着浏览器发 302 重定向。
### 第七步：浏览器侧
浏览器收到 302 响应和 Location 头指向的原始 URL 后，自动发起第二次请求访问原始网站。从用户视角看就是——点了一下短链接，页面自动跳到了目标网站，中间只隔了几十到几百毫秒。
 
用一句话概括：短链接本质是一个 key，系统通过缓存和数据库把这个 key 映射回原始 URL，然后用 HTTP 302 临时重定向告诉浏览器"去这里"。

# 第二家 较难
## 1.布隆过滤器在redis扩容的情况下还能用吗，如果要对布隆过滤器扩容怎么办？
### Redis 集群扩容，布隆过滤器还能用吗？
先说结论：能用，但有一些需要注意的地方。
我们项目里用的是 Redisson 提供的布隆过滤器实现。它在 Redis 里的本质是什么？就是一个 key 下面挂着一个大的位数组，外加几个哈希函数。在 Redis 单机模式下完全没问题，但如果换成 Redis Cluster，这个 key 会根据 CRC16 哈希落在一个固定的 slot 上，进而固定在某一个节点上。
当 Redis Cluster 做扩缩容——比如加了新节点、触发 slot 重新分配——这个 key 所在的 slot 可能会被迁移到新节点。Redis Cluster 的 slot 迁移机制本身是能保证数据完整性的，迁移过程中会有短暂的阻塞，但数据不会丢。所以从原理上讲，扩容后布隆过滤器还是能正常用的。
不过这里有一个隐患：布隆过滤器的位数组可能非常大。比如我们项目里用户注册用的那个，预计容量一亿，误判率千分之一，算下来位数组大概需要 1.4GB 左右。这么大的 key 在 slot 迁移时耗时会比较长，迁移期间这个 key 可能短暂不可用。所以在生产环境做 Redis Cluster 扩容时，如果布隆过滤器数据量很大，需要把这个因素考虑进迁移窗口的评估里。

### 布隆过滤器自身容量不够了，怎么扩容？
这个才是真正的难点。传统的布隆过滤器有一个先天限制：位数组长度和哈希函数数量在初始化时就定死了，没法像哈希表那样原地扩容。
为什么？因为布隆过滤器的工作原理是"把每个元素映射到位数组的几个位置，然后把那些位置置为 1"。如果你把位数组变长了，原来某个元素映射到位置 17 的，新数组里该映射到哪？哈希函数变了，结果完全不同，旧数据没法"迁移"——位数组里只有 0 和 1，你不知道哪些 1 是哪个元素贡献的，没法重建映射关系。
我们项目里是怎么处理的呢？坦白说，当前项目没有实现动态扩容，初始化时预估了一个比较大的容量——用户布隆过滤器一亿、分组布隆过滤器两亿，对于一个学习项目来说足够用了。但这里面有个容易踩的坑：Redisson 的 tryInit 方法有个特性，如果 Redis 里这个 key 已经存在了，它就什么都不做——不会覆盖、不会更新参数。这意味着即使你改了代码里的容量参数重启应用，旧的布隆过滤器也不会变大。
如果真要扩容，我觉得比较务实的方案有这么几种：
方案一：原地重建。 直接把旧的删了，建一个新的更大容量的，然后从数据库全量扫描一遍，把所有已有的用户名重新加载进去。优点是简单粗暴，缺点是重建期间布隆过滤器是空的，穿透防护有窗口期。可以挑业务低峰期做，或者临时提高数据库的扛压能力顶着。
方案二：新旧并行，平滑过渡。 不删旧的，新建一个容量更大的布隆过滤器。重建期间，写入操作同时写新旧两个，查询操作先查新的、查不到再查旧的。等新过滤器重建完成后，把旧的摘掉。这个方案没有防护窗口期，但实现复杂度高一些，而且过渡期间 Redis 里同时存在两个大位数组，内存压力翻倍。
方案三：分层布隆过滤器。 这是学术界提出的一种变体——不是把位数组变大，而是当现有布隆过滤器"满了"（误判率开始超过阈值），就**新建一个额外的布隆过滤器**，**两个一起用**。查询时依次查每一层，只要有一层返回"可能存在"就算命中。这个方案的缺点是随着层数增加，误判率会累积上升，而且每次查询要访问多个布隆过滤器，性能会下降。
总的来说，布隆过滤器的扩容本质上是一个"容量预估"的问题——你最好在初始化时就给未来留足余量。Redis 层面做内存估算也不难：容量 × 误判率对应的位数组大小，就是内存占用量。一亿容量千分之一误判率也就一个多 GB，对于 Redis 来说是可以接受的。我们项目中选一亿和两亿这两个值，也是基于"留足余量、一次到位"的考虑。

## 2. 消息队列发送是同步的吗，有没有重发机制，怎么设计的，如果要求短链接快速重定向为什么还要同步，当时为什么没考虑到
### 关于同步还是异步
我们当前用的是 同步发送——syncSend，还设了 2 秒的超时。这个调用链路是这样的：用户点击短链接 → restoreUrl 方法 → 构建统计数据 → 调用 shortLinkStatsSaveProducer.send() → 同步等待 RocketMQ 返回发送结果 → 然后才执行 sendRedirect 做重定向。
这意味着什么？重定向的响应时间里，包含了消息发送的耗时。正常情况下 RocketMQ 同步发送也就几毫秒到几十毫秒，影响不大。但如果 broker 负载高、网络抖动，最坏情况要等满 2 秒超时。这对用户体验来说是不可接受的——用户点一个短链接等了两秒才跳转，跟直接打开原链接有什么区别？
你问得对，当时为什么没考虑到？
说实话，这块我在做的时候确实没深入想。导师给的设计方案里就是用同步发送，我当时理解的重点是"统计数据不能丢"，同步发送能拿到发送结果，确认消息真的进了 broker，感觉更可靠。但现在回过头看，统计数据的可靠性不应该以牺牲主链路响应时间为代价。
正确的做法应该是用异步发送——调用 asyncSend，传一个回调，消息发送成功就完事，发送失败在回调里记日志或者落盘补偿，完全不阻塞重定向的返回。用户点击链接，我们拿到原始 URL 后立即重定向，统计消息异步发出去，两个动作解耦。哪怕消息发失败了，一条统计数据的丢失对业务来说是可以接受的，比起让用户多等几百毫秒甚至两秒，孰轻孰重一目了然。
如果再给我一次机会重做，我会这样设计：主流程只做缓存查询和重定向，统计数据的组装完成后直接扔进一个内存队列或者用 asyncSend 异步发送，重定向的响应和消息发送完全并行，不互相等待。
 
### 关于重发机制
坦率说，当前代码里没有实现显式的重发机制。syncSend 抛异常后，catch 块里只打了日志，没有重试逻辑。RocketMQ 客户端自己有一个默认的同步发送重试（默认 2 次），但那是框架层面的，不是我们主动设计的。
如果要补上这块，我现在的思路是这样：
第一层，生产者端重试。异步发送失败后，在回调里做有限次数的重试（比如 3 次），指数退避。如果还是失败，把消息落本地文件或者写进一张"待补偿"的数据库表，起一个定时任务定期扫表重新投递。
第二层，消费者端的幂等性兜底——就是我们之前聊的那套 Redis 幂等机制，保证就算消息最终重复投递了，也不会导致统计数据翻倍。
但这里有个取舍需要说清楚：统计类消息到底值不值得做这么重的一套重试+补偿？我们的场景是访问统计，丢一两条 PV 数据对整体趋势分析几乎没有影响。所以如果是我来决策，我会倾向于：异步发送 + 失败记日志 + 监控告警，而不会去实现复杂的补偿链路。引入补偿机制增加的复杂度和维护成本，远大于偶尔丢几条统计数据的损失。
 
所以总结一下：同步发送是当时的考虑不周，异步发送才是正确的选择，重试机制在当前场景下性价比不高，幂等兜底比分毫不差的投递保证更重要。 这也是做这个项目让我印象比较深的一个教训——不能为了"数据不丢"而牺牲"用户体验"。

## 3.如果有很多人生成短链接，怎么加快生成速度
### 先看现在的生成链路有哪些耗时环节
当前 createShortLink 一次请求要做这些事情：
域名白名单校验（毫秒级，可以忽略）
生成后缀——用 MurmurHash32 哈希原 URL，转 base62 编码出 6 位短码，然后查布隆过滤器判断是否重复，如果冲突就加随机盐重新哈希，最多重试 10 次
两次数据库 INSERT——t_link 和 t_link_goto，在一个事务里同步提交
Redis 缓存写入——把短链接和原始 URL 的映射写进 Redis
布隆过滤器更新——把新短链接加入布隆过滤器
还有一个隐藏的瓶颈：Sentinel 限流——创建短链接的接口被限到了 QPS=1，也就是每秒只允许一次创建请求。这应该是项目里故意加的防护，但在"大量用户同时生成"的场景下，这就是第一道天花板。
 
### 那怎么逐个击破瓶颈？
第一，提限流阈值。 QPS=1 显然太低了，如果是为了防刷，可以提到一个合理的值比如 100 或 500，然后配合用户维度的流量风控（项目里有 UserFlowRiskControlConfiguration，按时间窗口限制每个用户的可访问次数），让正常用户不受影响，恶意用户单独限制。
第二，解决哈希冲突带来的重试开销。 这是链路中最不稳定的环节。现在每次生成后缀都要做 MurmurHash32 → base62 → 布隆过滤器查重。MurmurHash32 的值域只有 43 亿，随着短链接数量增长，冲突概率会上升，冲突一次就要重新哈希、重新查布隆过滤器，每次都是网络往返。
更根本的解决方案是**预生成短码池**。思路是这样的：用一个分布式 ID 生成器（比如 Snowflake 雪花算法），**提前批量生成一批唯一 ID**，转成 base62 编码后放进 Redis 的一个 List 里。用户要创建短链接时，直接从这个 List 里 LPOP 一个出来用，就完全不存在哈希冲突问题了。生成过程变成纯内存操作，省掉了循环重试的开销。
预生成的短码用完了怎么办？起一个后台线程或者定时任务，监控 List 长度，低于阈值就触发补充。补充的时候可以用数据库自增 ID 或者雪花算法批量生产一批 6 位短码，提前校验是否有重复（其实用雪花算法基本不会重复），校验完塞进 List。
第三，数据库写入优化。 当前是同步 INSERT 两张表，事务提交后才返回。优化方向有两个：
一个是批量写入——项目里有 batchCreateShortLink 接口，但它内部是循环调用 createShortLink，相当于循环单条插入，没有真正用上批量。可以改成收集一批待创建的短链接，一次性 batch insert，减少和数据库的交互次数。
另一个更激进的做法是异步写入——短码确定可用后立刻返回给用户，数据库写入交给消息队列异步消费。代价是一致性风险：如果异步写入失败了，用户拿到短链接但实际不可用。所以这个方案更适合"允许短暂不一致"的场景，需要配合补偿机制和监控告警。
第四，分片化创建锁。 当前代码里有一个全局的创建锁 SHORT_LINK_CREATE_LOCK_KEY，所有创建请求抢同一把锁。如果能按分组或者分片键拆成多把锁，并发度就上去了。
第五，布隆过滤器查询优化。 其实布隆过滤器本身很快，瓶颈不在它。但要注意：如果用了预生成短码池，连布隆过滤器这一步都可以省掉——短码是预先生成并校验过的，生成时不需要再查重。布隆过滤器只保留给已经创建的短链接做缓存穿透防护，不再参与生成流程。
 
### 总结一下
最快的优化路径是：提限流 → 预生成短码池替代实时哈希 → 批量写入替代单条插入。这三步下来，创建短链接的吞吐量可以从 QPS=1 提到几千甚至上万。当然，这些优化都是"量变引起质变"后才需要的，项目当前规模下大部分开销其实都在毫秒级，真正的瓶颈是 Sentinel 主动限在了 QPS=1。

## 4. 那你觉得考率支持vip用户，分库分表，redis扩容，用更快的哈希函数等方法怎么样
### VIP 用户支持
这个我挺认同的，本质上是一个资源隔离和差异化服务的问题。
从业务上讲，VIP 用户确实应该有更好的体验。对应到我们的系统，可以做几件事：限流层面，**VIP 用户配更高的 QPS 阈值或者干脆不限流**，普通用户保持现有限制；短码生成层面，VIP 用户可以用更短的短码（比如 4 位），普通用户 6 位，短码越短越稀缺；还有回收站保留时长、分组数量上限、统计数据回溯时长等等，都可以做差异化。
不过从技术实现上看，这需要在网关层或 Controller 层做一层用户身份识别和路由——当前项目里网关已经有 Token 校验，token 验证通过后把 userId 放进请求头往下传，所以拿到用户身份判断是不是 VIP 这个链路是现成的。具体落地的话，可以在用户表里加一个 VIP 等级字段，然后在限流配置、短码生成策略里根据这个字段走不同分支。整体来说思路清晰，实现成本可控，属于"可以做"的范畴。
 
### 分库分表
这个要分开看。我们项目目前其实已经做了一部分——分表，t_link、t_user、t_group 都是用 ShardingSphere 按分片键拆了 16 张表。但有一个关键点：所有 16 张表都还在同一个数据库实例 ds_0 里，实际上是"分表没分库"。
如果要进一步做分库，好处是写吞吐量可以线性扩展——多个数据库实例分摊写入压力，每个实例各管一部分表。但代价也很大：跨库查询基本就废了，JOIN 和事务都要重新考虑。比如用户想看自己所有分组下的短链接统计数据，原来在同一个库里聚合就行，分库之后可能涉及多个库的查询合并。
所以我的判断是：分表在当前项目里已经做到位了，分库属于"量变到质变"才需要的手段。单库写吞吐量撑到瓶颈了才上分库，否则只会徒增复杂度。要看业务体量，如果日活只有几万、短链接总量不过亿，单库完全够用。
 
### Redis 扩容
这个方向上我觉得要分场景讨论。
对于短链接跳转缓存（short-link:goto:{url} 这种 key-value 对），用 Redis Cluster 做水平扩容是很自然的选择——每个 key 天然独立，slot 分配均匀，扩容就是加节点、迁移 slot，几乎零业务改动。
但问题出在布隆过滤器上。布隆过滤器在 Redis 里是一个单一的大 key，位数组可能有几百 MB 甚至上 GB。在 Redis Cluster 里，一个大 key 只能落在一个节点上，没法拆分。你加再多节点，布隆过滤器所在的节点该多大还是多大，而且迁移这个大 key 的成本极高。所以布隆过滤器是 Redis 水平扩容的死角。
解决思路有两个：要么在初始化布隆过滤器时把容量估得足够大，内存给它留足，让它一次到位，不走扩容；要么拆分布隆过滤器——比如按短链接首字符拆成 16 个小布隆过滤器，每个小过滤器独立运作、独立存储，这样就可以分散到不同 Redis 节点上了。但拆分会引入额外的路由逻辑，查询时要先确定去哪个小过滤器。
对于 UV/UIP 统计用的 Set（short-link:stats:uv:{url}），这些是按短链接维度拆分的，天然可以分散到不同节点，扩容没有障碍。
所以我的结论是：Redis Cluster 对缓存和统计数据扩容是可行的，但布隆过滤器是硬骨头，要么一次到位要么拆分，别指望靠加节点来解决。
 
### 用更快的哈希函数
这个说实话，收益可能没有想象中那么大。
我们当前用的是 MurmurHash32，它已经是公认的最快的非加密哈希之一了。换成 xxHash 或者 CityHash，单次哈希的耗时差异在纳秒级，即使每次生成短码要做一次哈希，这部分在整个链路上占比微乎其微。
真正的瓶颈不在哈希函数本身，而在哈希冲突后的重试链路——冲突一次，就要重新加盐、重新哈希、重新查布隆过滤器，每次都是 Redis 网络往返。哈希再快也架不住冲突带来的额外开销。所以与其换一个更快的哈希，不如从根本上消除冲突的可能性——就是我前面说的预生成短码池。用雪花算法生成唯一 ID，直接转 base62，不需要哈希，也不存在冲突，这才是真正消灭瓶颈的做法。
不过有一个方向可以提一下：如果坚持用哈希方案，可以换 64 位哈希替代当前的 32 位。32 位哈希值域只有 43 亿，随着短链接总量逼近这个量级，冲突概率会明显上升；换成 64 位，值域大几个数量级，冲突概率几乎可以忽略不计。这本质上也是在"降低冲突"而不是"加速哈希"。

## 5.用了什么哈希函数，还知道什么其他的哈希函数吗，md5和sha256的特定以及底层原理
我们项目用的是一个叫 MurmurHash 的哈希函数，具体是 32 位版本，来自 Hutool 工具库。选择它的原因挺直接的——MurmurHash 在非加密哈希里属于公认最快的梯队之一，计算开销小，而且分布均匀性好，碰撞率低。对于我们短链接后缀生成这种纯性能敏感、不需要安全性的场景，选它很合适。它不像 MD5、SHA 那样有复杂的安全设计，就是纯粹为了"算得快、散得开"而生的。
### 还知道哪些哈希函数
除了 MurmurHash，我了解过的还有几类：
非加密类还有 xxHash，号称比 MurmurHash 更快，尤其在处理大块数据时优势明显；CityHash 和 FarmHash 是 Google 出的，针对 x86 架构做了深度优化，短字符串场景表现很好；还有 Java 标准库自带的 hashCode，但分布性比较差，不适合生产场景。
加密类的就多了，MD5、SHA-1、SHA-256、SHA-3，还有国内的 SM3。
MD5 和 SHA-256 的特点与底层原理
这两个都属于加密哈希函数，跟 MurmurHash 有本质区别——加密哈希设计目标是"单向不可逆"和"抗碰撞"，而不只是"散得均匀算得快"。
MD5 输出固定 128 位（32 个十六进制字符）。它的原理用大白话说就是：把输入数据先补齐到 512 位的整数倍，然后分块处理，每 512 位一块。内部维护 4 个 32 位寄存器（A、B、C、D），初始值是固定的魔数。每一轮处理会对寄存器做一系列位运算——与或非、循环移位、加上当前数据块和预设的常数表——然后把结果迭代回寄存器，进入下一块。所有块处理完后，4 个寄存器的最终值拼起来就是 128 位的哈希值。
MD5 的核心特点是快，但安全性已经彻底崩了——早在 2004 年王小云教授团队就找到了构造碰撞的方法，现在可以人为制造两个不同文件产生完全相同的 MD5。所以 MD5 现在基本只用于校验数据完整性（比如下载文件后比对 MD5），绝对不能用于密码存储或数字签名。
SHA-256 输出 256 位，属于 SHA-2 家族。流程跟 MD5 类似但更复杂：同样是分 512 位一块处理，但内部维护的是 8 个 32 位寄存器（而不是 MD5 的 4 个），轮数是 64 轮（MD5 只有 4 轮，每轮 16 步）。每轮操作不仅包含 MD5 那种位运算，还引入了更复杂的消息扩展——把当前数据块的 16 个 32 位字通过位移和异或扩展成 64 个字，保证输入的微小变化能在多轮迭代中被充分扩散。这种"雪崩效应"设计使得输入哪怕只差一个比特，输出都会天差地别。
SHA-256 目前没有被实际攻破，安全性远高于 MD5。代价是计算量大概是 MD5 的好几倍，输出长度也多一倍。日常开发里，密码哈希一般推荐用专用的密钥派生函数如 bcrypt、Argon2，SHA-256 更多用于证书校验、区块链（比特币的 PoW 就是反复算 SHA-256）、文件签名等场景。

## 6. 短链接的哈希函数在对称加密和非对称加密怎么选择，还是都可以
### 哈希和加密的本质区别
哈希是单向的，你把数据扔进去出来一个固定长度的指纹，但没法从这个指纹反推出原始数据。加密是双向的，你用密钥加密，用对应的密钥（对称加密同一个密钥，非对称加密另一个密钥）可以解密还原。
短链接的诉求是什么？把长 URL 映射成一个短码，用户点短码时能找回原始 URL。所以核心要做的不是"加密长 URL"，而是建立映射关系——短码只是一个索引，真正的 URL 存在数据库或缓存里。
我们用 MurmurHash 把 URL 哈希成一个 6 位短码，然后把"短码 → 原始 URL"这条映射存到数据库里。用户点击短链接时，拿短码去查映射表，找到原始 URL 做重定向。哈希在这里的作用就是快速生成一个唯一标识，而不是"把 URL 藏起来"。
 
### 如果硬要用加密会怎样？
假设用对称加密比如 AES 来"生成短码"——把原始 URL 用密钥加密，得到的密文当作短码。第一个问题就是长度：AES 加密后的密文至少 16 字节，用 base62 编码之后至少二十几个字符，比我们现在的 6 位短码长了三四倍，"短链接"就不短了。
那如果换成非对称加密比如 RSA 呢？更惨。RSA 加密输出的密文长度等于密钥长度，2048 位的密钥输出就是 256 字节，转 base62 后几百个字符，根本没法当短链接用。
就算用格式保留加密（format-preserving encryption），它能保证输出长度等于输入长度，但一个几百字符的长 URL 加密后还是几百字符，对短链接完全没有帮助。
而且还有一个更根本的问题：加密需要管理密钥。对称加密的密钥一旦泄露，攻击者可以伪造短链接；非对称加密虽然私钥安全一些，但加密解密性能差几个数量级，高并发场景下完全不可行。
 
### 对称和非对称怎么选？
结论是都不选。不是"选哪个更好"的问题，而是加密这个方向从根上就不适合短链接的场景。短链接不需要对 URL 保密（URL 本来就是公开的），需要的是把很长的东西映射成一个很短的标识。这个需求天然是哈希函数的阵地，不是加密算法的阵地。
哈希函数在这个场景里的优势非常明显：输出长度固定且可控——你选 6 位 base62，就是 6 位，不管原始 URL 是一百个字符还是一万个字符；计算速度极快——MurmurHash 是微秒级的，而 RSA 是毫秒级的；不需要管理密钥——没有密钥泄露的风险。
所以如果面试官问的是"哈希函数在对称加密和非对称加密怎么选"，我觉得更准确的表述应该是：短链接生成用的是哈希函数，不是加密函数，二者解决的问题完全不同。对称加密和非对称加密适合用来保护数据的机密性，不适合用来生成短链接标识。

## 7. 短链接输入到显示页面的流程
整个流程大致分三层：网关层 → 业务层 → 存储层，核心逻辑在 restoreUrl 这个方法里，我按请求到达的顺序来说。
### 第一步：请求到达
用户在浏览器输入短链接比如 http://short.domain/abc123，请求先到 Spring Cloud Gateway。网关层有一个 Token 拦截器，但短链接跳转这个路径本身是在白名单里的（/{short-uri} 这种格式），所以直接放行，不需要登录态校验。
### 第二步：构造完整短链接
请求打到 ShortLinkController，匹配到 /{short-uri} 这个路径，取出 shortUri 也就是 abc123，拼上默认域名，得到完整短链接 short.domain/abc123。
### 第三步：查 Redis 缓存——快速路径
这是整个链路里最重要的优化点。绝大多数短链接访问走的都是这条路——直接拿完整短链接拼一个 Redis key short-link:goto:short.domain/abc123，去 Redis 里查 value。这个 value 就是原始长 URL。如果命中，直接走三步：收集访问统计信息（UV、IP、浏览器、操作系统等）→ 异步发一条消息给 RocketMQ 做后续统计入库 → sendRedirect 重定向到原始 URL。整个过程缓存命中时，Redis 查询是毫秒级的，用户几乎感觉不到延迟。
### 第四步：缓存没命中——多层兜底
缓存没命中不一定是短链接不存在，可能只是缓存过期了。这时候不能直接打数据库，因为可能有人恶意构造大量不存在的短链接来做缓存穿透。
第一层兜底是布隆过滤器。把完整短链接扔进布隆过滤器判断，如果返回"不存在"，那就直接跳到一个 notfound 页面，数据库完全不碰。布隆过滤器可能会有误判（说不存在就一定不存在，说存在却可能不存在），所以这一层是"宁可错杀一百，不可放过一个穿透"。
如果布隆过滤器说"可能存在"，接着查第二层兜底——空值缓存。Redis key 是 short-link:is-null:goto_short.domain/abc123，如果命中说明之前已经确认过这条短链接不存在，直接跳 notfound，也不用打数据库。空值缓存设了 30 分钟的过期时间。
### 第五步：加分布式锁回源数据库
前面几层都没命中，说明可能是缓存过期了，需要去数据库捞。但同一时刻可能有大量并发请求都走到这一步，如果大家都去查数据库就成"缓存击穿"了。所以这里用 Redisson 加了一把分布式锁——short-link:lock:goto:short.domain/abc123，只有拿到锁的请求去查数据库，其他请求等着。
拿到锁后，还会再查一次 Redis 缓存和空值缓存——这是双重检查，因为有可能在排队等锁的时候，前面拿到锁的线程已经把缓存补上了，没必要再查库。
### 第六步：查数据库
缓存确实没有，开始查库。先查 t_link_goto 表，按完整短链接查出对应的分组标识 gid。如果查不到，说明这个短链接确实不存在，写一条空值缓存（30 分钟 TTL），跳 notfound 页面。
如果 t_link_goto 查到了，再拿 gid 去 t_link 表查短链接详情。这里要检查三个条件：是否已删除、是否已禁用、是否已过期。任意一个不满足，同样写空值缓存、跳 notfound。
### 第七步：重建缓存并重定向
数据库确认短链接有效，拿到原始 URL 后，先重建 Redis 缓存——把原始 URL 写进 short-link:goto: 这个 key 里，TTL 按链接有效期计算（有有效期就按剩余时间，永久的默认 30 天）。这样后续同样的请求就能走缓存快速路径了。然后同样的流程：收集统计信息 → 发 RocketMQ → sendRedirect 重定向。
### 第八步：浏览器拿到重定向响应
服务端返回的是一个 302 重定向响应，Location 头指向原始 URL。浏览器收到后自动跳转，原始页面的加载就和我们的短链接系统无关了。
统计信息顺便说一下
在重定向之前，buildLinkStatsRecordAndSetUser 这个方法会收集一次访问的所有维度数据：UV 通过 Cookie 判断是否新用户（30 天有效期的 Cookie），UIP 通过 Redis Set 判断是否新 IP，User-Agent 解析出操作系统、浏览器、设备类型，IP 判断网络类型（WiFi 还是移动网络），还会调高德地图 API 根据 IP 反查地理位置（省份、城市）。这些数据打包成一条消息异步丢给 RocketMQ，消费者后续做统计入库。
 
用一句话概括整个链路：Redis 扛流量 → 布隆过滤器挡穿透 → 空值缓存防击穿 → 分布式锁保回源 → 数据库兜底查 → 异步统计不阻塞。每一层各司其职，层层递进，核心目标是让 99% 以上的请求在 Redis 这层就完成，根本碰不到数据库。

# 第三家
## 1.介绍下短链接项目
这是一个 SaaS 短链接系统，简单说就是把一个很长的 URL 转换成类似 short.domain/abc123 这样的短链接。用户点这个短链接，系统自动跳回原始的长 URL。听起来功能很简单，但背后要解决的东西不少——比如海量短链接怎么存储、高并发跳转怎么扛、访问数据怎么统计分析、多个租户之间怎么隔离。
核心功能有四块：长链接转短码、短链接重定向跳转、访问统计与分析（PV/UV/UIP、地区分布、浏览器、操作系统等）、以及多租户数据隔离（每个用户只能管自己的短链接）。应用场景主要是营销短信、活动推广、用户行为追踪这些——长链接在短信里又占字数又难看，短链接就解决了这个问题。

## 2.布隆过滤器去实现创建前的快速判重，布隆过滤器的原理？

## 3.布隆过滤器误判怎么处理（这里说了创建短链接和访问短链接误判两种情况）
### 创建短链接时的误判
创建短链接的判重链路是：哈希出短码 → 布隆过滤器检查 → 过滤器说"可能存在"就视为冲突 → 加随机盐重新哈希 → 重试最多 10 次。
这里的处理方式其实很直接——把"可能存在"当作"一定存在"来对待，宁可多算一次哈希，也不能冒险用一个可能冲突的短码去插入数据库。因为如果真冲突了，**数据库抛唯一键异常，事务回滚**，代价比多算一次哈希大多了。
重试 10 次还冲突就抛异常，让用户稍后再试。实际上这种情况概率极低——6 位 base62 有 568 亿个可能值，在短链接总量远小于这个数量级时，连续 10 次"恰好命中误判 + 恰好命中真实存在的短码"几乎不可能。所以这个看似粗暴的策略在实际中是够用的。
另外还有一个细节：如果插入数据库时真的出现了唯一键冲突（说明布隆过滤器漏判了，把实际存在的说成了不存在），**catch 住 DuplicateKeyException** 后会把这条短链接补加进布隆过滤器，然后抛异常。这样下次就不会再漏判同一个短链接了。
 
### 访问短链接时的误判
这个场景的误判影响和创建不一样，处理链也更复杂，是一层一层兜底的。
访问短链接的查询链路是这样的：
第一层：Redis 缓存。 先查正常的跳转缓存 short-link:goto:{url}。如果命中，直接重定向，后面的都不走了。大多数正常访问在这一层就返回了。
第二层：布隆过滤器。 缓存没命中，问布隆过滤器。如果返回"不存在"，说明短链接肯定没创建过，直接跳 notfound 页面，数据库碰都不碰。
但如果布隆过滤器误判——短链接根本没创建过，过滤器却说"可能存在"——请求就不会在这一层被拦截，而是会进入第三层。
第三层：**空值缓存**。 检查 short-link:is-null:goto_{url}。这个 key 的作用就是记录"之前已经确认过这条短链接不存在"。如果命中了，直接跳 notfound。而且这个缓存 TTL 是 30 分钟，意味着同一个不存在的短链接在 30 分钟内怎么请求都不会穿过这一层。
第四层：加分布式锁查数据库。 前面三层都没拦住，说明要么是一个真正存在但缓存过期的短链接（需要回源重建缓存），要么是一个布隆过滤器误判 + 空值缓存也没命中的不存在短链接。这时候加分布式锁，去 t_link_goto 表和 t_link 表里查。
查出来如果确实不存在，立刻写空值缓存，30 分钟内同样的请求不会再穿透。查出来如果存在，立刻重建跳转缓存，后续请求直接走第一层。
 
### 两层误判放一起看
创建短链接时误判的处理是"保守策略"——误判了就当冲突，多算几次哈希，代价可控。
访问短链接时误判的处理是"层层兜底"——布隆过滤器不是唯一的防线，后面还有空值缓存、数据库。误判的代价就是一次数据库查询，但因为前面有空值缓存挡着（30 分钟 TTL），同一个不存在的短链接最多穿透一次。而且布隆过滤器千分之一误判率本身已经很低了，在实际流量下，真正触达数据库的误判请求量微乎其微。
所以这个设计本质上是：布隆过滤器承担了 99.9% 的拦截工作，省掉了海量数据库查询；那 0.1% 的漏网之鱼交给空值缓存和数据库兜底，每次漏网的成本只是一次有锁保护的数据库查询，完全在可接受范围内。 这比"不用布隆过滤器、每次创建都查数据库"强了几个数量级。

## 4.介绍下空值缓存？存在哪的？
### 空值缓存是什么
空值缓存其实就是当确认一条短链接在数据库里确实不存在之后，往 Redis 里写一条标记，key 是 short-link:is-null:goto_{完整短链接}，value 就是一个占位符 "-"，过期时间设成 30 分钟。
它的作用很纯粹——防止缓存穿透。布隆过滤器有千分之一的误判率，意味着每 1000 个不存在的短链接请求里，大概有 1 个会穿过布隆过滤器继续往下走。如果没有空值缓存，这个请求就会穿透到数据库。而有了空值缓存，第一次穿过来查库确认不存在后，后面 30 分钟内的相同请求直接在 Redis 这层就返回了，数据库完全不受影响。
### 存在哪
存在 Redis 里，用 StringRedisTemplate 以普通 String 类型存的。跟项目里其他缓存一样，都在同一个 Redis 实例里。.
### 为什么 TTL 是 30 分钟
这是一个经验值。设得太短，空值缓存很快过期，穿透防护效果打折扣；设得太长，如果短链接后来被重新创建了，需要等很久空值缓存过期才能正常访问。30 分钟算是一个折中——既能在攻击窗口内提供足够的防护，又不至于让误伤持续太久。而且更新短链接时我们会主动删除空值缓存（不过我看代码，删除逻辑覆盖的场景主要是有效期变更，如果是一个全新的短链接后来才创建，目前确实得等空值缓存自然过期，算是一个可以改进的地方）。

# 第四家
## 1.短链接有效期是怎么设计的？
有效期设计上分两种类型：永久有效（类型值 0）和自定义有效期（类型值 1）。用户创建短链接时，前端传两个字段——validDateType 选 0 还是 1，选了 1 的话再传一个具体的到期时间 validDate。数据库里 t_link 表也是这两个字段，没有做额外的定期清理。
### 缓存的过期时间怎么算
创建短链接成功后，会立刻把原始 URL 写进 Redis 缓存。这个缓存的 TTL 计算逻辑跟有效期直接挂钩——核心代码在 LinkUtil.getLinkCacheValidTime 里。
如果是自定义有效期的短链接，TTL 就是从当前时间到 validDate 的剩余毫秒数。比如链接 7 天后过期，缓存 TTL 就是 7 天。链接过期了，缓存也刚好到期，Redis 自动清理，不会残留无效缓存。
如果是永久有效的短链接，TTL 设了一个默认值——大概是 30 天。为什么不设"永不过期"？因为缓存是 Redis，内存有限，永久不过期的话冷数据越积越多最终撑爆内存。那 30 天到了缓存过期怎么办？没关系，下次有人访问这个短链接时，缓存没命中会触发回源查询数据库，数据库里永久有效的链接是可以查到并重建缓存的。所以这里的 30 天不是为了限制短链接本身的有效期，而是限制单条缓存的驻留时间，是一个内存管理策略，跟业务有效期是两回事。
### 访问时的判断
在 restoreUrl 重定向方法里，从数据库查到短链接记录后，有一个判断：如果 validDate 不为空且早于当前时间，就认为链接已过期。处理逻辑跟"短链接不存在"一样——写空值缓存、跳 notfound 页面。也就是说，过期判断发生在每次访问时，是被动校验，不是主动扫描清理。
这里有个细节：如果一条自定义有效期的短链接过期了，它的缓存 TTL 刚好也到期了（因为 TTL 等于剩余有效期），所以缓存层面 Redis 自动清了，下次访问时缓存 miss、回源查库、发现过期、写空值缓存——整条链路自动走通，没有任何数据不一致。
### 更新时的一致性处理
更新短链接时，如果用户改了有效期类型或到期时间，系统会做两件事：第一，删除现有的跳转缓存，因为旧的 TTL 已经不准确了；第二，如果旧链接已经过期（所以可能存在空值缓存），而新有效期把它"复活"了，就删除空值缓存，否则用户访问时会误判为不存在

## 2.也就说如果说缓存没命中，然后我们还要去那个布隆过滤器去查一下，然后再进入空值缓存当中再查一下，空值缓存那种空值应该不会很多啊（因为布隆过滤器过滤了大部分），为什么还要再加一层空值缓存。

布隆过滤器防的是"广度"，空值缓存防的是"深度"
布隆过滤器解决的问题是：攻击者构造大量不同的不存在短链接来穿透——比如随机生成一千条、一万条、一百万条不同的短链接，每条都是新的。布隆过滤器能挡掉其中 99.9%，剩 0.1% 漏过去。
但问题来了——如果攻击者很聪明，不搞"广度攻击"，而是搞"深度攻击"呢？他只用同一条不存在的短链接，疯狂发请求，一秒钟打几万次。这条短链接恰好落在了布隆过滤器的 0.1% 误判区间里，每次请求布隆过滤器都说"可能存在"，一路绿灯放行。
没有空值缓存的情况下，这同一个短链接的每一次请求都会穿透到数据库。布隆过滤器不是"记住"了第一次查过就拦第二次——它每次判断都是独立的、无状态的，只取决于那几个位的值是 0 还是 1，跟之前查了多少次毫无关系。
空值缓存的价值就在这里：第一次穿透后写一条标记，后面 30 分钟内同一个 key 再怎么打都在 Redis 层返回，数据库只被碰一次。 它把"0.1% 的漏网率"变成了"0.1% 的漏网率 × 每个 distinct key 只穿透一次"。
所以空值缓存不是"布隆过滤器够用了就不需要"，而是补上了布隆过滤器在"同 key 重复攻击"场景下的盲区。布隆过滤器告诉你"这个 key 大概率不存在"，但它没办法告诉你"你刚才已经问过我一次了"。空值缓存就是来做这个"记性"的，让同一个漏网之鱼只能穿透一次，而不是反复穿透。

## 3.这个短链接是你们的域名对吧，然后会到你们的服务设备来，你们给用户返回的是什么？
这里不会返回任何内容，直接进行 302 重定向，这是标准的短链接跳转行为。

## ==4.你说那个 RocketMQ 完成消息队列的幂等的一个幂等场景，它就只消费一次，这个是怎么去做的？==
### 消息的唯一标识从哪来
生产者在发送消息前，用 UUID.randomUUID() 生成了一个**唯一的 keys**，塞进消息体里，同时作为 RocketMQ 的消息头 MessageConst.PROPERTY_KEYS 传给 broker。这样每条消息都有**全局唯一标识**，后续幂等判断全靠这个标识。
 
### 三步走的状态机
消费者的 onMessage 方法里，拿到 keys 后进入一个三步判断：
第一步：抢锁
用 **SETNX**（setIfAbsent）往 Redis 里写一条 key，格式是 short-link:idempotent:{keys}，value 初始为 "0"，TTL 设 2 分钟。
SETNX 是原子操作——Redis 保证"如果 key 不存在就写入并返回 true，如果存在就什么都不做返回 false"。这意味着：对于同一条消息，只有第一个到达的消费者线程能写成功，后面的都失败。
如果 SETNX 返回 true（写成功了，说明我是第一个），跳到第二步；如果返回 false（key 已经存在），说明有人在处理或者已经处理过了，进入第二步的判断。
第二步：判断状态
已经存在的 key，看它的 value 是什么。只有两种状态："0" 表示"正在处理中"，"1" 表示"已完成"。
如果 value 是 "1"：消息之前已经处理完了，直接 return，啥也不做。这就是"幂等"的核心——重复消息到达后，发现已经处理过了，跳过。
如果 value 是 "0"：说明有人正在处理，但还没完成。这时候主动抛一个异常，让 RocketMQ 触发重试机制，过一会儿重新投递这条消息。为什么这么做？因为如果直接 return 跳过，万一正在处理的那个线程崩溃了，消息就丢了；抛异常让 RocketMQ 重试，给正在处理的线程一些时间完成。
第三步：正常处理 → 标记完成
SETNX 抢到锁后，进入业务处理——把统计数据写入各张统计表（PV/UV、操作系统、浏览器、设备、地区等）。处理成功后，把 Redis 里那个 key 的 value 从 "0" 改成 "1"。
这样一来，**后续如果 RocketMQ 重试投递了同一条消息，到达第一步时 SETNX 失败，查到 value 是 "1"，直接跳过——幂等达成。**
第四步：异常回滚
如果处理过程中抛了异常（比如数据库写入失败），catch 块里做两件事：先删掉 Redis 里的幂等 key，然后把异常继续往上抛。删掉 key 的作用是——如果不删，key 的 value 还是 "0"，TTL 还有 2 分钟，RocketMQ 重试投递时会发现 key 存在且是 "0"，又在第二步抛异常重试，这样死循环。删掉 key 后，重试消息到达时 SETNX 重新成功，重新走完整处理流程。
 
为什么 TTL 是 2 分钟
这个 TTL 是兜底用的。正常一条统计消息处理完也就几十毫秒到几百毫秒。2 分钟远远超出了正常处理时间，所以如果 2 分钟到了 key 过期了，只有一种可能——处理线程挂了或者卡死了，key 没来得及改成 "1" 也没来得及删除。这时候 key 自然过期消失，RocketMQ 重试到达时 SETNX 成功，消息被重新处理，不会丢失。
 
![[image.png]]

这个设计覆盖了三种情况：第一条消息正常处理（SETNX 成功 → 处理 → 标记完成 → 重复消息跳过）、处理失败需要重试（删 key → 抛异常 → 重试重新走 SETNX）、处理超时或线程崩溃（TTL 过期 → key 消失 → 重试时 SETNX 重新成功）。三种情况都保证了"消息至少被处理一次，但最多只生效一次"。

## ==5.那如果说我这里存进去了，但是消费失败了，会有这种情况吗？==
### 消费失败的完整链路
假设消息到达消费者，SETNX 写成功了，Redis 里 key 的值是 "0"。然后进入业务处理，比如往统计表里写数据的时候数据库连接断了，抛了异常。
这个异常会被 onMessage 方法里的 catch 块捕获，做两件事：
第一，删掉 Redis 里的幂等 key。 为什么呢？因为如果不删，这个 key 的值还是 "0"，TTL 还有 2 分钟。RocketMQ 检测到消费异常后会重新投递这条消息，重试的消息到达时，SETNX 发现 key 已经存在了，查 value 是 "0"（处理中），就又会抛异常让 RocketMQ 继续重试——这就死循环了。删掉 key 之后，重试消息到达时 SETNX 重新成功，重新走一遍完整流程，给了这条消息一个"从头再来"的机会。
第二，把异常继续往上抛。 为什么要抛？RocketMQ 需要知道消费失败了，才会触发重试机制。如果 catch 了不抛，RocketMQ 以为消费成功了，不会重新投递，消息就丢了。
所以完整路径是：处理失败 → 删 key → 抛异常 → RocketMQ 重试 → SETNX 重新成功 → 重新处理。
但是即使内部异常被吞导致的状态不一致，影响范围是一条统计数据的丢失，风险可控。

# 第五家
## 1.生成的这个链接会有冲突的情况吗？如果冲突了需要怎么处理啊？
## 为什么会有冲突
原因出在哈希算法上。我们用的是 MurmurHash32，32 位的哈希值域只有大约 43 亿个可能的结果。6 位 base62 编码有 568 亿个组合，远大于 43 亿——所以卡脖子的不是短码长度，而是哈希函数的输出空间。随着短链接数量接近 43 亿这个量级，两个不同的原始 URL 哈希出同一个短码的概率会越来越明显。
另外还有一个场景：两个用户在同一瞬间提交了完全相同的原始 URL，哈希结果一样，也会冲突。
 
## 第一层防护：生成时的布隆过滤器预判
generateSuffix 这个方法里有重试逻辑。哈希出短码后，**先经过布隆过滤器判断这个短链接是否已经存在吗**？如果没有被布隆过滤器拦截，就认为有冲突，重新生成一个UUID 作为盐重新哈希，再试一次。每次加盐后哈希结果完全不同，相当于换了一条全新的短码。
**最多重试 10 次**。如果 10 次生成的短码全部被布隆过滤器判定为"可能存在"，就抛异常让用户稍后再试。实际上这个概率极低——短链接总量远小于 43 亿时，连续 10 次恰好命中已存在的短码几乎不可能。
 
## 第二层防护：数据库唯一键兜底
即使布隆过滤器放行了，最终插入数据库时还有一个兜底——t_link **表上有一个唯一索引**，建在 full_short_url 和 del_time 的联合字段上。如果真的出现了极端的并发冲突（比如两个请求同一瞬间生成同一个短码，又都通过了布隆过滤器），数据库**会抛 DuplicateKeyException**。
代码里 catch 了这个异常，把它包装成业务异常返回给前端，提示"短链接生成重复"。这样虽然这次生成失败了，但不会产生脏数据，用户重新提交一次就行。
另外 catch 块里还有一个补救动作——把这条冲突的短链接补加进布隆过滤器。因为冲突发生说明布隆过滤器漏判了（没拦住这个已存在的短码），补加之后下次就不会再漏判同一个了。
 
有没有根本性的解决方案
当前的设计本质上是"冲突后重试"，像一个乐观锁——先假设不冲突，冲突了再换一个。对于当前项目规模完全够用。但如果有更高要求，可以换个思路——用发号器替代哈希。比如用雪花算法生成唯一 ID，转 base62 就是唯一短码，哈希都不需要了，从根本上消除冲突。代价是需要引入一个分布式 ID 生成组件，但换来了零冲突和更快的生成速度。

## 2.那你短链接生成之后，比如说当别人请求这个用户请求这个短链接的时候，你是怎么样去识别和转换到原来的链接上？
### 第一步：拿到短链接后缀，拼成完整地址
用户请求的是 /{short-uri} 这种路径，比如 /abc123。Controller 捕获到后缀 abc123 后，拼上默认域名，得到 short.domain/abc123 这个完整短链接。后续所有查询都围绕这个完整短链接展开。
 
### 第二步：先查 Redis 缓存——最快路径
用完整短链接拼一个 Redis key：short-link:goto:short.domain/abc123，直接 GET。这个 value 存的什么？就是原始长 URL。创建短链接的时候，我们插入数据库后做的第一件事就是把这个映射关系写进 Redis。
如果命中了，零等待，直接 sendRedirect 重定向走人。99% 以上的正常访问在这一步就结束了。
 
### 第三步：缓存没命中——反向路由表查数据库
缓存没命中，说明要么缓存过期了，要么这条短链接可能不存在。这时候需要去数据库查。
但这里有一个关键设计——分表。t_link 表是按 gid（分组标识）分片的，有 16 张表。而用户请求短链接时，只带了短链接本身，没有 gid。没有 gid 就不知道数据落在哪张表里，没法直接在 t_link 里查。
所以项目里专门设计了一张额外的反向路由表 t_link_goto。它只有三个字段：id、完整短链接、gid。它的作用就是根据完整短链接查出 gid。这张表也是 16 张分表，但分片键是 full_short_url 而不是 gid——因为查它的时候我们手里只有短链接，没有 gid。
查的流程是：先在 t_link_goto 里用完整短链接查到 gid，然后拿着 gid 去 t_link 表里查出完整的短链接记录（包含原始 URL、有效期、启用状态等）。

### 中间插入的防护层
在查数据库之前，还有三道防护：
布隆过滤器：判断短链接是否可能存在。说"不存在"就直接返回 notfound，数据库碰都不碰。
空值缓存：之前确认过不存在的短链接，30 分钟内不重复查库。
分布式锁：防止同一个短链接缓存过期瞬间的大量并发请求同时打到数据库（缓存击穿）。
只有穿过这三层防护的请求，才会真正去数据库里查 t_link_goto 和 t_link。
### 第四步：校验和重定向
数据库查到记录后，有三个校验：del_flag 是否已删除、enable_status 是否被禁用、validDate 是否已过期。任何一个不通过，就写空值缓存、跳 notfound 页面。
校验通过，拿到原始 URL 后，先做一件事——重建缓存。把原始 URL 写回 Redis，TTL 按链接有效期来算。这一步很关键，因为后续同样的请求就能走缓存快速路径了。
然后 sendRedirect 重定向，浏览器自动跳转到原始 URL。

识别和转换的流程就是：短链接 → Redis 缓存（快速路径）→ t_link_goto 路由表查 gid（确定分片）→ t_link 表查原始 URL（获取数据）→ 校验有效性 → 重建缓存 → 重定向。

## 3.还了解哪些其他的重定向方式？

 好问题。项目中用的是 Servlet 的 sendRedirect，底层发的是 302 临时重定向。除了这个，HTTP 协议和相关技术里还有好几种方式，
 
### HTTP 状态码层面的不同重定向
HTTP 重定向本质上是服务器返回一个 3xx 状态码，带上 Location 头指向目标地址，浏览器收到后自动跳转。关键的区别在于"永久还是临时"以及"是否保留请求方法"。
**301 永久重定向**：告诉浏览器和搜索引擎"这个资源已经永久搬走了，以后直接去新地址，别来找我了"。浏览器会把这个映射关系缓存下来，下次再访问同样的短链接时，浏览器本地就直接跳转了，请求根本不会打到我们的服务器。
这对短链接系统来说是个双刃剑——好处是服务器负载大幅降低；坏处是后续的访问我们完全感知不到，PV、UV、地区分布这些统计数据全部丢失。所以我们项目用 302 不用 301，就是为了保证每次点击都能被统计到。
**302 临时重定向**：就是我们项目在用的。告诉浏览器"资源暂时在这个地方，下次你还是来找我"。浏览器不会缓存，每次点短链接都会请求一次我们的服务器，所以统计数据是完整的。代价就是每次都有网络请求，服务器要扛流量，但我们已经用 Redis 多级缓存把压力控制住了。
**307 临时重定向**：跟 302 类似，但严格保留原始请求方法。比如 POST 请求被 302 重定向后，有些浏览器会偷偷把 POST 改成 GET；307 就强制保持 POST 不变。短链接场景基本都是 GET 请求，307 和 302 效果一样，用不上这个区别。
**308 永久重定向**：301 的严格版，永久 + 保留请求方法。同样不适合短链接统计场景。
### 非 HTTP **层面的方式**
**HTML Meta 刷新**：返回一个 HTML 页面，里面写 <meta http-equiv="refresh" content="0;url=目标地址">，浏览器解析后跳转。好处是可以在跳转前展示一些东西，比如广告、提示信息、倒计时。坏处是必须解析 HTML 才能跳，比 302 多了一步。短链接追求快速跳转，不适合。
**JavaScript 跳转**：window.location.href = "目标地址"。更灵活，可以实现条件跳转、延迟跳转、甚至先发一个埋点请求再跳。但依赖 JS 执行，如果用户禁了 JS 就失效了。一般用于需要打更多行为日志的场景。
**服务端代理/转发**：服务器自己去请求目标 URL，把返回的 HTML 原样吐给用户。用户的浏览器全程不知道目标地址，地址栏一直显示短链接地址。好处是可以做内容过滤、注入广告、完全控制响应；坏处是服务器要代理所有流量，带宽和 CPU 开销极高，而且 HTTPS 证书、跨域 Cookie 都有坑。只有一些特殊的"内容审查"或"反向代理"场景会用，短链接几乎没人这么干。

# 第六家
## 1.怎么做限流的？
### 第一层：Sentinel 接口级限流
这是针对短链接创建接口的限流，用的是阿里的 Sentinel。在 createShortLink 这个方法上加了 @SentinelResource 注解，资源名是 create_short-link，规则是 QPS=1。
意思是一秒钟只允许一次创建请求，超过就被挡掉。挡掉的请求不会直接报错，而是走自定义的兜底方法，返回一个友好的提示"当前访问网站人数过多，请稍后再试"。
这个规则是在应用启动时通过 SentinelRuleConfig 自动加载的，实现了 InitializingBean，在 Bean 初始化完成后就把流控规则注册到 Sentinel 的规则管理器里。
坦白说 QPS=1 是非常保守的值，更像是一个演示环境的保护机制——防止有人恶意批量生成短链接打爆数据库。真正上线的话，这个值需要根据服务器承载能力调到合理水位。
 
### 第二层：用户维度流量风控
这一层比 Sentinel 更细粒度，是基于 Redis + Lua 脚本实现的 Servlet 过滤器，按每个用户做限流。配置项有三个：是否开启、时间窗口（秒）、窗口内最大请求数。
具体实现是一个 UserFlowRiskControlFilter，注册为全局过滤器，拦截所有请求。每次请求进来，拿到当前用户名（网关传下来的），执行一段 Lua 脚本。
这个 Lua 脚本的逻辑很简单：用 short-link:user-flow-risk-control:{用户名} 作为 Redis key，执行 INCR 原子递增。如果是第一次请求（计数为 1），就设置过期时间等于时间窗口长度。最后返回当前窗口内的计数。过滤器拿到这个计数，跟配置里的 maxAccessCount 对比，超过就拦截。
用 Lua 脚本而不是 Java 代码分步操作的原因是保证原子性——INCR 和 EXPIRE 必须在一次 Redis 调用里完成，否则可能出现"计数加上了但过期时间没设成功"的情况，导致 key 永久存在、用户被永久限流。
这里有个细节：这层限流是可配置开关的——配置 short-link.flow-limit.enable=true 才会启用。而且放在网关鉴权之后（order=10），先确认用户身份再做限流，确保是按"已登录用户"来计数，而不是按 IP。

## 2.阿里的Sentinel底层是如何实现限流的？超过限流数的请求如何处理？直接丢弃吗？
### 底层数据结构：滑动时间窗口
Sentinel 的 QPS 限流不是简单的"每秒清零计数器"，而是用了一个叫滑动时间窗口的数据结构。具体来说，把一个统计周期（比如 1 秒）切成若干个小的时间窗口（Sentinel 默认是 2 个，每个 500 毫秒），这些小窗口串成一个环形数组，像俄罗斯方块一样不停往前滑动。
每个小窗口里维护一个计数器，记录这个 500 毫秒内来了多少请求。判断是否超限时，看的是当前时间往前推 1 秒这个区间里所有小窗口的计数之和。因为窗口在滑动，所以每一毫秒进来请求，看的都是"最近 1 秒"的真实数据，不是到整秒才重置。
打个比方：如果两个小窗口分别是 [0ms-500ms: 3次] 和 [500ms-1000ms: 4次]，那当前 QPS 就是 7。到了 600ms 时，第一个窗口过期被丢弃，换成新的 [500ms-1000ms: 4次] 和 [1000ms-1500ms: 1次]，QPS 变成 5。这样既避免了临界点突发（比如整秒重置导致的前后一秒各放一批、实际两秒内打了两倍流量），又保证了内存开销可控。
 
### 超过限流的请求怎么处理？不是直接丢弃
这个是重点。Sentinel 对于超限请求提供了三种流控效果，不是简单的"丢弃"：
**第一种：快速失败（默认）**。当请求超过阈值，直接抛一个 BlockException。但抛异常不等于请求就没了——需要开发者自己注册一个降级处理方法。我们在项目里就写了 CustomBlockHandler，超限时不是报 500 错，而是返回一条 JSON：{"code": "B100000", "message": "当前访问网站人数过多，请稍后再试..."}。用户看到一个友好的提示，而不是一个空白页面或者系统崩溃。从用户体验角度，这叫"优雅降级"，不是粗暴丢弃。
**第二种：Warm Up 预热**。系统刚启动时，限流阈值从较低的值逐步爬升到设定值，而不是一上来就全量放开。比如冷启动时只放行阈值的 1/3，慢慢加到满。这种适合应对"系统刚重启、缓存还没预热、数据库连接池还没打满"的场景，避免冷启动瞬间被打爆。
**第三种：排队等待**。超限的请求不直接拒绝，而是放进一个队列里，按恒定速率匀速通过。比如 QPS 设为 100，那就是每 10 毫秒放一个请求过去，不管请求是集中打进来的还是分散的。这个策略适合处理突发流量——高峰期来了很多请求，不是直接挡掉，而是让它们排着队慢慢处理，保证下游系统的压力始终稳定。

## ==3.双重判定锁说一下==
### 问题场景：热点短链接缓存过期
假设一条很火的短链接，缓存刚好过期了，这一瞬间涌入了 1000 个并发请求。
这 1000 个请求会依次经过前面的防护层：查 Redis 缓存——全部 miss；查布隆过滤器——全部通过（链接是存在的）；查空值缓存——全部 miss。然后这 1000 个请求同时来到了"要查数据库"这一步。
如果 1000 个请求全部去打数据库，就是一次典型的缓存击穿。虽然数据库扛得住几次，但 1000 个同时查同一行数据，完全是浪费。
 
### 第一重判定：加锁前查缓存
这 1000 个请求在加锁之前，已经各查了一次 Redis。结果都是 miss。这一步叫"第一重判定"——不涉及锁，性能无损，是正常的快速路径。
 
### 分布式锁：只放一个人进去
接下来，1000 个请求全部尝试获取同一把分布式锁 short-link:lock:goto:{url}。Redisson 的分布式锁保证：只有一个请求能拿到锁，剩下的 999 个在排队等着。
 
### 第二重判定：加锁后立即再查缓存
拿到锁的那个请求，做的第一件事不是查数据库，而是再次查 Redis 缓存——这就是"第二重判定"。
为什么？因为很有可能出现这种情况：当前这个请求在排队等锁的时候，上一轮的锁持有者已经查完了数据库、把原始 URL 写进了 Redis。等当前请求终于拿到锁的时候，缓存已经在了。如果直接去查数据库，就重复工作了。
同理，还会再查一次空值缓存。因为上一轮也可能发现短链接不存在，写了空值缓存。
**两次双重检查之后，如果缓存还是没有，说明是第一次回源——这才真正去查数据库。**
 
### 释放锁后，后续排队者的命运
锁释放后，排在第二的请求拿到锁。它执行第二重判定时，发现 Redis 里已经有缓存了（第一个请求刚写进去的），直接重定向走人，数据库碰都不碰。排在第三、第四……第 1000 的请求同理——全部被第二重判定拦住，不会再穿透到数据库。
![[image-1.png]]
最终效果：1000 个并发请求，只有 1 次数据库查询，999 次在第二重判定时直接从 Redis 读取，0 次击穿。 这就是双重判定锁的价值——不是让 1000 个请求都能查缓存（它们本来就能），而是让 1000 个请求里只有 1 个去查数据库。

## 4.sharding jdbc 分片策略？
### 项目用的是什么策略
我们用的是 ShardingSphere-JDBC 的 STANDARD 标准分片策略，配合 HASH_MOD 取模算法。整体是"只分表、不分库"——所有 16 张表都在同一个 MySQL 数据库实例 ds_0 里。
具体配置上，分三步看：
第一，声明逻辑表到物理表的映射。比如 t_link 这个逻辑表，物理上对应 ds_0.t_link_0 到 ds_0.t_link_15 这 16 张表。
第二，指定分片键。每张表的策略不同：
t_link 用 gid（分组标识），因为业务查询都是按分组来的
t_link_goto 用 full_short_url（完整短链接），因为跳转时只有短链接没有 gid
t_user 用 username，查用户信息天然按用户名
t_group 用 username，查用户的分组列表
第三，指定分片算法。全部用 HASH_MOD，分片数 16。底层就是 hash(分片键值) % 16，结果 0 落到 _0，结果 15 落到 _15。
 
### 为什么选 STANDARD + HASH_MOD
ShardingSphere 提供好几种分片策略，我们选 STANDARD 是因为它最简单直接——单分片键、单算法，足够覆盖我们的场景。比它更复杂的有 COMPLEX（多分片键）、HINT（代码手动指定路由），我们的查询模式不需要这些。
HASH_MOD 这个算法本身的特点是均匀分布。只要分片键的值是随机的，数据就会均匀散到 16 张表，不会出现"某张表特别大、某张表一直空着"的数据倾斜问题。而且路由精准——知道分片键就能直接定位到唯一一张物理表，不需要全表扫描。
但它也有缺点：扩容时数据要全量迁移，因为 16 变 32 后取模结果全变了。另外不支持范围查询——比如查"gid 在某范围内"的所有短链接，HASH_MOD 无法使用，因为 gid 的哈希是离散的，不是按顺序排列的。
 
### ShardingSphere 其他可选的策略
虽然项目里只用了一种，但我也了解过 ShardingSphere 的其他策略：
INLINE 行表达式：直接写 Groovy 表达式，比如 gid % 16。比 HASH_MOD 更灵活，可以加一些简单的取模范围逻辑。我们没用是觉得语义上 HASH_MOD 更清晰。
INTERVAL 范围分片：不是取模，而是按值域区间分片。比如 gid 从 0-1000 放表0、1001-2000 放表1。好处是扩容方便——加新区间就行，旧数据不用动；坏处是容易数据倾斜，热门区间可能被压爆。
COMPLEX 复合分片：支持多个分片键联合决策。比如同时按 gid 和 create_time 分片，可以同时支持"按分组查"和"按时间范围查"两种模式。但实现复杂，我们没有两个维度的强查询需求，就没用。
HINT 强制路由：代码里手动指定去哪个分片，完全绕开算法。一般用于特殊场景，比如管理员要全量扫描所有短链接时手动逐表遍历。
 
### 分片键选择的考量
这个值得单独说一下，因为选分片键是做分片最重要的决策。我们的原则是：按最高频的查询维度来选。
对于 t_link，99% 的查询是"查看某个分组下的短链接列表"，查询条件带 gid，所以用 gid 做分片键。代价是"根据短链接反向查"需要多一张 t_link_goto 路由表——但这是低频操作，完全值得。
对于 t_link_goto，查询永远是"根据完整短链接查 gid"，所以直接用短链接本身做分片键，一次命中。
这个设计是典型的以空间换主路径优化——写的时候多写一张表，换来主查询路径零跨表。如果不做这个设计，要么每条短链接查的时候 16 张表全扫一遍，要么选错分片键导致日常查询全部跨表聚合，两种都不可接受。

# 第七家
## 1.怎么设置布隆过滤器里面的
### 布隆过滤器的初始化配置
项目里有两套布隆过滤器，都在 RBloomFilterConfiguration 里通过 @Bean 注入到 Spring 容器。
用户注册用的布隆过滤器，两个核心参数：预计容量一亿，误判率千分之一（0.001）。分组标识用的容量更大，两亿。
这两参数配置是通过 Redisson 的 tryInit 方法完成的，背后会自动算出最优的位数组长度和哈希函数个数。一亿容量千分之一误判率，算下来大概是 1.4GB 的位数组和 10 个哈希函数。
 
### 踩过的坑：tryInit 的语义
这里踩了一个坑，值得特别说一下。tryInit 这个方法名里带 "try"，它的语义是——如果 Redis 里这个 key 已经存在了，就什么都不做。不会覆盖、不会重置、不会更新参数。
这意味着什么？比如我刚开始初始化的时候随便设了个参数，后来改了容量从一千万到一亿，重启应用——布隆过滤器还是旧的，一千万的容量。因为 key 已经在了，tryInit 直接跳过了。
要真想重建，必须先手动删掉 Redis 里对应的 key，再重启应用。或者在代码里加判断，先删再建。这个细节书上看不到，是实际调试的时候发现的。
 
### 布隆过滤器在 Redis 里的样子
Redisson 封装的布隆过滤器在 Redis 里不是一个简单的 key，而是一个分布式的数据结构。底层用的是 Redis 的 SETBIT 和 GETBIT 命令来操作位数组。
每次添加或查询一个元素时，Redisson 不会把整个 1.4GB 的位数组加载到客户端，而是把要操作的那几个位的偏移量算出来，发 SETBIT 或 GETBIT 命令给 Redis。Redis 在服务端按位操作，只有结果通过网络返回。所以性能很快，也不会撑爆客户端内存。
 
### 在业务链路中的使用方式
布隆过滤器在两个场景被调用：
创建短链接时，生成后缀后先 contains 判断是否可能已存在。如果可能冲突就加盐重新哈希，最多 10 次。创建成功后立即 add 把新短链接加进去。
访问短链接时，缓存没命中后先 contains 判断。如果返回 false，说明绝对不存在，直接返回 notfound，数据库都不碰。如果返回 true 才进入后续的兜底流程。
这两处调用都是通过注入的 Spring Bean 来用的，不用每次都创建新对象。而且 Redisson 的 RBloomFilter 是线程安全的，多个并发请求同时调用 contains 和 add 不会有并发问题——因为最终都是 Redis 单线程执行位操作命令。
 
### 关于容量预估
初始化时的容量选择也是一个需要权衡的点。不能太小——如果实际数据量超过了预估容量，误判率会急剧上升，布隆过滤器就"废了"。但也不能太大——位数组按容量线性增长，每一亿容量大概是 1.4GB，两亿就是 2.8GB，Redis 内存不能无限投入。
我们的做法是一次到位，留足余量。一亿用户对一个短链接 SaaS 系统来说是一个非常远期的目标，在实际业务增长到这个量级之前，完全可以换用拆分后的分布式布隆过滤器。所以当前 1.4GB 的内存开销是完全可以接受的。

## ==2.使用分布式读写锁保证大量访问是什么意思==
### 要解决什么并发冲突
这条短链接正在被大量用户点击，Redis 里已经聚积了一堆统计消息，RocketMQ 消费者在不断消费这些消息、把 PV/UV 等数据写入统计表。每条统计消息在处理时，都需要知道短链接的 gid（分组标识），因为统计是按 gid 维度聚合的。
与此同时，短链接的主人做了一个操作：把这条短链接从一个分组移动到另一个分组——也就是改了 gid。
如果不加控制，就会出现这样的竞态窗口：统计消费者刚读到 gid = A，准备往 A 的统计表里写数据；但在写入完成前，更新操作把 gid 改成了 B。结果这条统计数据挂在了旧分组 A 下，但实际上用户点击时链接已经在分组 B 了。数据出现了归属错乱。
 
### 为什么是读写锁，不是互斥锁
如果直接用一把互斥锁，那就变成了：要么统计在做、更新等着；要么更新在做、所有统计等着。问题是统计操作的并发量非常大——一条热门短链接可能每秒产生几千条统计消息。互斥锁让它们全部串行化，吞吐量瞬间崩塌。
读写锁的语义正好匹配这个场景：
读锁是共享的——多个统计消费者可以同时持有读锁、并行写入，互不阻塞
写锁是排他的——更新 gid 时获取写锁，此时所有统计消费者都被阻塞在门外，等写锁释放后才能继续
用两个场景对比就清楚了：
![[image-2.png]]
统计操作之间仍然并行，但更新操作强制串行化——等所有正在进行的统计写入提交后，更新 gid，后续的统计自然就用新的 gid 写了。
 
### 锁的粒度
这个读写锁的 key 是 short-link:lock:update-gid:{fullShortUrl}，按短链接维度加锁，不是全局的。也就是说，修改 "abc123" 的分组只会阻塞 "abc123" 的统计写入，"xyz789" 的统计丝毫不受影响。这个粒度控制是读写锁设计里很重要的一环——如果做成全局锁，所有短链接的统计全部互相串行，那系统基本就瘫痪了。
 
### 一句话总结
分布式读写锁在这里做了一件事：让成千上万的统计操作互不阻塞地并行执行，同时保证修改 gid 的瞬间不会产生任何归属错乱的脏数据。 等价于给统计操作开了 N 个门同时进，给更新操作只留一扇门，而且关门时所有统计门都先锁上——一扇门关上了，N 扇门同时锁住，完事后 N 扇门又同时打开。

## ==3.RocketMQ的削峰体现在哪里==
### 没削峰之前的问题
短链接的访问有一个明显特征：平时可能没什么人点，但一旦被转发——比如发微博、贴公众号——流量瞬间暴涨。可能在某一秒内，同一链接被点击了几千甚至几万次。
如果每次点击都同步往统计数据库里写 7 张表——PV/UV 统计表、地区分布表、操作系统表、浏览器表、设备表、网络类型表、访问日志表——数据库连接池秒秒钟被打穿。而且这些表之间存在关联（都依赖 gid），一次点击就是 7 次数据库写操作。几千次点击并行过来，数据库根本扛不住。
 
### 削峰怎么做的
用户点击短链接时，restoreUrl 方法里做统计的不是直接写数据库，而是把一次点击的完整统计信息（UV 标识、IP、浏览器、操作系统、设备、网络类型、地理位置）打包成一条 JSON 消息，扔给 RocketMQ。然后放下不管，直接走重定向。
这一步，把"用户等待"和"统计入库"两个动作解耦了。用户等待的时间只取决于消息发送有多快——同步发送通常几十毫秒——而不取决于往 7 张表里写数据有多慢。
RocketMQ 在中间扮演了一个蓄水池的角色。流量洪峰来的时候，消息疯狂涌入 Topic，但不会直接冲击数据库。消费者按照自己的节奏——**单线程、逐条消费——从队列里拉消息、慢慢写入 7 张统计表。**
![[image-3.png]]
数据库看到的始终是稳定的、可控的写入速率，而不是洪峰。消息堆在 RocketMQ 里慢慢消化，最多产生几分钟的统计延迟，但数据库不会被打挂。
 
### 跟分布式读写锁的配合
削峰和前面说的分布式读写锁是一起工作的。大量消息堆积后，消费者逐条消费时，每条消息会获取读锁——这些读锁是共享的，多个统计写入互不阻塞。但如果此时短链接主人改了 gid——获取写锁——就会暂时阻塞后续统计写入，等 gid 更新完成后再恢复。
削峰保证了消费者不会同时处理太多条消息把锁竞争搞得太激烈；读写锁保证了即使消息堆积被慢慢消化，每条统计数据的 gid 归属也不会错乱。
 
还有一个被注释掉的延迟队列方案
项目里还有一个 @Deprecated 的 DelayShortLinkStatsConsumer，用的是 Redisson 的延迟队列——不是 RocketMQ。它的思路是：点击后不立即发统计消息，而是延迟 5 秒再处理。设计意图是短时间内对同一条短链接的多次点击做聚合（比如 5 秒内来 100 次点击，合并成一次统计写入），进一步减少数据库压力。
但最终标记为废弃了，改用了 RocketMQ。因为 RocketMQ 本身就有消息堆积能力，已经起到了缓冲作用，再用延迟聚合增加了复杂度、引入了延迟消费的风险，性价比不高。
 
### 一句话概括
削峰就是：RocketMQ 顶在数据库前面当蓄水池，洪峰来了先存着，数据库按自己能承受的节奏慢慢消化。用户那边该跳转跳转，感知不到统计入库的任何延迟

# ==第八家==
## ==1.你的读写锁是如何实现的？用什么实现的？==
### 怎么用的
获取方式很直接：传一个 key 拿到读写锁对象，然后根据场景选读锁还是写锁。
统计消费者写入时调用 readWriteLock.readLock()，拿读锁
修改 gid 时调用 readWriteLock.writeLock()，拿写锁
锁的 key 是 short-link:lock:update-gid:{完整短链接}，按短链接维度隔离——改 abc123 的 gid 只会阻塞 abc123 的统计，不影响 xyz789。
核心语义是：读锁共享（多个统计同时持锁并行写），写锁排他（修改 gid 时所有统计全部等着）。
### Redisson 底层怎么在 Redis 上实现读写锁的
这个是关键。Redis 原生的 SETNX 只能做互斥锁，不支持"多读单写"。Redisson 是怎么在 Redis 上造出读写锁语义的？用了两个数据结构配合。
写锁用 Hash + 模式匹配。当写锁被获取时，往一个 Hash 里记录锁持有者的线程 ID。其他任何锁请求——不管是读还是写——来的时候，先检查这个 Hash 里是否有写锁持有者，有就等着。
读锁用 Hash + 计数器。读锁不是一把独占锁，所以不能简单用"是否有人持锁"来判断。Redisson 在 Hash 里为每个读锁持有者维护一个计数器。读锁请求来时，先检查有没有写锁——没有的话就递增自己的计数器，表示"我也是在读"。释放时计数器减一。
锁竞争时的公平排队。多个请求同时等待时怎么决定谁先拿？Redisson 用了 Redis 的 Pub/Sub 消息通知。等待者订阅一个频道，锁释放时持有者发布一条通知，所有等待者同时醒来竞争。为了避免惊群效应（所有人同时抢，只有一个人抢到其他人继续睡），Redisson 内部做了排队机制。
整把读写锁在 Redis 里实际存了两个 key——一个管锁状态（Hash），一个管等待队列。Redisson 客户端用 Lua 脚本来保证锁状态检查和更新的原子性——一次 Redis 调用完成"检查写锁是否存在 + 设置读锁计数"或"检查读写锁是否都释放 + 设置写锁持有者"。
 
### 跟我们前面聊的双重判定锁的区别
前面 restoreUrl 里用的也是分布式锁，但那是 Redisson 的普通互斥锁 RLock——只有"持有"和"不持有"两种状态，谁拿到谁干活，其他人排队。
读写锁比互斥锁多了"读共享"的能力。互斥锁会让所有统计操作串行化，读写锁让统计操作并行，只在修改 gid 的极短窗口内做互斥。这是读写锁存在的意义——最大化并发度，只在必须互斥的时候才互斥。

## ==2.缓存和数据一致性是如何做的？==
### 当前策略：Cache-Aside + 更新即删
项目用的是最经典的 Cache-Aside 模式，配合更新数据库后主动删除缓存的策略。
创建短链接时的流程是：先 INSERT 两张数据库表（t_link + t_link_goto），提交事务后，往 Redis 写缓存。**顺序是先写数据库、再写缓存**——如果数据库写入失败事务回滚，缓存不会留下脏数据。
更新短链接时的流程是：先 UPDATE 数据库，然后删除 Redis 里对应的跳转缓存 key。为什么是删缓存而不是更新缓存？因为"更新缓存"存在并发问题——A 线程刚刚 update 了缓存、还没来得及 update 数据库，B 线程 update 了数据库、又 update 了缓存，最后缓存和数据库谁新谁旧根本说不清。而"删除缓存"把这个不确定性变成了确定性——缓存没了，下次请求回源数据库重建，重建出来的肯定是最新的数据。
具体代码里，更新时判断了三种情况需要删缓存：有效类型变了、到期时间变了、原始 URL 变了。另外，如果旧链接之前已经过期（存在空值缓存），更新后把它复活了，还会额外删除空值缓存——否则用户访问时会被空值缓存挡住，明明已生效却跳 notfound。
 
### 已知的不一致窗口
坦率说，当前方案存在一个短暂的不一致窗口。时序是这样的：
更新请求修改了数据库，准备删缓存
就在删缓存之前，来了一个读取请求，缓存已过期，它去数据库查
读取请求查到了更新前的旧数据，准备写回缓存
更新请求删除了缓存
读取请求把旧数据写进了缓存
结果：缓存里是旧数据，数据库里是新数据，不一致。下一次读取时命中旧缓存，用户被重定向到旧的原始 URL，直到缓存下次过期或手动删除。
这个窗口极短——发生在"读取请求查完库、写缓存之前"和"更新请求删缓存"之间的一瞬间。对于短链接跳转场景，一条链接正在被修改的同时被访问的概率本身就很低，而且不一致的影响只是一次跳到了旧 URL，没有资金损失或数据安全问题，所以项目当前没有做额外的强一致性保证。
如果真要解决，业界有两个经典方案：一个是延迟双删——更新前删一次缓存，更新数据库，延迟几百毫秒后再删一次，保证并发读写回的脏数据能被第二次删除清掉；另一个是订阅数据库 binlog，用 Canal 监听 MySQL 变更，异步删除对应的缓存，把"更新后删缓存"这个动作从业务代码里剥离出来，变成独立的、可靠的过程。
 
### 创建时的缓存一致性
创建时是先写数据库再写缓存，也有一个小窗口：数据库写完了、缓存还没写进去，这时如果来了读取请求，缓存 miss，回源数据库能查到（已经写入了），再重建缓存，没有问题。如果缓存写入失败，读取请求还是会回源数据库，缓存最终还是会被补上。
 
### 一句话总结
当前的策略是数据库为王、缓存为辅，更新即删、读时重建。没有做延迟双删或 binlog 订阅，一致性的保障依赖于"短链接修改和访问的并发概率极低"这个业务特征，属于最终一致性 + 可接受的不一致窗口。对于跳转类业务，这个取舍是合理的。

## ==2.你的更新流程是怎么样的，如何进行一致性处理，你的策略是什么？==
### 更新流程分两条分支
updateShortLink 这个方法进来后，先查数据库确认这条短链接存在，然后根据gid 是否变化走两条不同的路。
分支一：gid 没变（纯字段更新）
就是普通的 UPDATE。拼一个 LambdaUpdateWrapper，条件是对齐 fullShortUrl + gid + 未删除 + 启用状态，然后 set 新值——原始 URL、描述、有效期类型、有效期时间、图标。一条 SQL 搞定，不涉及锁。
分支二：gid 变了（跨分组迁移）
这个复杂很多，因为 gid 是分片键，改了 gid 意味着这条短链接要从一张物理表"搬"到另一张。不能直接 UPDATE gid 字段——分片键在 ShardingSphere 下是不允许更新的。所以用的是软删除 + 重新插入的策略：
拿写锁（readWriteLock.writeLock()），锁的 key 是 short-link:lock:update-gid:{完整短链接}。这个锁的目的是阻塞统计消费者——迁移期间不能让统计数据还在往旧 gid 写。
把旧记录软删除：delFlag 置为 1，delTime 记录当前时间戳。
插入一条新记录，gid 用新的，同时继承旧记录的 shortUri、totalPv、totalUv、totalUip 等统计数据（不丢失历史统计）。
更新 t_link_goto 反向路由表：删掉旧的 gid 记录，插入新的 gid 记录。
finally 里释放写锁。
 
### 缓存一致性策略：先写库、后删缓存
两个分支执行完后，都会走到缓存处理逻辑。策略很明确——不是更新缓存，而是删除缓存。
判断条件是：有效期类型变了、有效期时间变了、原始 URL 变了，三者满足其一就删除跳转缓存 short-link:goto:{fullShortUrl}。
为什么是删而不是更新？因为更新缓存有并发时序问题——两个线程谁先写谁后写根本说不清。而删除缓存是确定的——缓存没了，下次请求自然回源查数据库，拿到的一定是最新数据。
 
### 空值缓存的特殊处理
还有一个细节：如果这条短链接之前已过期（validDate 早于当前时间），意味着之前的访问全部返回了 notfound 页面，空值缓存 short-link:is-null:goto:{fullShortUrl} 里存着 "-"。
但现在用户把有效期改成了永久或者改成了未来时间——链接"复活"了。如果不删空值缓存，接下来 30 分钟内所有请求都会被空值缓存挡掉，明明链接已经有效了用户却还是看到 notfound。
所以代码里做了这个判断：旧链接已过期 + 新链接变为有效 → 同时删掉空值缓存，让链接立即可用。
 
### 总结一句话
策略是 Cache-Aside 模式 + 删除而非更新。写数据库成功后，只删除相关的 Redis key，让下次读请求自然回源——用"下一次缓存的延迟"换取"数据一定一致"的确定性。

## 3.先更改库再删除缓存，先删缓存再更改库有什么区别？
这个问题是缓存一致性最经典的二选一，我从并发时序的角度说清楚两种方案的差异，以及为什么项目选了前者。
 
### 方案一：先删缓存、再改库
时序是这样的：
线程 A 删掉 Redis 缓存
线程 B 这时恰好来读——缓存 miss，查数据库，拿到旧数据，把旧数据写回 Redis
线程 A 这才 UPDATE 数据库，把新数据写进去
结果：数据库是新数据，Redis 里却是线程 B 写进去的旧数据。而且这个旧数据会一直留在 Redis 里，直到 TTL 到期或者下次更新——这期间所有读请求拿到的都是脏数据。
这个问题本质上是删除缓存和写入数据库之间有时间窗口，而读请求恰好在这个窗口里"帮倒忙"把旧数据塞回了缓存。
业界有个补救手段叫延时双删——先删缓存 → 改库 → 等几百毫秒 → 再删一次缓存。第二次删除就是专门清理"窗口期被读请求写进去的旧数据"。但"等几百毫秒"本身是拍脑袋的——等短了清不掉，等长了影响性能，很尴尬。
 
### 方案二：先改库、再删缓存（项目采用）
时序是：
线程 A 先 UPDATE 数据库成功
线程 A 再 DELETE Redis 缓存
最坏情况：线程 B 在线程 A 改完库、还没来得及删缓存时来读——缓存命中，拿到的是旧数据。
**但这个不一致窗口极短**——就是 UPDATE 和 DELETE 两条命令之间的几毫秒。而且随着 DELETE 执行完成，不一致立刻消失。相比之下，方案一里"线程 B 把旧数据写回缓存"导致的不一致会持续到 TTL 到期——可能是几小时甚至几天。
所以方案二的脏数据窗口比方案一短几个数量级，这也是为什么绝大多数系统选择这个顺序。
 
方案二的真正风险：删缓存失败
如果数据库 UPDATE 成功了，但删 Redis 缓存时网络抖了一下失败了——数据库是新数据，Redis 里还是旧的。没有重试的话，不一致一直持续到 TTL。
项目里目前也没有重试机制，这是一个可以坦白承认的不足。生产环境常见的补救方式有：
MQ 异步重试：删缓存失败后发一条 MQ 消息，消费者做指数退避重试删除
Canal + Binlog：监听数据库 binlog，检测到数据变更后自动删缓存，完全解耦业务代码
设置合理的短 TTL：项目里永久链接的缓存 TTL 是约 30 天，折中了一个平衡——太长脏数据持续久，太短缓存命中率低
 
### 项目为什么选先改库、再删缓存
三个原因：
一是刚才说的，不一致窗口极短。二是业务语义更自然——数据库是真理源，真理先变更，缓存后清理。三是如果改库失败事务回滚了，缓存根本不会被删——不会出现"库没变、缓存没了"的无谓 miss。
 
一句话总结
先删缓存后改库：风险是"读请求在窗口期把旧数据刷回缓存"，不一致持续时间长。先改库后删缓存：风险是"删缓存失败导致持久不一致"，不一致窗口短但需要兜底重试。项目选了后者，用短不一致窗口换确定性，但缺少删除失败的重试机制是可以改进的点。

## 4.你的短链接修改和布隆过滤器判重，不会冲突嘛？
我从两个维度——创建判重和访问重定向——分别分析修改操作和布隆过滤器之间会不会有冲突。
 
### 先说结论：创建判重这边没有冲突
布隆过滤器存储的是 fullShortUrl，判重的语义是"这个短链接是否已经存在"。修改短链接时——不管是改原始 URL、改有效期、还是改 gid——shortUri 和 fullShortUrl 都不变。布隆过滤器里这条记录依然有效，下次有人碰巧哈希出同样的短码，布隆过滤器说"可能存在"，触发重试加盐重新哈希，这正是我们想要的效果。
所以"修改"和"创建判重"之间没有矛盾——布隆过滤器只增不删，只要这条短链接还在系统里（哪怕是软删除状态），它的短码就不应该被别人复用。
 
### 但访问路径这边，gid 变更时存在一个短暂的数据缺口
这个是关键。看代码，gid 变更分支里的操作顺序是：
拿写锁 → 软删除旧 t_link 记录 → 插入新 t_link 记录 → 删旧 t_link_goto → 插新 t_link_goto → 释放写锁
问题在于：删旧 t_link_goto 和插新 t_link_goto 之间有间隙。在这个间隙里如果有用户请求这个短链接：
Redis 缓存 miss
布隆过滤器说"可能存在" ✓（位数组里这个 URL 没被删）
空值缓存 miss
拿到分布式锁 → 查 t_link_goto 表 → 查不到（旧记录刚被删，新记录还没插入）
判定短链接不存在 → 写空值缓存 30 分钟 → 返回 notfound
几毫秒后新 t_link_goto 插入成功，但空值缓存已经进去了——接下来 30 分钟，所有用户访问这个短链接都返回 notfound，链接明明已经好了却不可用。
 
### 为什么写锁没挡住这个场景
这里有个设计细节值得注意：更新操作拿的写锁 key 是 short-link:lock:update-gid:{fullShortUrl}，而访问路径拿的互斥锁 key 是 short-link:lock:goto:{fullShortUrl}——两把不同的锁。
写锁的设计目的是阻塞统计消费者（统计消费者拿的是同一把写锁下的读锁），而不是阻塞用户访问。所以用户在 gid 迁移期间依然可以正常发起请求，也恰好暴露了 t_link_goto 短暂空缺的问题。
 
### 这个问题的严重程度
坦诚说，概率极低，影响可控。要触发需要三个条件同时满足：gid 在变更 + 缓存刚好过期或 miss + 请求恰好落在删和插之间的几毫秒窗口里。即使命中，最多一两个请求写入了空值缓存，让链接暂时不可用。比"先删缓存后改库"那种动辄脏数据留存几小时的问题轻得多。
如果要根治，可以在 gid 变更逻辑里，操作完 t_link_goto 后主动删一次空值缓存——就跟更新有效期时"复活"链接的处理方式一样。
## 5.你解决缓存击穿用的锁是lock还是trylock,为什么不用另一种锁

## 为什么用 `lock()` 而不是 `tryLock()`
这和解决的场景——**缓存击穿**——密切相关：

| | `lock()` | `tryLock()` |
|---|---|---|
| **行为** | 获取不到锁时**阻塞等待**，直到获取成功 | 获取不到锁时**立即返回 false**，不等待 |
| **请求结果** | 所有请求最终都能拿到数据 | 没抢到锁的请求会直接失败 |

**核心原因：不能让请求直接失败。**

缓存击穿的处理流程是：

```
大量并发请求 → 都发现 Redis 没数据
    ↓
只有第 1 个请求拿到 lock，去查数据库
    ↓
其他 99 个请求被 lock() 阻塞，原地等待
    ↓
第 1 个请求查完数据库、写入 Redis、释放锁
    ↓
其他 99 个请求逐个获得锁 → 双重检查(第267行) → 直接从 Redis 拿到数据 → 返回
```


如果用 `tryLock()`，后面 99 个请求抢锁失败后会立即返回 false，用户看到的就是**错误页面**，这显然不可接受。

## 另一个关键细节：双重检查

注意第 267 行——持有锁之后**又重新查了一次 Redis**：

```java
originalUrl = stringRedisTemplate.opsForValue().get(
    String.format(RedisKeyConstant.GOTO_SHORT_LINK_KEY, fullShortUrl));
```


这正是 `lock()` + **双重检查**的经典组合：**第一个请求写完缓存后释放锁，后面排队的请求拿到锁后，直接从 Redis 命中数据，根本不需要再查数据库了。**

**总结**：`lock()` 把并发请求从"抢着打数据库"变成了"排队等缓存"，保证每个用户请求都能正常返回，而不是直接报错。

## 6. 短链接生成原理，为什么使用murmurhash？有调研过其他哈希算法吗？为什么不用其他哈希算法？Murmurhash原理？为什么要用base62编码？
这几个问题串起来正好是短链接生成链路的完整画像，我一个一个说。

---
**短链接生成原理**

流程是 `原始 URL + 随机盐 → MurmurHash32 → base62 → 6 位短码`。

具体来说，每次生成时把用户的原始长 URL 拼上一个 `UUID.randomUUID()` 作为随机盐，然后喂给 MurmurHash32 得到一个 32 位整数。这个整数转成正数后做 base62 编码，得到 6 个字符。接着拿这个短码拼上域名，去布隆过滤器问"这个链接存在吗？"不存在就通过，存在就重新加盐再哈希，最多重试 10 次。最后把短码持久化到数据库并在布隆过滤器注册。

UUID 随机盐的作用很关键——同一个用户短时间内提交相同的原始 URL，如果不用随机盐，哈希结果完全一样，就会出现自己和自己冲突。加上 UUID 后每次哈希的输入都不同，输出自然也不同，避免了同源冲突。

---

**为什么用 MurmurHash，做过调研吗**

做短链接系统时，哈希算法的选择主要看三个维度：**速度、分布均匀度、输出长度是否可控**。MurmurHash 在这三个维度上最适合短链接场景。

坦诚说，项目里没有对其他算法做代码级的对比测试——直接用了 Hutool 提供的 MurmurHash 实现。但从业界的共识和算法本身的设计来看，选择是有道理的：

| 算法                   | 输出长度      | 速度  | 适用场景      |
| -------------------- | --------- | --- | --------- |
| **MurmurHash32**     | 32 位      | 极快  | 哈希表、短链接   |
| **MD5**              | 128 位     | 中   | 完整性校验、签名  |
| **SHA-256**          | 256 位     | 慢   | 安全加密、区块链  |
| **CRC32**            | 32 位      | 快   | 数据校验、但不均匀 |
| **xxHash/ CityHash** | 32/64/128 | 极快  | 同类替代，也很优秀 |
|                      |           |     |           |

MD5 和 SHA-256 干掉的原因很简单：一是太重了，安全哈希为了防碰撞和防逆向做了大量轮次运算，生成一条短链接要毫秒级，高并发下扛不住；二是输出太长，128 位转 base62 有 22 个字符，做短链接毫无意义——就算截断前面几位，也等于把 128 位的均匀分布特性主动破坏掉了，截断后的碰撞概率反而不可控。

CRC32 的问题是分布不够均匀，某些输入会产生聚集，导致短码冲突率偏高。xxHash 和 CityHash 其实是 MurmurHash 的同代竞争者，速度上 xxHash 甚至略快一点，但 MurmurHash 在 Java 生态里通过 Hutool 和 Guava 的集成度更高，落地成本低。

---

**MurmurHash 原理**

MurmurHash 名字来源于它的核心操作——**Mu**ltiply（乘法）和 **R**otate（旋转），"murmur"就是这两个词拼接出来的。

内部不依赖任何密码学原语，就是纯粹对 32 位整数做乘法、异或、位移这些 CPU 原生指令。核心逻辑大概是这样：

1. 把输入字节流按 4 字节一块分组
2. 每块乘一个大常数（如 `0x5bd1e995`），然后做位旋转（循环移位），再做异或混合
3. 对最后不足 4 字节的尾部做特殊处理
4. 最后对结果再做一轮"finalization"——乘大常数后异或、移位——目的是让高位和低位充分混合

这个 finalization 步骤很关键，它保证了**雪崩效应**——输入哪怕只改一个 bit，输出也会有一半的 bit 跟着翻转。这也是为什么加上 UUID 盐后哈希结果能完全不同。

int 值域有约 43 亿个可能，6 位 base62 有约 568 亿个组合，所以碰撞瓶颈在哈希输出空间而不在编码长度。但 43 亿对短链接场景来说已经足够——即使存了 1 亿条短链接，理论碰撞率也在千分之一以下，加上布隆过滤器的预判和重试机制，实际撞墙的概率更低。

---

**为什么用 base62 编码**

base62 的字符集是 `[0-9, A-Z, a-z]`，共 62 个字符。这么选有三层原因：

**第一层，URL 安全性。** base62 不包含 `+`、`/`、`=` 这些 base64 里的特殊字符，放在 URL 路径里不需要任何百分号转义，浏览器直接认识。也不包含容易混淆的字符如 `l/1/I`、`O/0`，用户手打不容易出错。

**第二层，编码密度高。** 62 个字符意味着每位能表示 62 种状态。对比十六进制的每位 16 种、十进制的每位 10 种，同样 6 位字符，base62 能表示 568 亿种，十六进制只能表示 1677 万种——差距是 3400 倍。

**第三层，长度刚好。** 32 位哈希值域约 43 亿，转成 base62 正好 6 个字符。像 `a3Bx9q` 这样，不长不短，短信友好，肉眼能快速扫读。相比 TinyURL 那种递增 ID 转 base62 的方案（历史上有很多短链接系统用自增 ID 再 base62 编码），哈希方案多了随机盐带来的防枚举性——用户不能通过递增遍历来发现别人的短链接。

---

**一句话总结**

选 MurmurHash 是**用安全换速度**——短链接不需要密码学级别的单向性和防碰撞，但需要极快的生成速度和合理的均匀分布。选 base62 是**用编码空间换 URL 友好性**——62 个字符刚好覆盖 URL 安全字符集的同时足够密集，6 位就能装下哈希产生的全部值域。
