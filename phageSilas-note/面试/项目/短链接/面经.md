## 1.短链接怎么生成的？
整体思路是：拿到原始长链接 → 哈希计算 → Base62 编码 → 得到一个短码。
具体来说，我们用的哈希算法是 MurmurHash。选它而不是 MD5 或 SHA，主要是因为它是一个非加密型哈希，速度快、碰撞率低，更适合短链接这种对性能敏感的场景。这个算法会把输入的字符串映射成一个 32 位的整数。
然后我们把这个整数转成 Base62 编码——也就是用 0-9、A-Z、a-z 这 62 个字符来表示。这样每个字符能表示 62 种状态，比纯数字或纯十六进制要紧凑得多，6 位就能表示几百亿的组合，足够用了。
但这里有个问题：如果两个不同用户同时对同一个长链接创建短链接，生成的后缀可能就是一样的。所以我们做了一步处理——生成哈希之前，会在原始 URL 后面拼上一个随机 UUID，这样输入就不一样了，极大降低了碰撞概率。
另外，生成的短链接还会和域名拼接成完整的短 URL，缓存到 Redis 里，这样后续访问时直接走缓存，不用每次都查库。
## 2.怎么确保短链接的唯一？
第一层：布隆过滤器预判。 在往数据库插入之前，先用布隆过滤器检查这个短链接是否已经存在。布隆过滤器是一种空间效率极高的概率型数据结构，它可能误判（说存在但实际不存在），但不会漏判（说不存在就真的不存在）。这里我们初始化时设了 1 亿的预期容量和千分之一的误判率。如果布隆过滤器说"没重复"，我们就可以放心去插入。
第二层：数据库唯一索引兜底。 短链接表里有一个联合唯一索引，建在"完整短 URL + 删除时间戳"上。即使布隆过滤器误判了、让一个重复的短链接漏过去，数据库也会直接抛 DuplicateKeyException，保证不会写入重复数据。这时候我们会把这个短链接加进布隆过滤器，然后提示用户"生成重复，请重试"。
第三层：还有一条额外的路径——分布式锁方案。 这是另一种实现方式，不用布隆过滤器，而是用 Redisson 分布式锁串行化创建过程，锁住之后直接查数据库判断是否重复。这种方案更保险但性能不如布隆过滤器，所以我们把它作为一个备用方案保留，默认还是走布隆过滤器的路径。

## 布隆过滤器的原理？有什么缺点？短链接存满了怎么扩容？占用多少空间？
### 原理
布隆过滤器本质上就是一个很长的二进制位数组 + 多个哈希函数。
具体流程是：当我们要标记"某个短链接已存在"的时候，会把这个短链接用多个不同的哈希函数各算一遍，得到几个位置，然后把位数组里这几个位置都标成 1。查询的时候也一样——用同样的哈希函数算出那几个位置，如果所有位置都是 1，就认为"可能存在"；如果有任何一个位置是 0，就说明"一定不存在"。
这里的关键在于"可能存在"这四个字。它不会漏判，但会误判——因为不同元素经过哈希后可能映射到相同的位置，A 元素把某些位标成了 1，B 元素来查的时候发现这些位也是 1，就被误判为存在了。
我们项目里给它初始化的时候，设了两个参数：预期元素数量 1 亿，误判率千分之一。在这两个参数下，Redisson 底层会自动算出需要多大的位数组和多少个哈希函数。
### 缺点
第一，不支持删除。 这是最经典的问题了。布隆过滤器不能随便把某一位改成 0，因为那一位可能同时被多个元素共用，你改了一个，别的元素就查不到了。我们在项目里也确实没做删除——短链接就算被删了，布隆过滤器的记录也还在，不过这个误判只是多查一次数据库，影响不大。
第二，有误判率。 千分之一的意思是一千次查询里大约有一次会误判。我们项目里用数据库唯一索引兜底，所以即使误判了也不会导致数据重复，只是多了一次无效的数据库写入。
第三，不能枚举。 你没法知道布隆过滤器里到底存了哪些元素，它只能回答"是不是可能存在"。
还有一个实际遇到的坑：Redisson 的 tryInit 方法，如果 Redis 里已经存在这个 key，它是 no-op 的，什么都不会做，也不会覆盖。 这意味着如果你想重新初始化或者扩容，必须先手动把 Redis 里的 key 删掉，不然调 tryInit 是无效的。

### 短链接存满了怎么扩容？
坦白说，我们项目里没有做自动扩容机制。布隆过滤器创建的时候就固定了容量，位数组大小和哈希函数数量都是初始化时算好的。
如果真的需要扩容，思路一般有几种：
最直接的是：删除旧 key，重新建一个更大的，然后全量扫描数据库重建数据。启动时或定时任务把数据库里所有存活的短链接重新加入新的布隆过滤器。但这个过程对大表来说会比较耗时。
更优雅的做法是多级布隆过滤器：旧的满了就新建一个，查询的时候先查新过滤器再查旧的。不过这样会线性增加查询开销。
还有一种思路是用可扩展布隆过滤器（Scalable Bloom Filter），它内部维护一个布隆过滤器列表，满了就追加新的，查询时遍历所有。但 Redisson 没有原生支持，需要自己实现。
如果要我现在做改进的话，我可能会在监控层面加一个告警——当布隆过滤器的元素数量接近初始化容量时，提前通知人工介入迁移，而不是等到满了才发现。

## 3.短链接监控消息队列的消息幂等？消息队列顺序性？
### 消息幂等
我们项目用的是 Redis Stream 作为消息队列。为什么需要幂等？因为消费过程中可能出现各种异常——比如消费到一半服务挂了，Redis Stream 会把这条消息重新投递，如果不做幂等，统计数据就可能重复累加。
我们实现了一套基于 Redis 的三段式状态机来保证幂等：
第一阶段：标记"正在消费"。 消费者拿到一条消息后，先用 Redis 的 setIfAbsent 命令，以消息 ID 作为 key，写入一个标记值 "0"。setIfAbsent 是原子操作，只有 key 不存在时才会写入成功。如果写入失败，说明这条消息已经在被处理了。
第二阶段：判断是否已完成。 如果发现消息已经在处理中，就去查这个 key 的 value。如果是 "1"，说明上一次已经消费成功了，直接跳过；如果还是 "0"，说明上一次处理到一半就挂了，这时候抛异常让 Redis Stream 重新投递。
第三阶段：标记完成或清理。 正常情况下，消费成功后把 value 更新为 "1"。如果消费过程中抛异常了，就删除这个幂等 key，这样下次重试时可以重新进入"正在消费"的状态。
整个幂等标记设置了 2 分钟的过期时间，避免 Redis 里堆积太多临时数据。
这里面有个比较巧妙的设计：用 "0" 和 "1" 两个状态区分"处理中"和"已完成"，而不是简单的 boolean。这样就能准确判断上一次是中途挂了还是正常完成了，不会漏消费也不会重复消费。
