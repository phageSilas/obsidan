# 第一家
## 1.短链接怎么生成的？
整体思路是：拿到原始长链接 → 哈希计算 → Base62 编码 → 得到一个短码。
具体来说，我们用的哈希算法是 MurmurHash。选它而不是 MD5 或 SHA，主要是因为它是一个非加密型哈希，速度快、碰撞率低，更适合短链接这种对性能敏感的场景。这个算法会把输入的字符串映射成一个 32 位的整数。
然后我们把这个整数转成 Base62 编码——也就是用 0-9、A-Z、a-z 这 62 个字符来表示。这样每个字符能表示 62 种状态，比纯数字或纯十六进制要紧凑得多，6 位就能表示几百亿的组合，足够用了。
但这里有个问题：如果两个不同用户同时对同一个长链接创建短链接，生成的后缀可能就是一样的。所以我们做了一步处理——生成哈希之前，会在原始 URL 后面拼上一个随机 UUID，这样输入就不一样了，极大降低了碰撞概率。
另外，生成的短链接还会和域名拼接成完整的短 URL，缓存到 Redis 里，这样后续访问时直接走缓存，不用每次都查库。
## 2.怎么确保短链接的唯一？
第一层：布隆过滤器预判。 在往数据库插入之前，先用布隆过滤器检查这个短链接是否已经存在。布隆过滤器是一种空间效率极高的概率型数据结构，它可能误判（说存在但实际不存在），但不会漏判（说不存在就真的不存在）。这里我们初始化时设了 1 亿的预期容量和千分之一的误判率。如果布隆过滤器说"没重复"，我们就可以放心去插入。
第二层：数据库唯一索引兜底。 短链接表里有一个联合唯一索引，建在"完整短 URL + 删除时间戳"上。即使布隆过滤器误判了、让一个重复的短链接漏过去，数据库也会直接抛 DuplicateKeyException，保证不会写入重复数据。这时候我们会把这个短链接加进布隆过滤器，然后提示用户"生成重复，请重试"。
第三层：还有一条额外的路径——分布式锁方案。 这是另一种实现方式，不用布隆过滤器，而是用 Redisson 分布式锁串行化创建过程，锁住之后直接查数据库判断是否重复。这种方案更保险但性能不如布隆过滤器，所以我们把它作为一个备用方案保留，默认还是走布隆过滤器的路径。

## 布隆过滤器的原理？有什么缺点？短链接存满了怎么扩容？占用多少空间？
### 原理
布隆过滤器本质上就是一个很长的二进制位数组 + 多个哈希函数。
具体流程是：当我们要标记"某个短链接已存在"的时候，会把这个短链接用多个不同的哈希函数各算一遍，得到几个位置，然后把位数组里这几个位置都标成 1。查询的时候也一样——用同样的哈希函数算出那几个位置，如果所有位置都是 1，就认为"可能存在"；如果有任何一个位置是 0，就说明"一定不存在"。
这里的关键在于"可能存在"这四个字。它不会漏判，但会误判——因为不同元素经过哈希后可能映射到相同的位置，A 元素把某些位标成了 1，B 元素来查的时候发现这些位也是 1，就被误判为存在了。
我们项目里给它初始化的时候，设了两个参数：预期元素数量 1 亿，误判率千分之一。在这两个参数下，Redisson 底层会自动算出需要多大的位数组和多少个哈希函数。
### 缺点
第一，不支持删除。 这是最经典的问题了。布隆过滤器不能随便把某一位改成 0，因为那一位可能同时被多个元素共用，你改了一个，别的元素就查不到了。我们在项目里也确实没做删除——短链接就算被删了，布隆过滤器的记录也还在，不过这个误判只是多查一次数据库，影响不大。
第二，有误判率。 千分之一的意思是一千次查询里大约有一次会误判。我们项目里用数据库唯一索引兜底，所以即使误判了也不会导致数据重复，只是多了一次无效的数据库写入。
第三，不能枚举。 你没法知道布隆过滤器里到底存了哪些元素，它只能回答"是不是可能存在"。
还有一个实际遇到的坑：Redisson 的 tryInit 方法，如果 Redis 里已经存在这个 key，它是 no-op 的，什么都不会做，也不会覆盖。 这意味着如果你想重新初始化或者扩容，必须先手动把 Redis 里的 key 删掉，不然调 tryInit 是无效的。

### 短链接存满了怎么扩容？
坦白说，我们项目里没有做自动扩容机制。布隆过滤器创建的时候就固定了容量，位数组大小和哈希函数数量都是初始化时算好的。
如果真的需要扩容，思路一般有几种：
最直接的是：删除旧 key，重新建一个更大的，然后全量扫描数据库重建数据。启动时或定时任务把数据库里所有存活的短链接重新加入新的布隆过滤器。但这个过程对大表来说会比较耗时。
更优雅的做法是多级布隆过滤器：旧的满了就新建一个，查询的时候先查新过滤器再查旧的。不过这样会线性增加查询开销。
还有一种思路是用可扩展布隆过滤器（Scalable Bloom Filter），它内部维护一个布隆过滤器列表，满了就追加新的，查询时遍历所有。但 Redisson 没有原生支持，需要自己实现。
如果要我现在做改进的话，我可能会在监控层面加一个告警——当布隆过滤器的元素数量接近初始化容量时，提前通知人工介入迁移，而不是等到满了才发现。

### 占用多少空间？
这个可以算出来。根据公式，要让 1 亿条数据保持千分之一误判率的话：
位数组大小大约是 14.4 亿位，换算下来就是 1.44 × 10⁹ / 8 ≈ 1.8 亿字节，约 172 MB。哈希函数需要大约 10 个。
也就是说，用 172 MB 的 Redis 内存，就能索引 1 亿个短链接。对比一下，如果全存 Redis 的字符串 key，1 亿个每个就算只占几十字节，也是好几个 GB 起步。所以布隆过滤器的空间优势非常明显——内存占用量跟存的元素数量成正比，跟元素本身的大小无关，一个几字节的短码和一个几千字节的长 URL，在布隆过滤器里占用的位是一样的。

## 3.短链接监控消息队列的消息幂等？消息队列顺序性？
### 消息幂等
我们的做法是借助 Redis 来实现消费幂等。整体思路分三步：
第一，消息到达消费者时，先拿消息的唯一标识去 Redis 里做检查——用的是 Redis 的 SETNX 命令，也就是"不存在才写入"的原子操作。如果写入成功，说明这条消息是第一次来，可以继续处理；如果写入失败，说明已经有人在处理了，就不重复消费。
第二，处理过程中还有一层状态标记。我们用 Redis 里的值来区分两种状态：值是 "0" 表示正在处理中，值是 "1" 表示已完成。这样如果消息重试到达时发现已经标记为 "1"，就直接跳过，避免重复入库。
第三，异常处理也很关键。如果消息处理到一半抛出异常，我们会主动删除这个幂等标识，让 RocketMQ 的重试机制能够重新投递这条消息；如果处理成功，就标记为 "1"。这样既保证了"至少处理一次"，又通过幂等判断保证了"实际生效一次"。
另外有个小细节，这套幂等标识设置了 2 分钟的过期时间。为什么是 2 分钟呢？因为正常的统计写入操作基本在秒级完成，2 分钟已经是很宽裕的兜底时间了——如果 2 分钟还没处理完，说明可能出了严重问题，这个标识自然过期也没关系，RocketMQ 可以重新投递。

### 队列顺序性
这个要坦诚说，我们项目里没有对消息顺序性做严格的保证。
原因在于我们的场景——短链接访问统计，它的数据特点是什么？PV、UV、地区、浏览器、操作系统这些维度的统计，本质上是在做累加。比如今天这条短链接来了 10 次访问，不管消息到达的顺序是 1→2→3 还是 3→2→1，最终累加出来的结果是一样的。所以我们追求的是"最终一致性"，而不是严格的顺序性。
如果非要保证顺序性，RocketMQ 本身是支持顺序消息的——可以把同一个短链接的消息都发到同一个 MessageQueue 里，这样消费者按单线程消费就能保证顺序。但代价是吞吐量会下降，而且消费失败后的重试机制也会打断顺序。对于我们这种统计场景来说，用顺序消息的代价大于收益，就没必要了。
所以总结一下：我们的设计思路是用幂等保证数据不重复、不丢失，用最终一致性接受短时间的统计延迟，而不是强依赖消息顺序。
## 4.短链接表的分表怎么做的？分表下怎么扩容？
### 分表
我们这个项目用的是 ShardingSphere 5.x 来做分表，核心策略就是基于分片键的取模哈希。
以短链接主表 为例：我们选的分片键是分组标识。为什么选分组标识 而不是短链接本身？因为在实际业务中，用户查询和管理短链接都是按"分组"维度来操作的——比如用户打开某个分组，看到的是这个分组下所有的短链接。用分组标识做分片键，意味着同一个分组的所有短链接会落在同一张物理表里，这样按分组查询时只需访问一张表，避免了跨表查询的性能问题。
具体配置上，ShardingSphere 用的是 HASH_MOD 算法，分片数量是 16，也就是分组标识的哈希值对 16 取模，结果 0 就落到 t_link_0，结果 1 落到 t_link_1，以此类推，总共 16 张表。

### 扩容
这个必须坦诚说，用 HASH_MOD 取模分片有一个天然的缺陷——扩容很麻烦。
因为一旦分片数变了，比如从 16 扩到 32，原来的 hash("abc") % 16 = 5 这条数据，在新算法下可能变成 hash("abc") % 32 = 21，路由完全变了。这意味着扩容时需要进行全量数据迁移，把所有历史数据按新规则重新分配到新表里，这个过程涉及数据双写、一致性校验、灰度切换等，成本非常高。
但我们当时为什么还是选了 HASH_MOD 呢？有两个考虑：
第一，这是一个面向学习的项目，16 张表对于演示分表机制已经足够了，不需要在项目里演示完整的动态扩容流程。
第二，在生产实践中，一个常用且务实的做法是翻倍扩容。比如从 16 扩到 32，算法虽然变了，但数据迁移有规律可循——原来 t_link_0 的数据只会流向新的 t_link_0 和 t_link_16，因为 n % 16 和 n % 32 的关系是有确定性的：如果 n % 16 = 0，那么 n % 32 只能是 0 或 16。这样我们可以"一拆二"地迁移，每张旧表的数据只散列到两张新表中，迁移范围是可控的。
如果让我重新设计，我可能会考虑两种改进方向：一是在分片键里引入时间维度，比如按月份分表，这样新月份自动落到新表，天然免迁移；二是用一致性哈希，避免取模算法在节点变化时的大面积重分布。不过这两个方案也各有代价——时间分片会导致冷热数据不均，一致性哈希在 ShardingSphere 里需要自定义算法，复杂度会高一些。
所以整体思路就是：用取模哈希实现快速路由，用分组标识保障查询亲和性，扩容靠翻倍策略做可控迁移——在当前项目规模下，这是一个合理的折中。

## 5.redis中短链接的过期时间如何设置？一段时间内redis缓存的短链接太多导致redis内存满了怎么办？淘汰哪些短链接？内存淘汰和过期删除的策略？

### 过期时间
我们项目里对缓存的过期时间是分两种情况处理的，核心逻辑就在创建短链接时。
第一种，如果用户创建短链接时设置了有效期——比如这条链接只在 7 天内有效——那我们缓存的 TTL 就是从现在到有效期结束的剩余毫秒数。也就是说，链接本身过期了，缓存也跟着自动过期，不会残留无效数据。
第二种，如果是永久有效的短链接，我们给了一个默认的缓存过期时间，大概是 30 天。为什么不设置成"永不过期"呢？因为 Redis 内存是有限资源，永久有效的话，冷数据会一直占着内存不放。
另外项目里还有一个"空值缓存"——当用户访问一个不存在的短链接时，我们会往 Redis 里写一个标记，过期时间设成 30 分钟。目的是防止有人恶意构造大量不存在的短链接来穿透缓存打到数据库上。

### 内存满了怎么办
坦诚说，我们项目里目前没有做专门的缓存淘汰策略配置，更多是依赖 Redis 自身的机制。但这个问题确实值得讨论，我分几个层面来说。
首先，我们项目里 Redis 存的短链接缓存，每条数据是什么体量？就是一个 key 是完整短链接、value 是原始 URL，外加一个 TTL。一条记录大概也就几百字节，假设一条 500 字节，一百万条也才 500MB 左右。对于单机 Redis 来说，内存压力并没有想象中那么大。真正占内存的其实是那些没有 TTL 的、或者 TTL 很长的 key 持续堆积。
那如果确实内存满了，Redis 会怎么做？这就涉及两个概念：过期删除和内存淘汰，它们不是一回事。
过期删除是 Redis 对已经设置了 TTL 的 key 的清理机制，有两种方式配合使用：一种是惰性删除，就是每次访问一个 key 时顺带检查是否过期，过期了就删；另一种是定期删除，Redis 每隔一段时间随机抽一批 key 检查，把过期的清理掉。这样既不会因为轮询所有 key 而阻塞主线程，也不会让过期 key 长期赖着不走。
内存淘汰是当 Redis 内存使用达到 maxmemory 上限时触发的策略。Redis 提供了好几种淘汰策略，我觉得跟我们场景相关的主要是两种：一个是 volatile-lru，只从设置了 TTL 的 key 里淘汰最近最少使用的；另一个是 allkeys-lru，从所有 key 里淘汰最近最少使用的。

### 淘汰哪些短链接
如果要我来选淘汰策略，我会倾向于 allkeys-lru。原因很简单——短链接的访问有明显的热点效应。一条营销活动链接可能在活动期间被疯狂点击，但活动一结束就很少有人访问了。LRU 算法天然会把那些"很久没人点"的冷门链接缓存淘汰掉，而保留高频访问的热门链接在内存里。
就算某个冷门链接的缓存被淘汰了也没关系——下次有人点击时，会触发缓存回源，从数据库里查出来再写回 Redis，代价就是一次缓存穿透的开销，但我们前面有布隆过滤器挡着，不会真的每次都打到数据库。
如果不用 LRU 而用 TTL 优先淘汰（volatile-ttl），可能会误伤一些 TTL 设置得比较短但实际还很热的链接，反而不如 LRU 贴合业务。当然，TTL 短本身说明这条链接有效期短，淘汰了影响也不大，所以两种策略在这个场景下都能接受。
总结一下：我们项目的设计思路是靠 TTL 做第一层自然淘汰，靠布隆过滤器兜底防穿透，内存淘汰策略交给 Redis 的 LRU 来保证热点数据优先留在内存里。如果重新做，我可能会明确在配置里指定 allkeys-lru，而不是依赖默认策略，这样行为更可控。

# 第二家 较难
## 1.布隆过滤器在redis扩容的情况下还能用吗，如果要对布隆过滤器扩容怎么办？
### Redis 集群扩容，布隆过滤器还能用吗？
先说结论：能用，但有一些需要注意的地方。
我们项目里用的是 Redisson 提供的布隆过滤器实现。它在 Redis 里的本质是什么？就是一个 key 下面挂着一个大的位数组，外加几个哈希函数。在 Redis 单机模式下完全没问题，但如果换成 Redis Cluster，这个 key 会根据 CRC16 哈希落在一个固定的 slot 上，进而固定在某一个节点上。
当 Redis Cluster 做扩缩容——比如加了新节点、触发 slot 重新分配——这个 key 所在的 slot 可能会被迁移到新节点。Redis Cluster 的 slot 迁移机制本身是能保证数据完整性的，迁移过程中会有短暂的阻塞，但数据不会丢。所以从原理上讲，扩容后布隆过滤器还是能正常用的。
不过这里有一个隐患：布隆过滤器的位数组可能非常大。比如我们项目里用户注册用的那个，预计容量一亿，误判率千分之一，算下来位数组大概需要 1.4GB 左右。这么大的 key 在 slot 迁移时耗时会比较长，迁移期间这个 key 可能短暂不可用。所以在生产环境做 Redis Cluster 扩容时，如果布隆过滤器数据量很大，需要把这个因素考虑进迁移窗口的评估里。

### 布隆过滤器自身容量不够了，怎么扩容？
这个才是真正的难点。传统的布隆过滤器有一个先天限制：位数组长度和哈希函数数量在初始化时就定死了，没法像哈希表那样原地扩容。
为什么？因为布隆过滤器的工作原理是"把每个元素映射到位数组的几个位置，然后把那些位置置为 1"。如果你把位数组变长了，原来某个元素映射到位置 17 的，新数组里该映射到哪？哈希函数变了，结果完全不同，旧数据没法"迁移"——位数组里只有 0 和 1，你不知道哪些 1 是哪个元素贡献的，没法重建映射关系。
我们项目里是怎么处理的呢？坦白说，当前项目没有实现动态扩容，初始化时预估了一个比较大的容量——用户布隆过滤器一亿、分组布隆过滤器两亿，对于一个学习项目来说足够用了。但这里面有个容易踩的坑：Redisson 的 tryInit 方法有个特性，如果 Redis 里这个 key 已经存在了，它就什么都不做——不会覆盖、不会更新参数。这意味着即使你改了代码里的容量参数重启应用，旧的布隆过滤器也不会变大。
如果真要扩容，我觉得比较务实的方案有这么几种：
方案一：原地重建。 直接把旧的删了，建一个新的更大容量的，然后从数据库全量扫描一遍，把所有已有的用户名重新加载进去。优点是简单粗暴，缺点是重建期间布隆过滤器是空的，穿透防护有窗口期。可以挑业务低峰期做，或者临时提高数据库的扛压能力顶着。
方案二：新旧并行，平滑过渡。 不删旧的，新建一个容量更大的布隆过滤器。重建期间，写入操作同时写新旧两个，查询操作先查新的、查不到再查旧的。等新过滤器重建完成后，把旧的摘掉。这个方案没有防护窗口期，但实现复杂度高一些，而且过渡期间 Redis 里同时存在两个大位数组，内存压力翻倍。
方案三：分层布隆过滤器。 这是学术界提出的一种变体——不是把位数组变大，而是当现有布隆过滤器"满了"（误判率开始超过阈值），就**新建一个额外的布隆过滤器**，**两个一起用**。查询时依次查每一层，只要有一层返回"可能存在"就算命中。这个方案的缺点是随着层数增加，误判率会累积上升，而且每次查询要访问多个布隆过滤器，性能会下降。
总的来说，布隆过滤器的扩容本质上是一个"容量预估"的问题——你最好在初始化时就给未来留足余量。Redis 层面做内存估算也不难：容量 × 误判率对应的位数组大小，就是内存占用量。一亿容量千分之一误判率也就一个多 GB，对于 Redis 来说是可以接受的。我们项目中选一亿和两亿这两个值，也是基于"留足余量、一次到位"的考虑。

## 2. 消息队列发送是同步的吗，有没有重发机制，怎么设计的，如果要求短链接快速重定向为什么还要同步，当时为什么没考虑到
### 关于同步还是异步
我们当前用的是 同步发送——syncSend，还设了 2 秒的超时。这个调用链路是这样的：用户点击短链接 → restoreUrl 方法 → 构建统计数据 → 调用 shortLinkStatsSaveProducer.send() → 同步等待 RocketMQ 返回发送结果 → 然后才执行 sendRedirect 做重定向。
这意味着什么？重定向的响应时间里，包含了消息发送的耗时。正常情况下 RocketMQ 同步发送也就几毫秒到几十毫秒，影响不大。但如果 broker 负载高、网络抖动，最坏情况要等满 2 秒超时。这对用户体验来说是不可接受的——用户点一个短链接等了两秒才跳转，跟直接打开原链接有什么区别？
你问得对，当时为什么没考虑到？
说实话，这块我在做的时候确实没深入想。导师给的设计方案里就是用同步发送，我当时理解的重点是"统计数据不能丢"，同步发送能拿到发送结果，确认消息真的进了 broker，感觉更可靠。但现在回过头看，统计数据的可靠性不应该以牺牲主链路响应时间为代价。
正确的做法应该是用异步发送——调用 asyncSend，传一个回调，消息发送成功就完事，发送失败在回调里记日志或者落盘补偿，完全不阻塞重定向的返回。用户点击链接，我们拿到原始 URL 后立即重定向，统计消息异步发出去，两个动作解耦。哪怕消息发失败了，一条统计数据的丢失对业务来说是可以接受的，比起让用户多等几百毫秒甚至两秒，孰轻孰重一目了然。
如果再给我一次机会重做，我会这样设计：主流程只做缓存查询和重定向，统计数据的组装完成后直接扔进一个内存队列或者用 asyncSend 异步发送，重定向的响应和消息发送完全并行，不互相等待。
 
### 关于重发机制
坦率说，当前代码里没有实现显式的重发机制。syncSend 抛异常后，catch 块里只打了日志，没有重试逻辑。RocketMQ 客户端自己有一个默认的同步发送重试（默认 2 次），但那是框架层面的，不是我们主动设计的。
如果要补上这块，我现在的思路是这样：
第一层，生产者端重试。异步发送失败后，在回调里做有限次数的重试（比如 3 次），指数退避。如果还是失败，把消息落本地文件或者写进一张"待补偿"的数据库表，起一个定时任务定期扫表重新投递。
第二层，消费者端的幂等性兜底——就是我们之前聊的那套 Redis 幂等机制，保证就算消息最终重复投递了，也不会导致统计数据翻倍。
但这里有个取舍需要说清楚：统计类消息到底值不值得做这么重的一套重试+补偿？我们的场景是访问统计，丢一两条 PV 数据对整体趋势分析几乎没有影响。所以如果是我来决策，我会倾向于：异步发送 + 失败记日志 + 监控告警，而不会去实现复杂的补偿链路。引入补偿机制增加的复杂度和维护成本，远大于偶尔丢几条统计数据的损失。
 
所以总结一下：同步发送是当时的考虑不周，异步发送才是正确的选择，重试机制在当前场景下性价比不高，幂等兜底比分毫不差的投递保证更重要。 这也是做这个项目让我印象比较深的一个教训——不能为了"数据不丢"而牺牲"用户体验"。

## 3.如果有很多人生成短链接，怎么加快生成速度
### 先看现在的生成链路有哪些耗时环节
当前 createShortLink 一次请求要做这些事情：
域名白名单校验（毫秒级，可以忽略）
生成后缀——用 MurmurHash32 哈希原 URL，转 base62 编码出 6 位短码，然后查布隆过滤器判断是否重复，如果冲突就加随机盐重新哈希，最多重试 10 次
两次数据库 INSERT——t_link 和 t_link_goto，在一个事务里同步提交
Redis 缓存写入——把短链接和原始 URL 的映射写进 Redis
布隆过滤器更新——把新短链接加入布隆过滤器
还有一个隐藏的瓶颈：Sentinel 限流——创建短链接的接口被限到了 QPS=1，也就是每秒只允许一次创建请求。这应该是项目里故意加的防护，但在"大量用户同时生成"的场景下，这就是第一道天花板。
 
### 那怎么逐个击破瓶颈？
第一，提限流阈值。 QPS=1 显然太低了，如果是为了防刷，可以提到一个合理的值比如 100 或 500，然后配合用户维度的流量风控（项目里有 UserFlowRiskControlConfiguration，按时间窗口限制每个用户的可访问次数），让正常用户不受影响，恶意用户单独限制。
第二，解决哈希冲突带来的重试开销。 这是链路中最不稳定的环节。现在每次生成后缀都要做 MurmurHash32 → base62 → 布隆过滤器查重。MurmurHash32 的值域只有 43 亿，随着短链接数量增长，冲突概率会上升，冲突一次就要重新哈希、重新查布隆过滤器，每次都是网络往返。
更根本的解决方案是**预生成短码池**。思路是这样的：用一个分布式 ID 生成器（比如 Snowflake 雪花算法），**提前批量生成一批唯一 ID**，转成 base62 编码后放进 Redis 的一个 List 里。用户要创建短链接时，直接从这个 List 里 LPOP 一个出来用，就完全不存在哈希冲突问题了。生成过程变成纯内存操作，省掉了循环重试的开销。
预生成的短码用完了怎么办？起一个后台线程或者定时任务，监控 List 长度，低于阈值就触发补充。补充的时候可以用数据库自增 ID 或者雪花算法批量生产一批 6 位短码，提前校验是否有重复（其实用雪花算法基本不会重复），校验完塞进 List。
第三，数据库写入优化。 当前是同步 INSERT 两张表，事务提交后才返回。优化方向有两个：
一个是批量写入——项目里有 batchCreateShortLink 接口，但它内部是循环调用 createShortLink，相当于循环单条插入，没有真正用上批量。可以改成收集一批待创建的短链接，一次性 batch insert，减少和数据库的交互次数。
另一个更激进的做法是异步写入——短码确定可用后立刻返回给用户，数据库写入交给消息队列异步消费。代价是一致性风险：如果异步写入失败了，用户拿到短链接但实际不可用。所以这个方案更适合"允许短暂不一致"的场景，需要配合补偿机制和监控告警。
第四，分片化创建锁。 当前代码里有一个全局的创建锁 SHORT_LINK_CREATE_LOCK_KEY，所有创建请求抢同一把锁。如果能按分组或者分片键拆成多把锁，并发度就上去了。
第五，布隆过滤器查询优化。 其实布隆过滤器本身很快，瓶颈不在它。但要注意：如果用了预生成短码池，连布隆过滤器这一步都可以省掉——短码是预先生成并校验过的，生成时不需要再查重。布隆过滤器只保留给已经创建的短链接做缓存穿透防护，不再参与生成流程。
 
### 总结一下
最快的优化路径是：提限流 → 预生成短码池替代实时哈希 → 批量写入替代单条插入。这三步下来，创建短链接的吞吐量可以从 QPS=1 提到几千甚至上万。当然，这些优化都是"量变引起质变"后才需要的，项目当前规模下大部分开销其实都在毫秒级，真正的瓶颈是 Sentinel 主动限在了 QPS=1。

## 4. 那你觉得考率支持vip用户，分库分表，redis扩容，用更快的哈希函数等方法怎么样
### VIP 用户支持
这个我挺认同的，本质上是一个资源隔离和差异化服务的问题。
从业务上讲，VIP 用户确实应该有更好的体验。对应到我们的系统，可以做几件事：限流层面，**VIP 用户配更高的 QPS 阈值或者干脆不限流**，普通用户保持现有限制；短码生成层面，VIP 用户可以用更短的短码（比如 4 位），普通用户 6 位，短码越短越稀缺；还有回收站保留时长、分组数量上限、统计数据回溯时长等等，都可以做差异化。
不过从技术实现上看，这需要在网关层或 Controller 层做一层用户身份识别和路由——当前项目里网关已经有 Token 校验，token 验证通过后把 userId 放进请求头往下传，所以拿到用户身份判断是不是 VIP 这个链路是现成的。具体落地的话，可以在用户表里加一个 VIP 等级字段，然后在限流配置、短码生成策略里根据这个字段走不同分支。整体来说思路清晰，实现成本可控，属于"可以做"的范畴。
 
### 分库分表
这个要分开看。我们项目目前其实已经做了一部分——分表，t_link、t_user、t_group 都是用 ShardingSphere 按分片键拆了 16 张表。但有一个关键点：所有 16 张表都还在同一个数据库实例 ds_0 里，实际上是"分表没分库"。
如果要进一步做分库，好处是写吞吐量可以线性扩展——多个数据库实例分摊写入压力，每个实例各管一部分表。但代价也很大：跨库查询基本就废了，JOIN 和事务都要重新考虑。比如用户想看自己所有分组下的短链接统计数据，原来在同一个库里聚合就行，分库之后可能涉及多个库的查询合并。
所以我的判断是：分表在当前项目里已经做到位了，分库属于"量变到质变"才需要的手段。单库写吞吐量撑到瓶颈了才上分库，否则只会徒增复杂度。要看业务体量，如果日活只有几万、短链接总量不过亿，单库完全够用。
 
### Redis 扩容
这个方向上我觉得要分场景讨论。
对于短链接跳转缓存（short-link:goto:{url} 这种 key-value 对），用 Redis Cluster 做水平扩容是很自然的选择——每个 key 天然独立，slot 分配均匀，扩容就是加节点、迁移 slot，几乎零业务改动。
但问题出在布隆过滤器上。布隆过滤器在 Redis 里是一个单一的大 key，位数组可能有几百 MB 甚至上 GB。在 Redis Cluster 里，一个大 key 只能落在一个节点上，没法拆分。你加再多节点，布隆过滤器所在的节点该多大还是多大，而且迁移这个大 key 的成本极高。所以布隆过滤器是 Redis 水平扩容的死角。
解决思路有两个：要么在初始化布隆过滤器时把容量估得足够大，内存给它留足，让它一次到位，不走扩容；要么拆分布隆过滤器——比如按短链接首字符拆成 16 个小布隆过滤器，每个小过滤器独立运作、独立存储，这样就可以分散到不同 Redis 节点上了。但拆分会引入额外的路由逻辑，查询时要先确定去哪个小过滤器。
对于 UV/UIP 统计用的 Set（short-link:stats:uv:{url}），这些是按短链接维度拆分的，天然可以分散到不同节点，扩容没有障碍。
所以我的结论是：Redis Cluster 对缓存和统计数据扩容是可行的，但布隆过滤器是硬骨头，要么一次到位要么拆分，别指望靠加节点来解决。
 
### 用更快的哈希函数
这个说实话，收益可能没有想象中那么大。
我们当前用的是 MurmurHash32，它已经是公认的最快的非加密哈希之一了。换成 xxHash 或者 CityHash，单次哈希的耗时差异在纳秒级，即使每次生成短码要做一次哈希，这部分在整个链路上占比微乎其微。
真正的瓶颈不在哈希函数本身，而在哈希冲突后的重试链路——冲突一次，就要重新加盐、重新哈希、重新查布隆过滤器，每次都是 Redis 网络往返。哈希再快也架不住冲突带来的额外开销。所以与其换一个更快的哈希，不如从根本上消除冲突的可能性——就是我前面说的预生成短码池。用雪花算法生成唯一 ID，直接转 base62，不需要哈希，也不存在冲突，这才是真正消灭瓶颈的做法。
不过有一个方向可以提一下：如果坚持用哈希方案，可以换 64 位哈希替代当前的 32 位。32 位哈希值域只有 43 亿，随着短链接总量逼近这个量级，冲突概率会明显上升；换成 64 位，值域大几个数量级，冲突概率几乎可以忽略不计。这本质上也是在"降低冲突"而不是"加速哈希"。

## 5.用了什么哈希函数，还知道什么其他的哈希函数吗，md5和sha256的特定以及底层原理
我们项目用的是一个叫 MurmurHash 的哈希函数，具体是 32 位版本，来自 Hutool 工具库。选择它的原因挺直接的——MurmurHash 在非加密哈希里属于公认最快的梯队之一，计算开销小，而且分布均匀性好，碰撞率低。对于我们短链接后缀生成这种纯性能敏感、不需要安全性的场景，选它很合适。它不像 MD5、SHA 那样有复杂的安全设计，就是纯粹为了"算得快、散得开"而生的。
### 还知道哪些哈希函数
除了 MurmurHash，我了解过的还有几类：
非加密类还有 xxHash，号称比 MurmurHash 更快，尤其在处理大块数据时优势明显；CityHash 和 FarmHash 是 Google 出的，针对 x86 架构做了深度优化，短字符串场景表现很好；还有 Java 标准库自带的 hashCode，但分布性比较差，不适合生产场景。
加密类的就多了，MD5、SHA-1、SHA-256、SHA-3，还有国内的 SM3。
MD5 和 SHA-256 的特点与底层原理
这两个都属于加密哈希函数，跟 MurmurHash 有本质区别——加密哈希设计目标是"单向不可逆"和"抗碰撞"，而不只是"散得均匀算得快"。
MD5 输出固定 128 位（32 个十六进制字符）。它的原理用大白话说就是：把输入数据先补齐到 512 位的整数倍，然后分块处理，每 512 位一块。内部维护 4 个 32 位寄存器（A、B、C、D），初始值是固定的魔数。每一轮处理会对寄存器做一系列位运算——与或非、循环移位、加上当前数据块和预设的常数表——然后把结果迭代回寄存器，进入下一块。所有块处理完后，4 个寄存器的最终值拼起来就是 128 位的哈希值。
MD5 的核心特点是快，但安全性已经彻底崩了——早在 2004 年王小云教授团队就找到了构造碰撞的方法，现在可以人为制造两个不同文件产生完全相同的 MD5。所以 MD5 现在基本只用于校验数据完整性（比如下载文件后比对 MD5），绝对不能用于密码存储或数字签名。
SHA-256 输出 256 位，属于 SHA-2 家族。流程跟 MD5 类似但更复杂：同样是分 512 位一块处理，但内部维护的是 8 个 32 位寄存器（而不是 MD5 的 4 个），轮数是 64 轮（MD5 只有 4 轮，每轮 16 步）。每轮操作不仅包含 MD5 那种位运算，还引入了更复杂的消息扩展——把当前数据块的 16 个 32 位字通过位移和异或扩展成 64 个字，保证输入的微小变化能在多轮迭代中被充分扩散。这种"雪崩效应"设计使得输入哪怕只差一个比特，输出都会天差地别。
SHA-256 目前没有被实际攻破，安全性远高于 MD5。代价是计算量大概是 MD5 的好几倍，输出长度也多一倍。日常开发里，密码哈希一般推荐用专用的密钥派生函数如 bcrypt、Argon2，SHA-256 更多用于证书校验、区块链（比特币的 PoW 就是反复算 SHA-256）、文件签名等场景。

## 6. 短链接的哈希函数在对称加密和非对称加密怎么选择，还是都可以
### 哈希和加密的本质区别
哈希是单向的，你把数据扔进去出来一个固定长度的指纹，但没法从这个指纹反推出原始数据。加密是双向的，你用密钥加密，用对应的密钥（对称加密同一个密钥，非对称加密另一个密钥）可以解密还原。
短链接的诉求是什么？把长 URL 映射成一个短码，用户点短码时能找回原始 URL。所以核心要做的不是"加密长 URL"，而是建立映射关系——短码只是一个索引，真正的 URL 存在数据库或缓存里。
我们用 MurmurHash 把 URL 哈希成一个 6 位短码，然后把"短码 → 原始 URL"这条映射存到数据库里。用户点击短链接时，拿短码去查映射表，找到原始 URL 做重定向。哈希在这里的作用就是快速生成一个唯一标识，而不是"把 URL 藏起来"。
 
### 如果硬要用加密会怎样？
假设用对称加密比如 AES 来"生成短码"——把原始 URL 用密钥加密，得到的密文当作短码。第一个问题就是长度：AES 加密后的密文至少 16 字节，用 base62 编码之后至少二十几个字符，比我们现在的 6 位短码长了三四倍，"短链接"就不短了。
那如果换成非对称加密比如 RSA 呢？更惨。RSA 加密输出的密文长度等于密钥长度，2048 位的密钥输出就是 256 字节，转 base62 后几百个字符，根本没法当短链接用。
就算用格式保留加密（format-preserving encryption），它能保证输出长度等于输入长度，但一个几百字符的长 URL 加密后还是几百字符，对短链接完全没有帮助。
而且还有一个更根本的问题：加密需要管理密钥。对称加密的密钥一旦泄露，攻击者可以伪造短链接；非对称加密虽然私钥安全一些，但加密解密性能差几个数量级，高并发场景下完全不可行。
 
### 对称和非对称怎么选？
结论是都不选。不是"选哪个更好"的问题，而是加密这个方向从根上就不适合短链接的场景。短链接不需要对 URL 保密（URL 本来就是公开的），需要的是把很长的东西映射成一个很短的标识。这个需求天然是哈希函数的阵地，不是加密算法的阵地。
哈希函数在这个场景里的优势非常明显：输出长度固定且可控——你选 6 位 base62，就是 6 位，不管原始 URL 是一百个字符还是一万个字符；计算速度极快——MurmurHash 是微秒级的，而 RSA 是毫秒级的；不需要管理密钥——没有密钥泄露的风险。
所以如果面试官问的是"哈希函数在对称加密和非对称加密怎么选"，我觉得更准确的表述应该是：短链接生成用的是哈希函数，不是加密函数，二者解决的问题完全不同。对称加密和非对称加密适合用来保护数据的机密性，不适合用来生成短链接标识。

## 7. 短链接输入到显示页面的流程
整个流程大致分三层：网关层 → 业务层 → 存储层，核心逻辑在 restoreUrl 这个方法里，我按请求到达的顺序来说。
### 第一步：请求到达
用户在浏览器输入短链接比如 http://short.domain/abc123，请求先到 Spring Cloud Gateway。网关层有一个 Token 拦截器，但短链接跳转这个路径本身是在白名单里的（/{short-uri} 这种格式），所以直接放行，不需要登录态校验。
### 第二步：构造完整短链接
请求打到 ShortLinkController，匹配到 /{short-uri} 这个路径，取出 shortUri 也就是 abc123，拼上默认域名，得到完整短链接 short.domain/abc123。
### 第三步：查 Redis 缓存——快速路径
这是整个链路里最重要的优化点。绝大多数短链接访问走的都是这条路——直接拿完整短链接拼一个 Redis key short-link:goto:short.domain/abc123，去 Redis 里查 value。这个 value 就是原始长 URL。如果命中，直接走三步：收集访问统计信息（UV、IP、浏览器、操作系统等）→ 异步发一条消息给 RocketMQ 做后续统计入库 → sendRedirect 重定向到原始 URL。整个过程缓存命中时，Redis 查询是毫秒级的，用户几乎感觉不到延迟。
### 第四步：缓存没命中——多层兜底
缓存没命中不一定是短链接不存在，可能只是缓存过期了。这时候不能直接打数据库，因为可能有人恶意构造大量不存在的短链接来做缓存穿透。
第一层兜底是布隆过滤器。把完整短链接扔进布隆过滤器判断，如果返回"不存在"，那就直接跳到一个 notfound 页面，数据库完全不碰。布隆过滤器可能会有误判（说不存在就一定不存在，说存在却可能不存在），所以这一层是"宁可错杀一百，不可放过一个穿透"。
如果布隆过滤器说"可能存在"，接着查第二层兜底——空值缓存。Redis key 是 short-link:is-null:goto_short.domain/abc123，如果命中说明之前已经确认过这条短链接不存在，直接跳 notfound，也不用打数据库。空值缓存设了 30 分钟的过期时间。
### 第五步：加分布式锁回源数据库
前面几层都没命中，说明可能是缓存过期了，需要去数据库捞。但同一时刻可能有大量并发请求都走到这一步，如果大家都去查数据库就成"缓存击穿"了。所以这里用 Redisson 加了一把分布式锁——short-link:lock:goto:short.domain/abc123，只有拿到锁的请求去查数据库，其他请求等着。
拿到锁后，还会再查一次 Redis 缓存和空值缓存——这是双重检查，因为有可能在排队等锁的时候，前面拿到锁的线程已经把缓存补上了，没必要再查库。
### 第六步：查数据库
缓存确实没有，开始查库。先查 t_link_goto 表，按完整短链接查出对应的分组标识 gid。如果查不到，说明这个短链接确实不存在，写一条空值缓存（30 分钟 TTL），跳 notfound 页面。
如果 t_link_goto 查到了，再拿 gid 去 t_link 表查短链接详情。这里要检查三个条件：是否已删除、是否已禁用、是否已过期。任意一个不满足，同样写空值缓存、跳 notfound。
### 第七步：重建缓存并重定向
数据库确认短链接有效，拿到原始 URL 后，先重建 Redis 缓存——把原始 URL 写进 short-link:goto: 这个 key 里，TTL 按链接有效期计算（有有效期就按剩余时间，永久的默认 30 天）。这样后续同样的请求就能走缓存快速路径了。然后同样的流程：收集统计信息 → 发 RocketMQ → sendRedirect 重定向。
### 第八步：浏览器拿到重定向响应
服务端返回的是一个 302 重定向响应，Location 头指向原始 URL。浏览器收到后自动跳转，原始页面的加载就和我们的短链接系统无关了。
统计信息顺便说一下
在重定向之前，buildLinkStatsRecordAndSetUser 这个方法会收集一次访问的所有维度数据：UV 通过 Cookie 判断是否新用户（30 天有效期的 Cookie），UIP 通过 Redis Set 判断是否新 IP，User-Agent 解析出操作系统、浏览器、设备类型，IP 判断网络类型（WiFi 还是移动网络），还会调高德地图 API 根据 IP 反查地理位置（省份、城市）。这些数据打包成一条消息异步丢给 RocketMQ，消费者后续做统计入库。
 
用一句话概括整个链路：Redis 扛流量 → 布隆过滤器挡穿透 → 空值缓存防击穿 → 分布式锁保回源 → 数据库兜底查 → 异步统计不阻塞。每一层各司其职，层层递进，核心目标是让 99% 以上的请求在 Redis 这层就完成，根本碰不到数据库。

# 第三家
## 1.介绍下短链接项目
这是一个 SaaS 短链接系统，简单说就是把一个很长的 URL 转换成类似 short.domain/abc123 这样的短链接。用户点这个短链接，系统自动跳回原始的长 URL。听起来功能很简单，但背后要解决的东西不少——比如海量短链接怎么存储、高并发跳转怎么扛、访问数据怎么统计分析、多个租户之间怎么隔离。
核心功能有四块：长链接转短码、短链接重定向跳转、访问统计与分析（PV/UV/UIP、地区分布、浏览器、操作系统等）、以及多租户数据隔离（每个用户只能管自己的短链接）。应用场景主要是营销短信、活动推广、用户行为追踪这些——长链接在短信里又占字数又难看，短链接就解决了这个问题。

## 3.布隆过滤器误判怎么处理（这里说了创建短链接和访问短链接误判两种情况）
### 创建短链接时的误判
创建短链接的判重链路是：哈希出短码 → 布隆过滤器检查 → 过滤器说"可能存在"就视为冲突 → 加随机盐重新哈希 → 重试最多 10 次。
这里的处理方式其实很直接——把"可能存在"当作"一定存在"来对待，宁可多算一次哈希，也不能冒险用一个可能冲突的短码去插入数据库。因为如果真冲突了，**数据库抛唯一键异常，事务回滚**，代价比多算一次哈希大多了。
重试 10 次还冲突就抛异常，让用户稍后再试。实际上这种情况概率极低——6 位 base62 有 568 亿个可能值，在短链接总量远小于这个数量级时，连续 10 次"恰好命中误判 + 恰好命中真实存在的短码"几乎不可能。所以这个看似粗暴的策略在实际中是够用的。
另外还有一个细节：如果插入数据库时真的出现了唯一键冲突（说明布隆过滤器漏判了，把实际存在的说成了不存在），**catch 住 DuplicateKeyException** 后会把这条短链接补加进布隆过滤器，然后抛异常。这样下次就不会再漏判同一个短链接了。
 
### 访问短链接时的误判
这个场景的误判影响和创建不一样，处理链也更复杂，是一层一层兜底的。
访问短链接的查询链路是这样的：
第一层：Redis 缓存。 先查正常的跳转缓存 short-link:goto:{url}。如果命中，直接重定向，后面的都不走了。大多数正常访问在这一层就返回了。
第二层：布隆过滤器。 缓存没命中，问布隆过滤器。如果返回"不存在"，说明短链接肯定没创建过，直接跳 notfound 页面，数据库碰都不碰。
但如果布隆过滤器误判——短链接根本没创建过，过滤器却说"可能存在"——请求就不会在这一层被拦截，而是会进入第三层。
第三层：**空值缓存**。 检查 short-link:is-null:goto_{url}。这个 key 的作用就是记录"之前已经确认过这条短链接不存在"。如果命中了，直接跳 notfound。而且这个缓存 TTL 是 30 分钟，意味着同一个不存在的短链接在 30 分钟内怎么请求都不会穿过这一层。
第四层：加分布式锁查数据库。 前面三层都没拦住，说明要么是一个真正存在但缓存过期的短链接（需要回源重建缓存），要么是一个布隆过滤器误判 + 空值缓存也没命中的不存在短链接。这时候加分布式锁，去 t_link_goto 表和 t_link 表里查。
查出来如果确实不存在，立刻写空值缓存，30 分钟内同样的请求不会再穿透。查出来如果存在，立刻重建跳转缓存，后续请求直接走第一层。
 
### 两层误判放一起看
创建短链接时误判的处理是"保守策略"——误判了就当冲突，多算几次哈希，代价可控。
访问短链接时误判的处理是"层层兜底"——布隆过滤器不是唯一的防线，后面还有空值缓存、数据库。误判的代价就是一次数据库查询，但因为前面有空值缓存挡着（30 分钟 TTL），同一个不存在的短链接最多穿透一次。而且布隆过滤器千分之一误判率本身已经很低了，在实际流量下，真正触达数据库的误判请求量微乎其微。
所以这个设计本质上是：布隆过滤器承担了 99.9% 的拦截工作，省掉了海量数据库查询；那 0.1% 的漏网之鱼交给空值缓存和数据库兜底，每次漏网的成本只是一次有锁保护的数据库查询，完全在可接受范围内。 这比"不用布隆过滤器、每次创建都查数据库"强了几个数量级。
