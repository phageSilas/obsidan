## 1.短链接怎么生成的？
整体思路是：拿到原始长链接 → 哈希计算 → Base62 编码 → 得到一个短码。
具体来说，我们用的哈希算法是 MurmurHash。选它而不是 MD5 或 SHA，主要是因为它是一个非加密型哈希，速度快、碰撞率低，更适合短链接这种对性能敏感的场景。这个算法会把输入的字符串映射成一个 32 位的整数。
然后我们把这个整数转成 Base62 编码——也就是用 0-9、A-Z、a-z 这 62 个字符来表示。这样每个字符能表示 62 种状态，比纯数字或纯十六进制要紧凑得多，6 位就能表示几百亿的组合，足够用了。
但这里有个问题：如果两个不同用户同时对同一个长链接创建短链接，生成的后缀可能就是一样的。所以我们做了一步处理——生成哈希之前，会在原始 URL 后面拼上一个随机 UUID，这样输入就不一样了，极大降低了碰撞概率。
另外，生成的短链接还会和域名拼接成完整的短 URL，缓存到 Redis 里，这样后续访问时直接走缓存，不用每次都查库。
## 2.怎么确保短链接的唯一？
第一层：布隆过滤器预判。 在往数据库插入之前，先用布隆过滤器检查这个短链接是否已经存在。布隆过滤器是一种空间效率极高的概率型数据结构，它可能误判（说存在但实际不存在），但不会漏判（说不存在就真的不存在）。这里我们初始化时设了 1 亿的预期容量和千分之一的误判率。如果布隆过滤器说"没重复"，我们就可以放心去插入。
第二层：数据库唯一索引兜底。 短链接表里有一个联合唯一索引，建在"完整短 URL + 删除时间戳"上。即使布隆过滤器误判了、让一个重复的短链接漏过去，数据库也会直接抛 DuplicateKeyException，保证不会写入重复数据。这时候我们会把这个短链接加进布隆过滤器，然后提示用户"生成重复，请重试"。
第三层：还有一条额外的路径——分布式锁方案。 这是另一种实现方式，不用布隆过滤器，而是用 Redisson 分布式锁串行化创建过程，锁住之后直接查数据库判断是否重复。这种方案更保险但性能不如布隆过滤器，所以我们把它作为一个备用方案保留，默认还是走布隆过滤器的路径。

## 布隆过滤器的原理？有什么缺点？短链接存满了怎么扩容？占用多少空间？
### 原理
布隆过滤器本质上就是一个很长的二进制位数组 + 多个哈希函数。
具体流程是：当我们要标记"某个短链接已存在"的时候，会把这个短链接用多个不同的哈希函数各算一遍，得到几个位置，然后把位数组里这几个位置都标成 1。查询的时候也一样——用同样的哈希函数算出那几个位置，如果所有位置都是 1，就认为"可能存在"；如果有任何一个位置是 0，就说明"一定不存在"。
这里的关键在于"可能存在"这四个字。它不会漏判，但会误判——因为不同元素经过哈希后可能映射到相同的位置，A 元素把某些位标成了 1，B 元素来查的时候发现这些位也是 1，就被误判为存在了。
我们项目里给它初始化的时候，设了两个参数：预期元素数量 1 亿，误判率千分之一。在这两个参数下，Redisson 底层会自动算出需要多大的位数组和多少个哈希函数。
### 缺点
第一，不支持删除。 这是最经典的问题了。布隆过滤器不能随便把某一位改成 0，因为那一位可能同时被多个元素共用，你改了一个，别的元素就查不到了。我们在项目里也确实没做删除——短链接就算被删了，布隆过滤器的记录也还在，不过这个误判只是多查一次数据库，影响不大。
第二，有误判率。 千分之一的意思是一千次查询里大约有一次会误判。我们项目里用数据库唯一索引兜底，所以即使误判了也不会导致数据重复，只是多了一次无效的数据库写入。
第三，不能枚举。 你没法知道布隆过滤器里到底存了哪些元素，它只能回答"是不是可能存在"。
还有一个实际遇到的坑：Redisson 的 tryInit 方法，如果 Redis 里已经存在这个 key，它是 no-op 的，什么都不会做，也不会覆盖。 这意味着如果你想重新初始化或者扩容，必须先手动把 Redis 里的 key 删掉，不然调 tryInit 是无效的。

### 短链接存满了怎么扩容？
坦白说，我们项目里没有做自动扩容机制。布隆过滤器创建的时候就固定了容量，位数组大小和哈希函数数量都是初始化时算好的。
如果真的需要扩容，思路一般有几种：
最直接的是：删除旧 key，重新建一个更大的，然后全量扫描数据库重建数据。启动时或定时任务把数据库里所有存活的短链接重新加入新的布隆过滤器。但这个过程对大表来说会比较耗时。
更优雅的做法是多级布隆过滤器：旧的满了就新建一个，查询的时候先查新过滤器再查旧的。不过这样会线性增加查询开销。
还有一种思路是用可扩展布隆过滤器（Scalable Bloom Filter），它内部维护一个布隆过滤器列表，满了就追加新的，查询时遍历所有。但 Redisson 没有原生支持，需要自己实现。
如果要我现在做改进的话，我可能会在监控层面加一个告警——当布隆过滤器的元素数量接近初始化容量时，提前通知人工介入迁移，而不是等到满了才发现。

位数组大小大约是 14.4 亿位，换算下来就是 1.44 × 10⁹ / 8 ≈ 1.8 亿字节，约 172 MB。哈希函数需要大约 10 个。
也就是说，用 172 MB 的 Redis 内存，就能索引 1 亿个短链接。对比一下，如果全存 Redis 的字符串 key，1 亿个每个就算只占几十字节，也是好几个 GB 起步。所以布隆过滤器的空间优势非常明显——内存占用量跟存的元素数量成正比，跟元素本身的大小无关，一个几字节的短码和一个几千字节的长 URL，在布隆过滤器里占用的位是一样的。

## 3.短链接监控消息队列的消息幂等？消息队列顺序性？
### 消息幂等
我们的做法是借助 Redis 来实现消费幂等。整体思路分三步：
第一，消息到达消费者时，先拿消息的唯一标识去 Redis 里做检查——用的是 Redis 的 SETNX 命令，也就是"不存在才写入"的原子操作。如果写入成功，说明这条消息是第一次来，可以继续处理；如果写入失败，说明已经有人在处理了，就不重复消费。
第二，处理过程中还有一层状态标记。我们用 Redis 里的值来区分两种状态：值是 "0" 表示正在处理中，值是 "1" 表示已完成。这样如果消息重试到达时发现已经标记为 "1"，就直接跳过，避免重复入库。
第三，异常处理也很关键。如果消息处理到一半抛出异常，我们会主动删除这个幂等标识，让 RocketMQ 的重试机制能够重新投递这条消息；如果处理成功，就标记为 "1"。这样既保证了"至少处理一次"，又通过幂等判断保证了"实际生效一次"。
另外有个小细节，这套幂等标识设置了 2 分钟的过期时间。为什么是 2 分钟呢？因为正常的统计写入操作基本在秒级完成，2 分钟已经是很宽裕的兜底时间了——如果 2 分钟还没处理完，说明可能出了严重问题，这个标识自然过期也没关系，RocketMQ 可以重新投递。

### 队列顺序性
这个要坦诚说，我们项目里没有对消息顺序性做严格的保证。
原因在于我们的场景——短链接访问统计，它的数据特点是什么？PV、UV、地区、浏览器、操作系统这些维度的统计，本质上是在做累加。比如今天这条短链接来了 10 次访问，不管消息到达的顺序是 1→2→3 还是 3→2→1，最终累加出来的结果是一样的。所以我们追求的是"最终一致性"，而不是严格的顺序性。
如果非要保证顺序性，RocketMQ 本身是支持顺序消息的——可以把同一个短链接的消息都发到同一个 MessageQueue 里，这样消费者按单线程消费就能保证顺序。但代价是吞吐量会下降，而且消费失败后的重试机制也会打断顺序。对于我们这种统计场景来说，用顺序消息的代价大于收益，就没必要了。
所以总结一下：我们的设计思路是用幂等保证数据不重复、不丢失，用最终一致性接受短时间的统计延迟，而不是强依赖消息顺序。
## 4.短链接表的分表怎么做的？分表下怎么扩容？
### 分表
我们这个项目用的是 ShardingSphere 5.x 来做分表，核心策略就是基于分片键的取模哈希。
以短链接主表 为例：我们选的分片键是分组标识。为什么选分组标识 而不是短链接本身？因为在实际业务中，用户查询和管理短链接都是按"分组"维度来操作的——比如用户打开某个分组，看到的是这个分组下所有的短链接。用分组标识做分片键，意味着同一个分组的所有短链接会落在同一张物理表里，这样按分组查询时只需访问一张表，避免了跨表查询的性能问题。
具体配置上，ShardingSphere 用的是 HASH_MOD 算法，分片数量是 16，也就是分组标识的哈希值对 16 取模，结果 0 就落到 t_link_0，结果 1 落到 t_link_1，以此类推，总共 16 张表。

### 扩容
这个必须坦诚说，用 HASH_MOD 取模分片有一个天然的缺陷——扩容很麻烦。
因为一旦分片数变了，比如从 16 扩到 32，原来的 hash("abc") % 16 = 5 这条数据，在新算法下可能变成 hash("abc") % 32 = 21，路由完全变了。这意味着扩容时需要进行全量数据迁移，把所有历史数据按新规则重新分配到新表里，这个过程涉及数据双写、一致性校验、灰度切换等，成本非常高。
但我们当时为什么还是选了 HASH_MOD 呢？有两个考虑：
第一，这是一个面向学习的项目，16 张表对于演示分表机制已经足够了，不需要在项目里演示完整的动态扩容流程。
第二，在生产实践中，一个常用且务实的做法是翻倍扩容。比如从 16 扩到 32，算法虽然变了，但数据迁移有规律可循——原来 t_link_0 的数据只会流向新的 t_link_0 和 t_link_16，因为 n % 16 和 n % 32 的关系是有确定性的：如果 n % 16 = 0，那么 n % 32 只能是 0 或 16。这样我们可以"一拆二"地迁移，每张旧表的数据只散列到两张新表中，迁移范围是可控的。
如果让我重新设计，我可能会考虑两种改进方向：一是在分片键里引入时间维度，比如按月份分表，这样新月份自动落到新表，天然免迁移；二是用一致性哈希，避免取模算法在节点变化时的大面积重分布。不过这两个方案也各有代价——时间分片会导致冷热数据不均，一致性哈希在 ShardingSphere 里需要自定义算法，复杂度会高一些。
所以整体思路就是：用取模哈希实现快速路由，用分组标识保障查询亲和性，扩容靠翻倍策略做可控迁移——在当前项目规模下，这是一个合理的折中。

## 5.redis中短链接的过期时间如何设置？一段时间内redis缓存的短链接太多导致redis内存满了怎么办？淘汰哪些短链接？内存淘汰和过期删除的策略？

### 过期时间
我们项目里对缓存的过期时间是分两种情况处理的，核心逻辑就在创建短链接时。
第一种，如果用户创建短链接时设置了有效期——比如这条链接只在 7 天内有效——那我们缓存的 TTL 就是从现在到有效期结束的剩余毫秒数。也就是说，链接本身过期了，缓存也跟着自动过期，不会残留无效数据。
第二种，如果是永久有效的短链接，我们给了一个默认的缓存过期时间，大概是 30 天。为什么不设置成"永不过期"呢？因为 Redis 内存是有限资源，永久有效的话，冷数据会一直占着内存不放。
另外项目里还有一个"空值缓存"——当用户访问一个不存在的短链接时，我们会往 Redis 里写一个标记，过期时间设成 30 分钟。目的是防止有人恶意构造大量不存在的短链接来穿透缓存打到数据库上。

### 内存满了怎么办
坦诚说，我们项目里目前没有做专门的缓存淘汰策略配置，更多是依赖 Redis 自身的机制。但这个问题确实值得讨论，我分几个层面来说。
首先，我们项目里 Redis 存的短链接缓存，每条数据是什么体量？就是一个 key 是完整短链接、value 是原始 URL，外加一个 TTL。一条记录大概也就几百字节，假设一条 500 字节，一百万条也才 500MB 左右。对于单机 Redis 来说，内存压力并没有想象中那么大。真正占内存的其实是那些没有 TTL 的、或者 TTL 很长的 key 持续堆积。
那如果确实内存满了，Redis 会怎么做？这就涉及两个概念：过期删除和内存淘汰，它们不是一回事。
过期删除是 Redis 对已经设置了 TTL 的 key 的清理机制，有两种方式配合使用：一种是惰性删除，就是每次访问一个 key 时顺带检查是否过期，过期了就删；另一种是定期删除，Redis 每隔一段时间随机抽一批 key 检查，把过期的清理掉。这样既不会因为轮询所有 key 而阻塞主线程，也不会让过期 key 长期赖着不走。
内存淘汰是当 Redis 内存使用达到 maxmemory 上限时触发的策略。Redis 提供了好几种淘汰策略，我觉得跟我们场景相关的主要是两种：一个是 volatile-lru，只从设置了 TTL 的 key 里淘汰最近最少使用的；另一个是 allkeys-lru，从所有 key 里淘汰最近最少使用的。

### 淘汰哪些短链接
如果要我来选淘汰策略，我会倾向于 allkeys-lru。原因很简单——短链接的访问有明显的热点效应。一条营销活动链接可能在活动期间被疯狂点击，但活动一结束就很少有人访问了。LRU 算法天然会把那些"很久没人点"的冷门链接缓存淘汰掉，而保留高频访问的热门链接在内存里。
就算某个冷门链接的缓存被淘汰了也没关系——下次有人点击时，会触发缓存回源，从数据库里查出来再写回 Redis，代价就是一次缓存穿透的开销，但我们前面有布隆过滤器挡着，不会真的每次都打到数据库。
如果不用 LRU 而用 TTL 优先淘汰（volatile-ttl），可能会误伤一些 TTL 设置得比较短但实际还很热的链接，反而不如 LRU 贴合业务。当然，TTL 短本身说明这条链接有效期短，淘汰了影响也不大，所以两种策略在这个场景下都能接受。
总结一下：我们项目的设计思路是靠 TTL 做第一层自然淘汰，靠布隆过滤器兜底防穿透，内存淘汰策略交给 Redis 的 LRU 来保证热点数据优先留在内存里。如果重新做，我可能会明确在配置里指定 allkeys-lru，而不是依赖默认策略，这样行为更可控。
