之前已经把服务发现和网关路由拆开讲了，现在把 Nacos 从头到尾、从配置到注解全部串起来。

## 总结:
在启动类上写注解@@EnableDiscoveryClient,那么启动时就会根据每个模块的的配置文件,自动把相应服务加入nacos服务发现中心

## 一、Nacos 是什么

Nacos 在 Spring Cloud 生态里主要干两件事：

- **服务注册与发现**（本项目用到）——每个微服务启动时把自己报到 Nacos，调用方从 Nacos 拉取目标服务的 IP:Port 列表
- **配置中心**（本项目没用到）——把配置文件托管到 Nacos，支持动态刷新

本项目只用到了**服务注册与发现**这一半能力。

`D:\IDEA-java\mading_shortLink\nacos-3.2.0\conf\application.properties`

关键配置：

```
nacos.server.main.port=8848                          # Nacos 服务端口
```

这是一个**单机模式**的 Nacos，数据存在内嵌 Derby 里，不依赖外部 MySQL。启动后访问 `http://127.0.0.1:8848/nacos` 可以看到管理控制台。

## 三、客户端配置（每个微服务都要配）

四个服务模块的 `application.yaml` 中，统一配了这一段：

```
spring:
  application:
    name: short-link-admin       # 在 Nacos 中的服务名（每个模块不同）
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848   # Nacos Server 地址
```

四个模块的服务名：

|模块|`spring.application.name`|端口|
|---|---|---|
|gateway|`short-link-gateway`|8000|
|project|`short-link-project`|8001|
|admin|`short-link-admin`|8002|
|aggregation|`short-link-aggregation`|8003|

**这就是你问的"用到了什么配置"**——服务发现端就这三行：服务名 + Nacos 地址，Spring Cloud Alibaba 自动帮你完成注册。

## 四、核心注解及各自作用

### 4.1 `@EnableDiscoveryClient` —— 开启服务注册

三个业务服务启动类上都打了这个注解：

`admin/ShortLinkAdminApplication.java:31`

``` java
@SpringBootApplication
@EnableDiscoveryClient              // ← 启动时自动向 Nacos 注册
@EnableFeignClients("com.nageoffer.shortlink.admin.remote")
@MapperScan("com.nageoffer.shortlink.admin.dao.mapper")
public class ShortLinkAdminApplication { ... }
```

`project/ShortLinkApplication.java:30`

``` java
@SpringBootApplication
@EnableDiscoveryClient
@MapperScan("com.nageoffer.shortlink.project.dao.mapper")
public class ShortLinkApplication { ... }
```

`aggregation/AggregationServiceApplication.java:29`

``` java
@EnableDiscoveryClient
@SpringBootApplication(scanBasePackages = {
    "com.nageoffer.shortlink.admin",    // 把 admin 代码也扫进来
    "com.nageoffer.shortlink.project",  // 把 project 代码也扫进来
    "com.nageoffer.shortlink.aggregation"
})
public class AggregationServiceApplication { ... }
```

**作用**：Spring Boot 启动时，这个注解告诉框架"把本服务注册到 Nacos"。底层做的事：

``` java
1. 读取 spring.application.name → "short-link-admin"
2. 读取 spring.cloud.nacos.discovery.server-addr → "127.0.0.1:8848"
3. 获取本机 IP 和 server.port → 192.168.x.x:8002
4. 调 Nacos API：POST /nacos/v1/ns/instance
   注册 {"serviceName":"short-link-admin","ip":"...","port":8002}
5. 启动心跳线程，每 5 秒发一次保活
```

> **Gateway 为什么没加 `@EnableDiscoveryClient`？** Gateway 本身不是被调用方，不需要注册自己。但它的 pom 里引入了 `spring-cloud-starter-alibaba-nacos-discovery`，所以它**作为调用方**可以从 Nacos 拉实例列表——有 `lb://` 就够了。

### 4.2 `@EnableFeignClients` —— 开启声明式服务调用

只有 **admin** 模块有这个注解：

`admin/ShortLinkAdminApplication.java:32`

``` java
@EnableFeignClients("com.nageoffer.shortlink.admin.remote")
```

**作用**：扫描 `com.nageoffer.shortlink.admin.remote` 包下所有 `@FeignClient` 接口，为他们生成动态代理对象。

### 4.3 `@FeignClient` —— 声明远程服务接口

`D:\IDEA-java\mading_shortLink\admin\src\main\java\com\nageoffer\shortlink\admin\remote\ShortLinkActualRemoteService.java:47`

``` java

    value = "short-link-project",           // Nacos 服务名 —— 服务发现用
    url = "${aggregation.remote-url:}",     // 直连 URL —— 聚合模式用
    configuration = OpenFeignConfiguration.class  // 自定义配置（透传用户信息）
)
public interface ShortLinkActualRemoteService {

    @PostMapping("/api/short-link/v1/create")
    Result<ShortLinkCreateRespDTO> createShortLink(@RequestBody ShortLinkCreateReqDTO requestParam);
    // ... 十几个方法
}
```

**三个参数的含义**：

|参数|作用|
|---|---|

## 五、两种部署模式的切换逻辑

这个项目设计了一个巧妙的**双模式切换**，就在 FeignClient 的 `url` 参数上：

### 独立部署（dev 模式）

`aggregation.remote-url` 没配 → `url` 为空 → Feign 走 Nacos 发现：

``` java
Admin(8002) 调用 createShortLink()
  → Feign 从 Nacos 查到 "short-link-project" → [192.168.1.5:8001]
  → HTTP POST http://192.168.1.5:8001/api/short-link/v1/create
```

### 聚合部署（aggregation 模式，当前激活）

`aggregation.remote-url=http://127.0.0.1:8003` → `url` 不为空 → 跳过 Nacos，直连：

``` java
Aggregation(8003) 内部调用 createShortLink()
  → Feign 发现 url 有值 → 直接 POST http://127.0.0.1:8003/api/short-link/v1/create
  → 因为 admin 和 project 代码被 scanBasePackages 合并到了同一个 JVM
```

``` java
  → 拼接 URL 转发
```

## 八、总结：Nacos 在这个项目中的体现

| 维度               | 体现                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------- |
| **Nacos Server** | 本地 8848 端口，单机模式 + Derby 存储                                                             |
| **注册配置**         | `spring.cloud.nacos.discovery.server-addr: 127.0.0.1:8848` + `spring.application.name` |
| **注册注解**         | `@EnableDiscoveryClient` 打在 admin/project/aggregation 三个启动类上                           |
| **发现方式一**        | Gateway 的 `lb://服务名` → LoadBalancer 从 Nacos 拿实例列表                                      |
| **发现方式二**        | `@FeignClient(value = "服务名")` → Feign 从 Nacos 拿实例列表                                    |
| **扫描 Feign**     | `@EnableFeignClients("包路径")` 打在 admin 启动类上                                             |
| **聚合切换**         | FeignClient 的 `url = "${aggregation.remote-url:}"` 不为空则直连，跳过 Nacos                     |
| **未使用的功能**       | 配置中心（Nacos Config）——本项目所有配置都写在本地 yaml 里                                                |

一句话：**Nacos 就是这个项目的"电话本"**，`@EnableDiscoveryClient` 把号码登记上去，`@FeignClient` 和 `lb://` 从电话本里查号码然后拨过去。

# openfeign是什么,有什么用,在项目中哪体现了,有什么相关注解和注解,他们的作用是什么

现在把 OpenFeign 从头到尾讲透。

## 总结:
在启动类上加上注解@EnableFeignClient,呢么程序运行时就会启动远程调用功能,比如在后管的模块里写个接口,上面加上注解@FeignClient(),括号里写上要调用的服务的url或者nacos服务名,那么在调用该接口时,便会调用对应的服务方法

---

## 一、OpenFeign 是什么

OpenFeign 是 Spring Cloud 下的**声明式 HTTP 客户端**。它的核心思想：**你只需要定义一个 Java 接口 + 几个注解，框架帮你自动生成 HTTP 请求代码**，不用手写 `RestTemplate`、`HttpClient`、拼接 URL、序列化/反序列化这些样板代码。

对比一下：

``` java
// 不用 Feign —— 手写 HTTP 调用
RestTemplate rest = new RestTemplate();
String url = "http://192.168.1.5:8001/api/short-link/v1/create";
Result<ShortLinkCreateRespDTO> result = rest.postForObject(url, requestParam, ...);

// 用 Feign —— 声明式调用
Result<ShortLinkCreateRespDTO> result = shortLinkActualRemoteService.createShortLink(requestParam);
```

**OpenFeign = 把 HTTP 远程调用伪装成本地方法调用**。

## 二、项目中涉及的所有注解及作用

### 2.1 `@EnableFeignClients` —— 总开关

`D:\IDEA-java\mading_shortLink\admin\src\main\java\com\nageoffer\shortlink\admin\ShortLinkAdminApplication.java:32`

``` java
@SpringBootApplication
@EnableDiscoveryClient
@EnableFeignClients("com.nageoffer.shortlink.admin.remote")   // ← 总开关
@MapperScan("com.nageoffer.shortlink.admin.dao.mapper")
public class ShortLinkAdminApplication { ... }
```

**作用**：扫描指定包路径下所有 `@FeignClient` 接口，为每个接口生成一个**动态代理对象**并注入 Spring 容器。没有这个注解，`@FeignClient` 不会生效。

> 注意：`@EnableFeignClients` 只打在 **admin** 模块上，因为只有 admin 需要远程调用 project。project 是被调用方，不需要这个注解。

### 2.2 `@FeignClient` —— 定义远程服务

`D:\IDEA-java\mading_shortLink\admin\src\main\java\com\nageoffer\shortlink\admin\remote\ShortLinkActualRemoteService.java:47`

``` java
@FeignClient(
    value = "short-link-project",                    // ① Nacos 服务名，用于服务发现
    url = "${aggregation.remote-url:}",              // ② 直连 URL，聚合模式用
    configuration = OpenFeignConfiguration.class     // ③ 自定义配置类
)
public interface ShortLinkActualRemoteService {
    @PostMapping("/api/short-link/v1/create")
    Result<ShortLinkCreateRespDTO> createShortLink(@RequestBody ShortLinkCreateReqDTO requestParam);
    // ... 十几个方法
}
```

**三个属性逐个拆解**：

|属性|含义|
|---|---|
|`value` = `"short-link-project"`|告诉 Feign："去 Nacos 找这个服务名对应的 IP:Port"|
|`url` = `"${aggregation.remote-url:}"`|如果配置了值，直接连这个 URL，**跳过 Nacos 服务发现**。默认 `${...}` 带 `:` 后缀表示没配就为空|
|`configuration` = `OpenFeignConfiguration.class`|绑定自定义配置，这里用于注入 `RequestInterceptor`|

### 2.3 `@PostMapping` / `@GetMapping` / `@RequestBody` / `@RequestParam` —— MVC 注解复用

Feign 接口上的这些注解，和 Spring MVC Controller 上的**完全一样**：

``` java
@PostMapping("/api/short-link/v1/create")                          // HTTP 方法 + 路径
Result<ShortLinkCreateRespDTO> createShortLink(
    @RequestBody ShortLinkCreateReqDTO requestParam                // 请求体 JSON 序列化
);

@GetMapping("/api/short-link/v1/page")
Result<Page<ShortLinkPageRespDTO>> pageShortLink(
    @RequestParam("gid") String gid,                               // URL 查询参数
    @RequestParam("orderTag") String orderTag,
    @RequestParam("current") Long current,
    @RequestParam("size") Long size
);
```

**作用**：这些注解定义了"HTTP 请求长什么样"。Feign 在底层把这些注解翻译成真正的 HTTP 请求。

### 2.4 `@Configuration` + `RequestInterceptor` —— 请求拦截器

`D:\IDEA-java\mading_shortLink\admin\src\main\java\com\nageoffer\shortlink\admin\config\OpenFeignConfiguration.java`

``` java
@Configuration
public class OpenFeignConfiguration {

    @Bean
    public RequestInterceptor requestInterceptor() {
        return template -> {
            template.header("username", UserContext.getUsername());
            template.header("userId", UserContext.getUserId());
            template.header("realName", UserContext.getRealName());
        };
    }
}
```

**作用**：每次 Feign 发 HTTP 请求之前，自动往请求头里塞 `username`、`userId`、`realName`。这样被调方（project）就能从 Header 里拿到当前用户信息，不用每个方法里手动传。

## 四、完整调用链路（独立部署模式）

```
用户请求：POST /api/short-link/admin/v1/create
    ↓
Gateway(8000)
    │ Path 匹配 → TokenValidate 鉴权 → 透传 userId 到 Header
    │ lb://short-link-admin → 从 Nacos 拿到 admin 实例 8002
    ↓
Admin(8002) ShortLinkController.createShortLink()
    │ 调用 shortLinkActualRemoteService.createShortLink(dto)
    │   ↑ 这是一个 Feign 动态代理对象
    ↓
Feign 代理内部：
    │ 1. 从 @FeignClient(value = "short-link-project") 知道目标服务名
    │ 2. 从 Nacos 拉取 "short-link-project" 实例列表 → [192.168.1.5:8001]
    │ 3. LoadBalancer 选一个实例
    │ 4. RequestInterceptor 往 Header 塞 username/userId/realName
    │ 5. 根据 @PostMapping("/api/short-link/v1/create") 拼 URL
    │    → http://192.168.1.5:8001/api/short-link/v1/create
    │ 6. 将 @RequestBody 的参数 JSON 序列化
    │ 7. 发 HTTP POST 请求
    ↓
Project(8001) ShortLinkController.createShortLink()
    │ 真正执行业务逻辑：写 DB、写缓存、返回结果
    ↓
Feign 收到响应 → JSON 反序列化为 Result<ShortLinkCreateRespDTO> → 返回给 Admin Controller
```

## 六、注解全景总结

|注解|位置|作用|
|---|---|---|
|`@EnableFeignClients`|admin 启动类|扫描并激活所有 Feign 客户端接口|
|`@FeignClient`|`ShortLinkActualRemoteService`|声明"这是一个远程服务的 HTTP 客户端"|
|`@FeignClient.value`|同上|指定 Nacos 中的目标服务名，用于服务发现|
|FeignClient.url|同上|直连 URL，配了值就跳过服务发现|
|`@FeignClient.configuration`|同上|绑定自定义拦截器配置|
|`@PostMapping` / `@GetMapping`|Feign 接口方法上|定义 HTTP 方法和请求路径|
|`@RequestBody`|Feign 接口方法参数|标记参数放到 HTTP 请求体|
|`@RequestParam`|Feign 接口方法参数|标记参数放到 URL 查询字符串|
|`@Configuration`|`OpenFeignConfiguration`|声明这是一个配置类|
|`@Bean` + `RequestInterceptor`|同上|每次 Feign 请求前自动塞用户信息到 Header|

**一句话**：OpenFeign 让你在 admin 模块里定义一个接口、标几个注解，就能像调用本地方法一样调用 project 模块的 HTTP 接口，底层自动帮你完成服务发现、负载均衡、序列化、HTTP 通信全部脏活。

## 一、Gateway 是什么，在项目中的角色

Spring Cloud Gateway 是基于 **WebFlux（Netty + Reactor）** 的 API 网关。它在这个项目中是**整个系统的唯一入口**——所有前端请求都先打到 Gateway，然后由它决定：

1. **路由**——这个请求该转发给哪个微服务
2. **鉴权**——请求带没带合法 Token
3. **透传**——鉴权通过后把用户信息塞进 Header 传给下游

Gateway 模块只有 **4 个 Java 文件**，极简但五脏俱全：

```
gateway/src/main/java/com/nageoffer/shortlink/gateway/
├── GatewayServiceApplication.java          # 启动类
├── config/
│   └── Config.java                         # TokenValidate 的白名单配置类
├── dto/
│   └── GatewayErrorResult.java             # 鉴权失败返回体
└── filter/
    └── TokenValidateGatewayFilterFactory.java  # 自定义 Token 鉴权过滤器
```

## 五、路由三要素详解

每条路由由三个核心部分组成：

### 5.1 Predicate（断言）—— "这个请求归我管吗？"

```
predicates:
  - Path=/api/short-link/admin/**
```

Spring Cloud Gateway 内置了多种断言（Path、Header、Host、Method、Cookie 等），这里只用到了 `Path`。逻辑是：

```
请求路径以 /api/short-link/admin/ 开头 → 匹配 short-link-admin 路由
请求路径以 /api/short-link/ 开头（但非 admin） → 匹配 short-link-project 路由
```

> 路由匹配是**有序**的，先匹配 /admin 的那条，匹配不上才落到 /project 那条。

### 5.2 URI（目标地址）—— "往哪转发？"

```
uri: lb://short-link-aggregation/api/short-link/admin/**
```

`lb://` 的工作流程：

```
1. 从 Nacos 拉取 "short-link-aggregation" 的所有健康实例
2. LoadBalancer 轮询选一台（比如 192.168.1.5:8003）
3. 拼接完整 URL：http://192.168.1.5:8003/api/short-link/admin/xxx
4. 发 HTTP 请求
```

**聚合 vs 独立的关键区别**：

|模式|`uri` 中的服务名|转发给谁|
|---|---|---|
|dev|`lb://short-link-admin`|admin 服务（8002）|
|dev|`lb://short-link-project`|project 服务（8001）|
|aggregation|`lb://short-link-aggregation`|aggregation 服务（8003，admin+project 合并）|

### 5.3 Filter（过滤器）—— "转发前做什么处理？"

```
filters:
  - name: TokenValidate
    args:
      whitePathList:
        - /api/short-link/admin/v1/user/login
        - /api/short-link/admin/v1/user/has-username
```

`TokenValidate` 是自定义的 GatewayFilter，名字对应 `TokenValidateGatewayFilterFactory` 类（Spring Cloud Gateway 的命名约定：类名去掉 `GatewayFilterFactory` 前缀）。

## 六、TokenValidate 过滤器 —— 鉴权核心

`D:\IDEA-java\mading_shortLink\gateway\src\main\java\com\nageoffer\shortlink\gateway\filter\TokenValidateGatewayFilterFactory.java`

### 6.1 类结构

```
@Component
public class TokenValidateGatewayFilterFactory
        extends AbstractGatewayFilterFactory<Config> {   // Config 是配置类

    private final StringRedisTemplate stringRedisTemplate;  // 查 Redis 验证 Token

    public TokenValidateGatewayFilterFactory(StringRedisTemplate stringRedisTemplate) {
        super(Config.class);           // 告诉父类：我的配置类是 Config
        this.stringRedisTemplate = stringRedisTemplate;
    }
    // ...
}
```

`Config` 类（`gateway/config/Config.java`）：

```
@Data
public class Config {
    private List<String> whitePathList;   // 白名单路径列表
}
```

**yaml 中的 `args.whitePathList` 会自动映射到 `Config.whitePathList`**。

### 6.2 鉴权执行流程

```
@Override
public GatewayFilter apply(Config config) {
    return (exchange, chain) -> {
        // ① 拿到请求路径和请求方法
        String requestPath = request.getPath().toString();
        String requestMethod = request.getMethod().name();

        // ② 判断是否在白名单中
        if (!isPathInWhiteList(requestPath, requestMethod, config.getWhitePathList())) {

            // ③ 不在白名单 → 从 Header 取 username 和 token
            String username = request.getHeaders().getFirst("username");
            String token = request.getHeaders().getFirst("token");

            // ④ 去 Redis 验证：short-link:login:{username} 这个 Hash 里有没有这个 token
            userInfo = stringRedisTemplate.opsForHash()
                .get("short-link:login:" + username, token);

            if (userInfo != null) {
                // ⑤ 验证通过 → 解析用户 JSON，把 userId 和 realName 塞进 Header
                JSONObject userJson = JSON.parseObject(userInfo.toString());
                httpHeaders.set("userId", userJson.getString("id"));
                httpHeaders.set("realName", URLEncoder.encode(realName, UTF_8));
                return chain.filter(exchange);   // 放行
            }

            // ⑥ 验证失败 → 返回 401
            response.setStatusCode(HttpStatus.UNAUTHORIZED);
            return response.writeWith(Mono.fromSupplier(() -> {
                GatewayErrorResult result = GatewayErrorResult.builder()
                    .status(401)
                    .message("Token validation error")
                    .build();
                return bufferFactory.wrap(JSON.toJSONString(result).getBytes());
            }));
        }
        // ⑦ 在白名单 → 直接放行
        return chain.filter(exchange);
    };
}
```

### 6.3 白名单判断逻辑

```
private boolean isPathInWhiteList(String requestPath, String requestMethod,
                                   List<String> whitePathList) {
    // 条件 1：路径以白名单中的任何一条开头
    boolean inWhiteList = whitePathList.stream()
        .anyMatch(requestPath::startsWith);
    // 条件 2：POST /api/short-link/admin/v1/user（注册接口）
    boolean isRegister = Objects.equals(requestPath, "/api/short-link/admin/v1/user")
                      && Objects.equals(requestMethod, "POST");
    return inWhiteList || isRegister;
}
```

**白名单覆盖的情况**：

|路径|为什么放行|
|---|---|
|`/api/short-link/admin/v1/user/login`|登录接口，还没 token 呢|
|`/api/short-link/admin/v1/user/has-username`|检查用户名是否已存在|
|`POST /api/short-link/admin/v1/user`|注册接口|

## 七、Gateway 与下游服务的协作 —— 用户信息传递链路

这是 Gateway 设计中最巧妙的一环，三个组件接力完成：

```
┌─────────────────────────────────────────────────────────────┐
│  前端请求 Header: username=zhangsan, token=abc123            │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│  Gateway TokenValidate                                      │
│  ① 从 Header 拿 username + token                             │
│  ② Redis 校验：short-link:login:zhangsan → {id:1,name:张三}  │
│  ③ 把 userId=1, realName=张三 塞进转发 Header                 │
└──────────────────────┬──────────────────────────────────────┘
                       ↓ Header: username, token, userId, realName
┌─────────────────────────────────────────────────────────────┐
│  Admin 服务 UserTransmitFilter (order=0, 最先执行)            │
│  从 Header 取 userId, username, realName                     │
│  写入 UserContext（TransmittableThreadLocal）                 │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│  Admin 服务 UserContext                                      │
│  静态方法 getUserId() / getUsername() / getRealName()        │
│  任何地方都可以随时拿到当前用户信息                            │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│  OpenFeign 的 RequestInterceptor                             │
│  发 Feign 请求前，自动从 UserContext 取用户信息塞 Header       │
│  把用户信息继续传递给 Project 服务                            │
└─────────────────────────────────────────────────────────────┘
```

### 关键组件对照

|组件|位置|职责|
|---|---|---|
|`TokenValidateGatewayFilterFactory`|gateway|在网关层统一鉴权，鉴权通过后往 Header 塞 `userId`、`realName`|
|`UserTransmitFilter`|admin|下游第一个过滤器，从 Header 取出用户信息，写入 `UserContext`|
|`UserContext`|admin|基于 `TransmittableThreadLocal` 的线程级用户上下文容器|
|`OpenFeignConfiguration`|admin|Feign 拦截器，发请求前从 `UserContext` 取用户信息塞到 Header|

**为什么要用 `TransmittableThreadLocal` 而不是普通 `ThreadLocal`？** 因为项目里用到了线程池异步任务，普通 `ThreadLocal` 在跨线程时会丢失数据，`TransmittableThreadLocal`（阿里的 TTL 库）能保证父子线程间传递。

## 八、一个完整请求的生命周期

```
用户登录：POST /api/short-link/admin/v1/user/login
    ↓
Gateway(8000)
    Path 匹配 → /api/short-link/admin/** 开头
    → 路由 short-link-admin-aggregation
    → TokenValidate 过滤器：在白名单 → 直接放行
    → lb://short-link-aggregation → 转发到 8003
    ↓
Aggregation(8003)
    UserController.login() → 验证用户名密码 → 生成 token
    → 写入 Redis：HSET short-link:login:zhangsan token值 userJson
    → 返回 {token: "abc123", ...}
```

```
用户创建短链接：POST /api/short-link/admin/v1/create
    Header: username=zhangsan, token=abc123
    ↓
Gateway(8000)
    Path 匹配 → /api/short-link/admin/** 开头
    → 路由 short-link-admin-aggregation
    → TokenValidate 过滤器：
       不在白名单 → 拿 Header 中的 username + token
       → Redis 查 HSET short-link:login:zhangsan → 命中，拿到 {id: "1", realName: "张三"}
       → Header 中追加 userId=1, realName=张三
       → 放行
    → lb://short-link-aggregation → 转发到 8003
    ↓
Aggregation(8003)
    UserTransmitFilter：从 Header 取 userId/username/realName → 写入 UserContext
    UserFlowRiskControlFilter：流控检查
    ShortLinkController.createShortLink() → 业务处理
    → 返回短链接
```

```
Token 无效：POST /api/short-link/admin/v1/create
    Header: username=zhangsan, token=expired_token
    ↓
Gateway(8000)
    → TokenValidate：Redis 中查不到这个 token → 返回 401
    → 响应体：{"status": 401, "message": "Token validation error"}
    ↓
请求根本没到下游服务，直接在网关拦截
```

## 十、一句话

**Gateway = 系统的门禁**。它在 8000 端口接住所有请求，根据 Path 决定路由给谁（聚合模式下只有一个 aggregation 服务），在转发前用自定义的 `TokenValidate` 过滤器统一校验登录态——白名单放行、校验通过透传用户信息、校验失败直接返回 401，请求根本到不了下游。
