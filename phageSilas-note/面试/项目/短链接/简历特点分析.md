# 第二点
## Cache Aside是什么,在项目中是怎么体现的
### 什么是 Cache Aside？

**Cache Aside（旁路缓存）** 是分布式系统中维护缓存与数据库一致性的经典模式。其核心思想是：**缓存只是数据库的一个"旁路副本"，应用程序直接同时与缓存和数据库交互，而非让缓存层自动同步。**

该模式有四项核心操作原则：

```
┌─────────────────────────────────────────────────────────┐
│                   Cache Aside 模式                        │
├─────────────────┬───────────────────────────────────────┤
│   读操作        │   写操作                                │
│                 │                                        │
│  1. 先查缓存    │  1. 先更新数据库                        │
│  2. 命中→返回   │  2. 再删除缓存（而非更新缓存）           │
│  3. 未命中→查DB │                                        │
│  4. 写回缓存    │                                        │
└─────────────────┴───────────────────────────────────────┘
```


**为什么是"删除缓存"而不是"更新缓存"？** —— 因为删除是幂等的，避免了并发写导致的缓存脏数据。下次读请求自然会回源数据库并重建缓存。

### 在项目中的具体体现

这个项目围绕短链接跳转场景，Cache Aside 模式体现在三个层面：

#### 一、读流程 —— `restoreUrl` 方法

[/project/src/main/java/.../ShortLinkServiceImpl.java](file://D:/IDEA-java/mading_shortLink/project/src/main/java/com/nageoffer/shortlink/project/service/impl/ShortLinkServiceImpl.java#L370-L453)

```java
// 1️⃣ 先查 Redis 缓存
String originalLink = stringRedisTemplate.opsForValue()
    .get(String.format(GOTO_SHORT_LINK_KEY, fullShortUrl));
if (StrUtil.isNotBlank(originalLink)) {
    // 缓存命中 → 直接重定向
    ((HttpServletResponse) response).sendRedirect(originalLink);
    return;
}

// 2️⃣ 缓存未命中 → 加分布式锁防击穿 → 查数据库
ShortLinkDO shortLinkDO = baseMapper.selectOne(queryWrapper);

// 3️⃣ 将数据库结果写回 Redis 缓存
stringRedisTemplate.opsForValue().set(
    String.format(GOTO_SHORT_LINK_KEY, fullShortUrl),
    shortLinkDO.getOriginUrl(),
    LinkUtil.getLinkCacheValidTime(shortLinkDO.getValidDate()), TimeUnit.MILLISECONDS
);
```


**对应 Cache Aside 读路径：** 缓存命中直接返回 → 未命中查 DB → 写回缓存。

#### 二、写流程 —— `updateShortLink` 方法

[/project/src/main/java/.../ShortLinkServiceImpl.java](file://D:/IDEA-java/mading_shortLink/project/src/main/java/com/nageoffer/shortlink/project/service/impl/ShortLinkServiceImpl.java#L333-L344)

```java
// 1️⃣ 先更新数据库（代码中前面已经执行了 baseMapper.update 或 insert）
// ...

// 2️⃣ 再删除缓存（关键步骤！）
if (!Objects.equals(hasShortLinkDO.getValidDateType(), requestParam.getValidDateType())
        || !Objects.equals(hasShortLinkDO.getValidDate(), requestParam.getValidDate())
        || !Objects.equals(hasShortLinkDO.getOriginUrl(), requestParam.getOriginUrl())) {
    
    // 删除跳转缓存
    stringRedisTemplate.delete(String.format(GOTO_SHORT_LINK_KEY, requestParam.getFullShortUrl()));
    
    // 过期复活场景：同时删除空值缓存
    if (hasShortLinkDO.getValidDate() != null && hasShortLinkDO.getValidDate().before(new Date())) {
        if (requestParam.getValidDateType() == PERMANENT || requestParam.getValidDate().after(new Date())) {
            stringRedisTemplate.delete(String.format(GOTO_IS_NULL_SHORT_LINK_KEY, requestParam.getFullShortUrl()));
        }
    }
}
```


**对应 Cache Aside 写路径：** 先改数据库 → 再删缓存（不是更新！）。只有有效期类型、有效期时间、原始URL这三项真正影响跳转结果的字段变更时才删除缓存，避免了不必要的缓存失效。

### 总结：Cache Aside 在项目中的三条铁律

| 原则 | 项目实现 |
|------|---------|
| **读：缓存优先，未命中回源** | `restoreUrl` 先查 Redis → 未命中查 DB → 写回 Redis |
| **写：先数据库，后删缓存** | `updateShortLink` / 回收站操作都是先 `baseMapper.update()` → 再 `stringRedisTemplate.delete()` |
| **删缓存而非更新缓存** | 所有写操作一律 `delete`，绝不 `set` 新值到跳转缓存 |
| **防穿透防击穿补充** | 布隆过滤器 + 空值缓存 + 分布式锁，这三件套让 Cache Aside 在高并发下依然可靠 |

这个设计确保了：**即使 Redis 宕机或被清空，系统依然能通过数据库正常提供服务；同时在高频跳转场景下，绝大多数请求被 Redis 缓存拦截，数据库压力极小。**
