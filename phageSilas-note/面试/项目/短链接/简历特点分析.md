## Cache Aside是什么,在项目中是怎么体现的
### 什么是 Cache Aside？

**Cache Aside（旁路缓存）** 是分布式系统中维护缓存与数据库一致性的经典模式。其核心思想是：**缓存只是数据库的一个"旁路副本"，应用程序直接同时与缓存和数据库交互，而非让缓存层自动同步。**

该模式有四项核心操作原则：

```
┌─────────────────────────────────────────────────────────┐
│                   Cache Aside 模式                        │
├─────────────────┬───────────────────────────────────────┤
│   读操作        │   写操作                                │
│                 │                                        │
│  1. 先查缓存    │  1. 先更新数据库                        │
│  2. 命中→返回   │  2. 再删除缓存（而非更新缓存）           │
│  3. 未命中→查DB │                                        │
│  4. 写回缓存    │                                        │
└─────────────────┴───────────────────────────────────────┘
```


**为什么是"删除缓存"而不是"更新缓存"？** —— 因为删除是幂等的，避免了并发写导致的缓存脏数据。下次读请求自然会回源数据库并重建缓存。

### 总结：Cache Aside 在项目中的三条铁律

| 原则 | 项目实现 |
|------|---------|
| **读：缓存优先，未命中回源** | `restoreUrl` 先查 Redis → 未命中查 DB → 写回 Redis |
| **写：先数据库，后删缓存** | `updateShortLink` / 回收站操作都是先 `baseMapper.update()` → 再 `stringRedisTemplate.delete()` |
| **删缓存而非更新缓存** | 所有写操作一律 `delete`，绝不 `set` 新值到跳转缓存 |
| **防穿透防击穿补充** | 布隆过滤器 + 空值缓存 + 分布式锁，这三件套让 Cache Aside 在高并发下依然可靠 |

这个设计确保了：**即使 Redis 宕机或被清空，系统依然能通过数据库正常提供服务；同时在高频跳转场景下，绝大多数请求被 Redis 缓存拦截，数据库压力极小。**

### 一、双重判定在哪里体现？

```java
// ═══════════════ 第一次判定（无锁，快速路径） ═══════════════
// 判定1：查 Redis 跳转缓存
String originalLink = stringRedisTemplate.opsForValue()
    .get(String.format(GOTO_SHORT_LINK_KEY, fullShortUrl));
if (StrUtil.isNotBlank(originalLink)) {
    ((HttpServletResponse) response).sendRedirect(originalLink);
    return;  // ✅ 命中，直接返回，不走后续任何逻辑
}

// 判定2：布隆过滤器——不存在则一定不存在
boolean contains = shortUriCreateCachePenetrationBloomFilter.contains(fullShortUrl);
if (!contains) {
    ((HttpServletResponse) response).sendRedirect("/page/notfound");
    return;  // ✅ 拦截不存在 key，防穿透
}

// 判定3：空值缓存——之前已经确认过不存在的 key
String gotoIsNullShortLink = stringRedisTemplate.opsForValue()
    .get(String.format(GOTO_IS_NULL_SHORT_LINK_KEY, fullShortUrl));
if (StrUtil.isNotBlank(gotoIsNullShortLink)) {
    ((HttpServletResponse) response).sendRedirect("/page/notfound");
    return;  // ✅ 已知无效，直接拒绝
}

// ═══════════════ 加分布式锁 ═══════════════
RLock lock = redissonClient.getLock(String.format(LOCK_GOTO_SHORT_LINK_KEY, fullShortUrl));
lock.lock();
try {
    // ═══════════════ 第二次判定（有锁，精确路径） ═══════════════
    // 判定4：再次查 Redis 跳转缓存 ← 这就是"双重判定"的核心！
    originalLink = stringRedisTemplate.opsForValue()
        .get(String.format(GOTO_SHORT_LINK_KEY, fullShortUrl));
    if (StrUtil.isNotBlank(originalLink)) {
        // ✅ 上一个拿到锁的线程已经把数据写入了缓存，直接用！
        ((HttpServletResponse) response).sendRedirect(originalLink);
        return;
    }

    // 判定5：再次查空值缓存
    gotoIsNullShortLink = stringRedisTemplate.opsForValue()
        .get(String.format(GOTO_IS_NULL_SHORT_LINK_KEY, fullShortUrl));
    if (StrUtil.isNotBlank(gotoIsNullShortLink)) {
        ((HttpServletResponse) response).sendRedirect("/page/notfound");
        return;
    }

    // ⚠️ 两次判定都未命中，确认缓存中确实没有 → 查数据库
    ShortLinkDO shortLinkDO = baseMapper.selectOne(queryWrapper);
    // ... 写回缓存 ...
} finally {
    lock.unlock();
}
```


**双重判定的"双重"指的就是——同一个缓存 key，在加锁前查一次，加锁后再查一次。** 这正是经典的 **Double-Check Locking（双重检查锁定）** 模式。

---

### 二、为什么要双重判定？

用一幅时序图来说明：

![[image-4.png]]


**如果没有第二次判定**，请求 B 获得锁后会直接查数据库——但此时请求 A 已经把数据写入 Redis 了！请求 B 白查一次数据库，C、D 也各自白查一次。

**有了第二次判定**，请求 B 获得锁后再查一次 Redis → **命中！** → 直接返回，不再查 DB。B、C、D 都不会再打到数据库。

> 核心价值：**N 个并发请求同时发现缓存未命中，只有第 1 个真正查了 DB，其余 N-1 个全部靠第二次判定从缓存中获取。**

---

### 三、为什么还要加分布式锁？

```
不加锁的后果（缓存击穿）：

   热点 key "short-link:goto:abc123" 在 Redis 中过期
                    │
    ┌───────┬───────┼───────┬───────┐
    ▼       ▼       ▼       ▼       ▼
  请求1   请求2   请求3   ...     请求N
    │       │       │               │
    ▼       ▼       ▼               ▼
  查DB    查DB    查DB           查DB
    │       │       │               │
    └───────┴───────┴───────────────┘
                    │
                    ▼
           数据库瞬间 N 个相同查询
              → DB 压力飙升 → 雪崩
```


加上分布式锁后：

```
   热点 key 过期，N 个请求同时发现缓存未命中
                    │
    ┌───────┬───────┼───────┬───────┐
    ▼       ▼       ▼       ▼       ▼
  请求1   请求2   请求3   ...     请求N
    │       │       │               │
  争抢同一把分布式锁（基于 Redis + Lua 原子操作）
    │       │       │               │
    ▼       ▼       ▼               ▼
  获得锁   等待    等待            等待
    │
  查DB → 写缓存 → 释放锁
    │
    └──── 请求2~N 获得锁 → 第二次判定 → 命中缓存 ✓
                    │
                    ▼
           数据库只承受 1 次查询！
```


**分布式锁把"N 次 DB 查询"压缩成了"1 次 DB 查询"。**

---

### 四、如何减少缓存穿透和缓存击穿？

| 问题 | 攻击方式 | 本项目的防御层次 |
|------|---------|----------------|
| **缓存穿透** | 用不存在的 key 大量请求 | **第1层：布隆过滤器**（判定不存在则直接拒绝）→ **第2层：空值缓存**（已确认无效的 key 缓存标记 `-`，30分钟） |
| **缓存击穿** | 热点 key 过期瞬间大量并发 | **第3层：分布式锁**（同一 key 只允许一个请求查 DB）→ **第4层：双重判定**（等锁期间缓存已被填充，直接命中） |

整个防御链路是一条**逐层过滤的漏斗**：

```
  海量请求
     │
     ▼
┌─────────────┐
│ Redis 缓存   │  ← 99%+ 命中，直接返回（Cache Aside 读路径）
└──────┬──────┘
       │ miss
       ▼
┌─────────────┐
│ 布隆过滤器   │  ← 拦截不存在 key → 防穿透
└──────┬──────┘
       │ may exist
       ▼
┌─────────────┐
│ 空值缓存     │  ← 拦截已确认无效 key → 防穿透
└──────┬──────┘
       │ miss
       ▼
┌─────────────┐
│ 分布式锁     │  ← 串行化 DB 访问 → 防击穿
└──────┬──────┘
       │ 获得锁
       ▼
┌─────────────┐
│ 双重判定     │  ← 等锁期间缓存可能已被填充 → 避免重复查 DB
└──────┬──────┘
       │ 二次 miss（极端罕见）
       ▼
┌─────────────┐
│ 数据库查询   │  ← 只有极少数请求到达这里
└─────────────┘
```


**总结一句话：双重判定是"等锁白等"的解决方案，分布式锁是"N 个请求一起砸 DB"的闸门，二者配合让缓存击穿场景下数据库只承受 1 次查询压力。**

## 关键误区：你忽略了"等锁期间"发生的事情

你的推理是：

> "只有一个请求拿到锁 → 从拿锁到写缓存之间没有其他请求 → 第二次查缓存多余"

这个推理的漏洞在于：**请求 B 在"等锁"期间，请求 A 已经完成了"查 DB → 写缓存 → 释放锁"这一整套操作。**

## 问题的本质

| 时间点 | 请求 A | 请求 B | Redis 中有数据？ |
|--------|--------|--------|:---:|
| T1 | 第1次查缓存 → MISS | — | ❌ |
| T2 | 获得锁 | 第1次查缓存 → MISS | ❌ |
| T3 | 第2次查缓存 → MISS | **等待锁中...** | ❌ |
| T4 | 查 DB | **等待锁中...** | ❌ |
| T5 | **写缓存** ✅ | **等待锁中...** | ✅ |
| T6 | 释放锁 | **等待锁中...** | ✅ |
| T7 | — | 获得锁 | ✅ |
| T8 | — | **第2次查缓存 → HIT** 🎯 | ✅ |

**请求 B 的第1次查缓存发生在 T2**，此时 A 刚刚拿到锁，缓存里还没有数据。**B 的第2次查缓存发生在 T8**，此时 A 早已写完缓存并释放了锁。

两次查缓存之间，**世界已经变了**——这就是第二次判定存在的全部意义。

## 没有第二次判定会怎样？

```java
// 假设去掉第二次判定，获得锁后直接查 DB：
lock.lock();
try {
    // 直接查 DB，不查缓存
    ShortLinkDO shortLinkDO = baseMapper.selectOne(queryWrapper);  // 多余的 DB 查询！
    // ...
}
```


如果同时有 **100 个请求**在等同一把锁，那么：
- 有第二次判定：**1 次 DB 查询**（A 查），剩下 99 个全部命中缓存
- 没有第二次判定：**100 次 DB 查询**，每个请求获得锁后都去查一次

---

## 一句话总结

> **你假设的是"同一时刻只有一个请求在操作"，但真实情况是"多个请求串行排队操作"，两次判定之间的间隔内，缓存状态已经被排在前面的请求改变了。第二次判定就是用来感知这个变化的。**

## 也就是说第二层查缓存只是减少了可能多余的查db操作,从结果上看不影响,主要是减少db压力的是吗,我说的对吗

**完全正确，理解非常到位。**

总结一下就是：

> **第二次查缓存不影响最终结果的正确性，它唯一的目的是——让那些"排队白等了"的请求省掉一次多余的 DB 查询。**

用一句话概括：**分布式锁负责"挡"，双重判定负责"省"。**

- 锁挡住了 N-1 个请求并发砸向 DB
- 第二次判定让这 N-1 个请求排队拿到锁后，发现缓存已经有了，直接走人，**连那一次 DB 查询都省了**

所以如果只有 2 个并发请求，收益是省 1 次 DB 查询；如果有 1000 个并发请求，收益就是省 999 次 DB 查询。**并发越高，这个设计的价值越大。**

## 说一下Redisson分布式锁,为什么不用redis自带的setnx,优点在哪
