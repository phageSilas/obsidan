## Cache Aside是什么,在项目中是怎么体现的
### 什么是 Cache Aside？

**Cache Aside（旁路缓存）** 是分布式系统中维护缓存与数据库一致性的经典模式。其核心思想是：**缓存只是数据库的一个"旁路副本"，应用程序直接同时与缓存和数据库交互，而非让缓存层自动同步。**

该模式有四项核心操作原则：

```
┌─────────────────────────────────────────────────────────┐
│                   Cache Aside 模式                        │
├─────────────────┬───────────────────────────────────────┤
│   读操作        │   写操作                                │
│                 │                                        │
│  1. 先查缓存    │  1. 先更新数据库                        │
│  2. 命中→返回   │  2. 再删除缓存（而非更新缓存）           │
│  3. 未命中→查DB │                                        │
│  4. 写回缓存    │                                        │
└─────────────────┴───────────────────────────────────────┘
```


**为什么是"删除缓存"而不是"更新缓存"？** —— 因为删除是幂等的，避免了并发写导致的缓存脏数据。下次读请求自然会回源数据库并重建缓存。

### 总结：Cache Aside 在项目中的三条铁律

| 原则 | 项目实现 |
|------|---------|
| **读：缓存优先，未命中回源** | `restoreUrl` 先查 Redis → 未命中查 DB → 写回 Redis |
| **写：先数据库，后删缓存** | `updateShortLink` / 回收站操作都是先 `baseMapper.update()` → 再 `stringRedisTemplate.delete()` |
| **删缓存而非更新缓存** | 所有写操作一律 `delete`，绝不 `set` 新值到跳转缓存 |
| **防穿透防击穿补充** | 布隆过滤器 + 空值缓存 + 分布式锁，这三件套让 Cache Aside 在高并发下依然可靠 |

这个设计确保了：**即使 Redis 宕机或被清空，系统依然能通过数据库正常提供服务；同时在高频跳转场景下，绝大多数请求被 Redis 缓存拦截，数据库压力极小。**

### 一、双重判定在哪里体现？

```java
// ═══════════════ 第一次判定（无锁，快速路径） ═══════════════
// 判定1：查 Redis 跳转缓存
String originalLink = stringRedisTemplate.opsForValue()
    .get(String.format(GOTO_SHORT_LINK_KEY, fullShortUrl));
if (StrUtil.isNotBlank(originalLink)) {
    ((HttpServletResponse) response).sendRedirect(originalLink);
    return;  // ✅ 命中，直接返回，不走后续任何逻辑
}

// 判定2：布隆过滤器——不存在则一定不存在
boolean contains = shortUriCreateCachePenetrationBloomFilter.contains(fullShortUrl);
if (!contains) {
    ((HttpServletResponse) response).sendRedirect("/page/notfound");
    return;  // ✅ 拦截不存在 key，防穿透
}

// 判定3：空值缓存——之前已经确认过不存在的 key
String gotoIsNullShortLink = stringRedisTemplate.opsForValue()
    .get(String.format(GOTO_IS_NULL_SHORT_LINK_KEY, fullShortUrl));
if (StrUtil.isNotBlank(gotoIsNullShortLink)) {
    ((HttpServletResponse) response).sendRedirect("/page/notfound");
    return;  // ✅ 已知无效，直接拒绝
}

// ═══════════════ 加分布式锁 ═══════════════
RLock lock = redissonClient.getLock(String.format(LOCK_GOTO_SHORT_LINK_KEY, fullShortUrl));
lock.lock();
try {
    // ═══════════════ 第二次判定（有锁，精确路径） ═══════════════
    // 判定4：再次查 Redis 跳转缓存 ← 这就是"双重判定"的核心！
    originalLink = stringRedisTemplate.opsForValue()
        .get(String.format(GOTO_SHORT_LINK_KEY, fullShortUrl));
    if (StrUtil.isNotBlank(originalLink)) {
        // ✅ 上一个拿到锁的线程已经把数据写入了缓存，直接用！
        ((HttpServletResponse) response).sendRedirect(originalLink);
        return;
    }

    // 判定5：再次查空值缓存
    gotoIsNullShortLink = stringRedisTemplate.opsForValue()
        .get(String.format(GOTO_IS_NULL_SHORT_LINK_KEY, fullShortUrl));
    if (StrUtil.isNotBlank(gotoIsNullShortLink)) {
        ((HttpServletResponse) response).sendRedirect("/page/notfound");
        return;
    }

    // ⚠️ 两次判定都未命中，确认缓存中确实没有 → 查数据库
    ShortLinkDO shortLinkDO = baseMapper.selectOne(queryWrapper);
    // ... 写回缓存 ...
} finally {
    lock.unlock();
}
```


**双重判定的"双重"指的就是——同一个缓存 key，在加锁前查一次，加锁后再查一次。** 这正是经典的 **Double-Check Locking（双重检查锁定）** 模式。

---

### 二、为什么要双重判定？

用一幅时序图来说明：

![[image-4.png]]


**如果没有第二次判定**，请求 B 获得锁后会直接查数据库——但此时请求 A 已经把数据写入 Redis 了！请求 B 白查一次数据库，C、D 也各自白查一次。

**有了第二次判定**，请求 B 获得锁后再查一次 Redis → **命中！** → 直接返回，不再查 DB。B、C、D 都不会再打到数据库。

> 核心价值：**N 个并发请求同时发现缓存未命中，只有第 1 个真正查了 DB，其余 N-1 个全部靠第二次判定从缓存中获取。**

---

### 三、为什么还要加分布式锁？

```
不加锁的后果（缓存击穿）：

   热点 key "short-link:goto:abc123" 在 Redis 中过期
                    │
    ┌───────┬───────┼───────┬───────┐
    ▼       ▼       ▼       ▼       ▼
  请求1   请求2   请求3   ...     请求N
    │       │       │               │
    ▼       ▼       ▼               ▼
  查DB    查DB    查DB           查DB
    │       │       │               │
    └───────┴───────┴───────────────┘
                    │
                    ▼
           数据库瞬间 N 个相同查询
              → DB 压力飙升 → 雪崩
```


加上分布式锁后：

```
   热点 key 过期，N 个请求同时发现缓存未命中
                    │
    ┌───────┬───────┼───────┬───────┐
    ▼       ▼       ▼       ▼       ▼
  请求1   请求2   请求3   ...     请求N
    │       │       │               │
  争抢同一把分布式锁（基于 Redis + Lua 原子操作）
    │       │       │               │
    ▼       ▼       ▼               ▼
  获得锁   等待    等待            等待
    │
  查DB → 写缓存 → 释放锁
    │
    └──── 请求2~N 获得锁 → 第二次判定 → 命中缓存 ✓
                    │
                    ▼
           数据库只承受 1 次查询！
```


**分布式锁把"N 次 DB 查询"压缩成了"1 次 DB 查询"。**

---

### 四、如何减少缓存穿透和缓存击穿？

| 问题 | 攻击方式 | 本项目的防御层次 |
|------|---------|----------------|
| **缓存穿透** | 用不存在的 key 大量请求 | **第1层：布隆过滤器**（判定不存在则直接拒绝）→ **第2层：空值缓存**（已确认无效的 key 缓存标记 `-`，30分钟） |
| **缓存击穿** | 热点 key 过期瞬间大量并发 | **第3层：分布式锁**（同一 key 只允许一个请求查 DB）→ **第4层：双重判定**（等锁期间缓存已被填充，直接命中） |

整个防御链路是一条**逐层过滤的漏斗**：

```
  海量请求
     │
     ▼
┌─────────────┐
│ Redis 缓存   │  ← 99%+ 命中，直接返回（Cache Aside 读路径）
└──────┬──────┘
       │ miss
       ▼
┌─────────────┐
│ 布隆过滤器   │  ← 拦截不存在 key → 防穿透
└──────┬──────┘
       │ may exist
       ▼
┌─────────────┐
│ 空值缓存     │  ← 拦截已确认无效 key → 防穿透
└──────┬──────┘
       │ miss
       ▼
┌─────────────┐
│ 分布式锁     │  ← 串行化 DB 访问 → 防击穿
└──────┬──────┘
       │ 获得锁
       ▼
┌─────────────┐
│ 双重判定     │  ← 等锁期间缓存可能已被填充 → 避免重复查 DB
└──────┬──────┘
       │ 二次 miss（极端罕见）
       ▼
┌─────────────┐
│ 数据库查询   │  ← 只有极少数请求到达这里
└─────────────┘
```


**总结一句话：双重判定是"等锁白等"的解决方案，分布式锁是"N 个请求一起砸 DB"的闸门，二者配合让缓存击穿场景下数据库只承受 1 次查询压力。**

### 关键误区：你忽略了"等锁期间"发生的事情

你的推理是：

### 问题的本质

| 时间点 | 请求 A | 请求 B | Redis 中有数据？ |
|--------|--------|--------|:---:|
| T1 | 第1次查缓存 → MISS | — | ❌ |
| T2 | 获得锁 | 第1次查缓存 → MISS | ❌ |
| T3 | 第2次查缓存 → MISS | **等待锁中...** | ❌ |
| T4 | 查 DB | **等待锁中...** | ❌ |
| T5 | **写缓存** ✅ | **等待锁中...** | ✅ |
| T6 | 释放锁 | **等待锁中...** | ✅ |
| T7 | — | 获得锁 | ✅ |
| T8 | — | **第2次查缓存 → HIT** 🎯 | ✅ |

**请求 B 的第1次查缓存发生在 T2**，此时 A 刚刚拿到锁，缓存里还没有数据。**B 的第2次查缓存发生在 T8**，此时 A 早已写完缓存并释放了锁。

两次查缓存之间，**世界已经变了**——这就是第二次判定存在的全部意义。

### 没有第二次判定会怎样？

```java
// 假设去掉第二次判定，获得锁后直接查 DB：
lock.lock();
try {
    // 直接查 DB，不查缓存
    ShortLinkDO shortLinkDO = baseMapper.selectOne(queryWrapper);  // 多余的 DB 查询！
    // ...
}
```


如果同时有 **100 个请求**在等同一把锁，那么：
- 有第二次判定：**1 次 DB 查询**（A 查），剩下 99 个全部命中缓存
- 没有第二次判定：**100 次 DB 查询**，每个请求获得锁后都去查一次

---

### 一句话总结

> **你假设的是"同一时刻只有一个请求在操作"，但真实情况是"多个请求串行排队操作"，两次判定之间的间隔内，缓存状态已经被排在前面的请求改变了。第二次判定就是用来感知这个变化的。**

## 也就是说第二层查缓存只是减少了可能多余的查db操作,从结果上看不影响,主要是减少db压力的是吗,我说的对吗

**完全正确，理解非常到位。**

总结一下就是：

> **第二次查缓存不影响最终结果的正确性，它唯一的目的是——让那些"排队白等了"的请求省掉一次多余的 DB 查询。**

用一句话概括：**分布式锁负责"挡"，双重判定负责"省"。**

- 锁挡住了 N-1 个请求并发砸向 DB
- 第二次判定让这 N-1 个请求排队拿到锁后，发现缓存已经有了，直接走人，**连那一次 DB 查询都省了**

所以如果只有 2 个并发请求，收益是省 1 次 DB 查询；如果有 1000 个并发请求，收益就是省 999 次 DB 查询。**并发越高，这个设计的价值越大。**

## 说一下Redisson分布式锁,为什么不用redis自带的setnx,优点在哪

---


### 一、原生 SETNX 能做什么，不能做什么？

用原生 Redis 命令实现一个"分布式锁"，你通常这样写：

**这能工作，但有大量你感知不到的坑：**

| 问题 | 原生 SETNX | Redisson |
|------|:----------:|:--------:|
| 不可重入 | ❌ 同一线程再次加锁会死锁自己 | ✅ 可重入，内部维护持有计数 |
| 锁续期 | ❌ 业务没执行完锁就过期了 | ✅ Watch Dog 自动续期（默认30秒检查一次） |
| 等待机制 | ❌ 只能自旋轮询，空耗 CPU | ✅ Redis Pub/Sub 通知唤醒，不占 CPU |
| 锁释放安全 | ❌ 容易误删别人的锁 | ✅ Lua 脚本校验持有者身份 |
| 读写锁 | ❌ 不支持 | ✅ RReadWriteLock，读读不互斥 |
| 红锁(RedLock) | ❌ 需手写复杂算法 | ✅ 内置 `getRedLock()` |

---

### 二、Watch Dog 自动续期 —— 最容易被忽略的致命问题

```
原生 SETNX 的困境：

  加锁 SET lock_key val NX EX 30
   │
   ▼
  执行业务... 第 28 秒时还没执行完 ── 锁自动过期了！
   │
   ▼
  另一个请求拿到锁 ── 两个请求同时在操作同一资源 → 数据错乱
```


Redisson 的 Watch Dog 机制：

```
  加锁（默认不设过期时间，Watch Dog 接管）
   │
   ▼
  每 10 秒自动续期到 30 秒 ──── 只要线程还活着就不停续
   │
   ▼
  业务执行完成 → 主动 unlock() → Watch Dog 停止续期
```


**你永远不用担心"业务执行太久，锁自动过期"这种灾难。**

---

### 三、Pub/Sub 唤醒 vs 自旋轮询

```
SETNX 自旋等待：
  while (!SETNX(lock_key, val)) {
      Thread.sleep(100);  // 空耗 CPU + 延迟不精确
  }

Redisson Pub/Sub：
  请求A释放锁 → 发布消息到 channel "redisson_lock__channel:{lock_key}"
  请求B 阻塞在 subscribe 上 → 收到消息 → 立即唤醒尝试加锁
```


CPU 占用降低几个数量级，响应延迟降到毫秒级。

---

### 四、项目中 RReadWriteLock 的实际体现 —— 这才是不能用 SETNX 替代的根本原因

项目里有两处使用了**同一把读写锁**（同一个 key：`LOCK_GID_UPDATE_KEY`）：

**写锁 — `ShortLinkServiceImpl.updateShortLink()`（gid 变更时）：**

```java
// Line 289-291
RReadWriteLock readWriteLock = redissonClient.getReadWriteLock(
    String.format(LOCK_GID_UPDATE_KEY, requestParam.getFullShortUrl()));
RLock rLock = readWriteLock.writeLock();  // 🔴 写锁：独占
rLock.lock();
// ... 软删除旧记录 + 重新插入 + 更新 Goto 表 ...
rLock.unlock();
```


**读锁 — `ShortLinkStatsSaveConsumer.actualSaveShortLinkStats()`（每次跳转写统计）：**

```java
// Line 128-130
RReadWriteLock readWriteLock = redissonClient.getReadWriteLock(
    String.format(LOCK_GID_UPDATE_KEY, fullShortUrl));
RLock rLock = readWriteLock.readLock();   // 🟢 读锁：共享
rLock.lock();
// ... 写入 PV/UV/UIP、浏览器、设备等 9 张统计表 ...
rLock.unlock();
```


**翻译成业务场景：**

```
场景：短链接 "abc123" 正在被疯狂点击，同时管理员修改了它的 gid

  每秒 1000+ 个点击 ────────── 统计写入（读锁）
       │                            │
       │                    ┌───────┼───────┐
       │                    ▼       ▼       ▼
       │                   读锁    读锁    读锁
       │                    │       │       │
       │                   ✅ 互不阻塞，全部并发执行
       │
  管理员修改 gid ───────── 写锁
       │                    │
       ▼                    ▼
    写锁需要等所有读锁释放 → 拿到写锁 → 独占期间：
       │                    ├── 所有新的读请求阻塞
       │                    ├── 所有新的写请求阻塞
       │                    └── 执行软删除+重新插入
       │
       └── 写锁释放 → 读锁恢复并发
```


**读写锁的精髓：**
- **读读不互斥**：每分钟上万次统计写入互不阻塞，吞吐量拉满
- **写写互斥**：gid 变更只有一个线程操作
- **读写互斥**：gid 变更期间，统计写入暂停，保证数据一致性

> 如果不用读写锁，用 SETNX 普通互斥锁，那么**每次统计写入都会互相阻塞**——高并发场景下吞吐量直接崩塌。

---

### 五、总结

| 维度 | SETNX | Redisson RLock | Redisson RReadWriteLock |
|------|:-----:|:--------------:|:-----------------------:|
| 可重入 | ❌ | ✅ | ✅ |
| 自动续期 | ❌ | ✅ | ✅ |
| Pub/Sub 唤醒 | ❌ | ✅ | ✅ |
| 读读不互斥 | — | ❌ | ✅ |
| 适用场景 | 实验/Demo | 通用互斥 | **高读低写（本项目）** |

**一句话：原生 SETNX 只给了你一把锁的骨架，Redisson 给了你锁的全套场景解决方案——尤其是读写锁，在"修改频率极低但读取极高"的短链接场景下，是 SETNX 永远无法替代的。**

## 说说细粒度是说的什么,体现在哪,为什么要说读链路优化,不说写链路优化

---

### 一、"细粒度"体现在哪？

看锁的 key：

```java
// RedisKeyConstant.java Line 44
LOCK_GID_UPDATE_KEY = "short-link:lock:update-gid:%s"
//                                                   ↑
//                                            占位符是 fullShortUrl
```


两处使用：

```java
// updateShortLink — 写锁
RReadWriteLock readWriteLock = redissonClient.getReadWriteLock(
    String.format(LOCK_GID_UPDATE_KEY, requestParam.getFullShortUrl()));
//                                     ↑ 每个短链接一把独立的锁

// ShortLinkStatsSaveConsumer — 读锁
RReadWriteLock readWriteLock = redissonClient.getReadWriteLock(
    String.format(LOCK_GID_UPDATE_KEY, fullShortUrl));
//                                     ↑ 同一个短链接共用同一把锁
```


**粗粒度 vs 细粒度的对比如下：**

```
❌ 粗粒度（如果这样设计）：
  所有短链接共享一把全局锁 "short-link:lock:update-gid:all"

  管理员修改 abc123 的 gid
      │
      ▼
  所有短链接的统计写入全部被阻塞！
  xyz789、def456 明明没被修改，也跟着等锁 → 吞吐量崩塌


✅ 细粒度（项目实际设计）：
  每个短链接独立一把锁 "short-link:lock:update-gid:abc123"

  管理员修改 abc123 的 gid
      │
      ▼
  只有 abc123 的统计写入被阻塞
  xyz789、def456 的统计写入照常并发 → 互不影响
```


**锁的粒度 = `fullShortUrl`**，也就是精确到**每一条短链接**。修改短链接 A，绝不会影响短链接 B 的访问统计。这就是"细粒度"的含义。

---

### 二、为什么说"读链路优化"，不说"写链路优化"？

先说结论：**因为这个读写锁的存在意义，90% 是为了让读链路（统计写入）不受写链路（gid 更新）的拖累，而不是反过来。**

看完整的链路分层：

```
─────────────────────────────────────────────────────────────────
  链路层级          │  操作              │  频率      │  锁情况
─────────────────────────────────────────────────────────────────
  L1 跳转热路径     │  restoreUrl        │  极高      │  无锁！
                    │  (缓存命中直接返回)  │  (99%+)    │  (纯读内存)
─────────────────────────────────────────────────────────────────
  L2 统计写入       │  读锁 readLock()   │  高        │  读读共享
                    │  (PV/UV/设备/地域) │  (每次点击)  │  互不阻塞
─────────────────────────────────────────────────────────────────
  L3 gid 变更       │  写锁 writeLock()  │  极低      │  独占
                    │  (软删除+重新插入)  │  (可能几天)  │  阻塞读锁
─────────────────────────────────────────────────────────────────
```


**所谓"读链路优化"指的就是：**

> L2 海量统计写入之间互不阻塞。一个短链接每秒被点击 1000 次，1000 次统计写入通过读锁并发执行，而不是排队串行。

如果没有读写锁，用普通互斥锁的话：

```
普通互斥锁（假设不用读写锁）：
  统计1 ── 拿锁 ── 写DB ── 放锁
                             统计2 ── 拿锁 ── 写DB ── 放锁
                                                         统计3 ── ...
  完全是串行的！1000 次点击 = 1000 次排队。
```


而有了读写锁：

```
读写锁（实际设计）：
  统计1 ── 读锁 ── 写DB ── 释放
  统计2 ── 读锁 ── 写DB ── 释放    ← 全部并发！
  统计3 ── 读锁 ── 写DB ── 释放
  ...
  统计1000 ── 读锁 ── 写DB ── 释放
```


---

### 三、那为什么不优化写链路？

**因为写链路不需要优化——它发生的频率太低了，低到优化它没有任何收益。**

|        | 读链路（统计写入）      | 写链路（gid 变更）             |
| :----- | :------------- | :---------------------- |
| 频率     | 每秒钟成千上万次       | 可能几天才一次                 |
| 耗时     | 写 9 张统计表，几十 ms | 软删除+插入+Goto 表更新，也就几十 ms |
| 瓶颈在哪里？ | **并发冲突**是瓶颈    | 操作本身是瓶颈，锁不算什么           |
| 优化方向   | 让它们**尽量不要互斥**  | 没东西可优化                  |

**写链路阻塞的那几十毫秒，对于一个几天才发生一次的操作来说，根本不痛不痒。但读链路如果被阻塞，高并发下立刻崩溃。**

---

### 四、一句话总结

> **"细粒度"是指锁精确到每条短链接，修改短链接 A 不影响短链接 B。"读链路优化"是因为读写锁的核心价值在于让海量统计写入（读锁）互不阻塞，而修改操作（写锁）频率极低，不需要优化。**
