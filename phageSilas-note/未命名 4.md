# 个人薪资险种明细完整方案改造计划

## Summary
- 在 `hrms-business-salary` 按完整方案补齐个人薪资里的 `养老保险 / 医疗保险 / 失业保险` 明细，不再把 `socialInsurance` 仅当作一个无法解释的合计值。
- 采用你刚确认的建模方式：**员工薪资档案存“各险种基数 + 各险种比例”**，工资条明细存“各险种实扣金额”，同时保留 `socialInsurance` 作为三项合计，兼容现有总额展示。
- 这次改造既覆盖薪资档案接口，也覆盖工资条详情、批次预览/管理端明细和月度核算逻辑。

## Key Changes
- 数据库与实体：
  - `hr_employee_salary_profile` 新增：
    - `pension_insurance_base`
    - `pension_insurance_rate`
    - `medical_insurance_base`
    - `medical_insurance_rate`
    - `unemployment_insurance_base`
    - `unemployment_insurance_rate`
  - `hr_salary_batch_item` 新增：
    - `pension_insurance`
    - `medical_insurance`
    - `unemployment_insurance`
  - 同步更新：
    - `EmployeeSalaryProfileEntity`
    - `SalaryBatchItemEntity`
- 薪资档案接口：
  - `EmployeeSalaryProfileRequestDTO` 新增上述 6 个档案字段，继续通过 `PUT /api/v1/salary/employees/{employeeId}/profile` 写入
  - `EmployeeSalaryProfileVO` 新增同名返回字段，`GET /api/v1/salary/employees/{employeeId}/profile` 返回完整险种配置
  - 现有 `socialInsuranceBase` 建议保留为“社保合计基数”兼容字段，值由三项基数的业务口径决定：
    - 推荐直接返回三项中主基数一致时的同值；若三项基数可不同，则不再作为权威输入字段，只保留只读兼容语义
- 工资条/批次明细接口：
  - `SalaryBatchItemVO` 新增：
    - `pensionInsurance`
    - `medicalInsurance`
    - `unemploymentInsurance`
  - `SalaryPayslipDetailVO` 继承后自动获得上述字段
  - 影响接口包括：
    - `GET /api/v1/salary/payslip/{id}`
    - `GET /api/v1/salary/manage/payslip/{id}`
    - `GET /api/v1/salary/batches/{id}/preview`
    - 管理端工资条分页如后续要展示也可直接复用这些字段，但本次不强制加到分页列表
- 核算逻辑：
  - `SalaryServiceImpl.calculateEmployeeItem(...)` 从“一个 `socialInsuranceBase * 0.08`”改为分别计算：
    - `pensionInsurance = pensionInsuranceBase * pensionInsuranceRate`
    - `medicalInsurance = medicalInsuranceBase * medicalInsuranceRate`
    - `unemploymentInsurance = unemploymentInsuranceBase * unemploymentInsuranceRate`
  - `socialInsurance = pensionInsurance + medicalInsurance + unemploymentInsurance`
  - `deductionTotal` 与 `incomeTax` 继续基于新的社保合计参与计算
  - `fillZeroSalary(...)`、人工调整重算、批次重算后明细汇总也要同步兼容新字段，避免只改首次核算、不改重算链路
- 兼容与迁移：
  - 老字段 `socialInsurance` 保留，不删除
  - 老档案字段 `socialInsuranceBase` 若当前前端仍在使用，可保留一版兼容期；但新前端应改用三项险种基数/比例字段
  - 需要提供一份 SQL 迁移脚本，为新列设置默认值，避免历史数据因空值导致核算异常
  - 历史档案无新字段时，核算默认按 `0` 处理，或在兼容期允许用旧 `socialInsuranceBase + 默认比例` 回填三项，这里推荐在迁移 SQL 中一次性初始化，避免代码长期背双口径

## Test Plan
- 编译验证：
  - `cd backend`
  - `mvn -pl hrms-business/hrms-business-salary -am -DskipTests compile`
- 数据与接口场景：
  - 更新员工薪资档案时可写入三项险种的基数和比例，再查询档案能完整回显
  - 生成新的薪资批次后，`hr_salary_batch_item` 正确写入：
    - `pension_insurance`
    - `medical_insurance`
    - `unemployment_insurance`
    - `social_insurance = 三项合计`
  - 员工端工资条详情与管理端工资条详情均返回三项险种金额
  - 批次预览接口返回三项险种金额，且 `deductionTotal/netSalary` 与新口径一致
  - 人工调整保存、批次重算后，新字段不会丢失，合计金额仍正确
  - 历史数据在完成迁移脚本后，不会因新字段为空导致工资条详情报错
- Git：
  - 推荐拆成两个接口级或能力级提交：
    - `feat(salary): 补充个人薪资险种配置字段`
    - `feat(salary): 工资条明细支持养老医疗失业保险`

## Assumptions
- 本次“个人薪资”不仅包含员工薪资档案，还包含工资条详情和批次明细中的个人扣款展示。
- 养老/医疗/失业保险均按“个人承担部分”口径存入 `hr_salary_batch_item`。
- 比例字段建议使用 `DECIMAL(5,4)` 或同等精度，传入时按小数表示，例如 `0.0800`。
- `socialInsurance` 继续作为三项社保合计字段保留，用于兼容现有前端和统计逻辑，但不再表示“养老保险”。
