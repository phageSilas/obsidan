可以用，而且这个设计在 HRMS 里挺适合包装成“高并发一致性保障方案”。不过它不是所有地方都该上，最好放在**读多、计算/初始化成本高、并发重复执行会有风险**的功能点上。

你说的“Redis 判空 + Redisson 分布式锁 + Redis 再判空”，本质是：

```
先查 Redis
  有数据：直接返回
  无数据：尝试获取 Redisson 锁
    获取锁后再次查 Redis
      有数据：说明别的线程已经构建好了，直接返回
      无数据：查数据库 / 执行业务计算 / 写 Redis
    释放锁
```

这个模式最适合解决：**缓存击穿、重复初始化、重复生成、并发计算、并发创建默认数据**。

## 考勤模块适合用的地方

### 1. 员工当天打卡状态缓存

比如员工进入打卡页时，需要查当天是否已上班打卡、是否已下班打卡、当前状态是什么。

适合使用：

```
attendance:record:daily:{employeeId}:{date}
```

场景：

- 员工频繁刷新打卡页
- 打卡页首页访问量较大
- 查询当天打卡状态读多写少
- 缓存不存在时需要查 `hr_attendance_record`

可以设计成：

```
先查 Redis 当日打卡状态
为空则加锁 attendance:record:daily:lock:{employeeId}:{date}
加锁后再查 Redis
仍为空则查数据库并写入 Redis
```

适合写进系分里的亮点：**防止上班高峰大量员工重复查询数据库导致缓存击穿**。

### 2. 员工所属考勤组解析

打卡时要判断员工属于哪个考勤组。这个逻辑可能涉及：

- 员工维度
- 部门维度
- 职位维度
- 生效日期
- 考勤组优先级

适合缓存：

```
attendance:group:employee:{employeeId}
```

使用双重判定锁很合理，因为同一个员工的考勤组解析结果短期内不会频繁变化，但打卡时会高频读取。

尤其适合：

```
员工点击打卡
查 Redis 是否已有考勤组
为空则加锁
锁内再次查 Redis
仍为空则查询考勤组成员表、员工表、部门表，计算适用考勤组
写入 Redis
```

这是考勤模块里最适合包装成高级设计的点之一。

### 3. 工作日 / 节假日配置缓存

打卡时需要判断今天是不是工作日、休息日、法定节假日。

适合缓存：

```
attendance:calendar:{groupId}:{date}
```

如果缓存为空，加锁后查库并写入。这个场景读非常多，配置变化少，非常适合 Redis 缓存 + 分布式锁。

### 4. 月度考勤统计生成防重复执行

比如 HR 手动点击“生成月度考勤统计”，或者定时任务也会触发。

这里不只是缓存击穿，而是**防重复任务执行**。

适合加 Redisson 锁：

```
attendance:stat:generate:lock:{statMonth}
```

逻辑：

```
先查 Redis / DB 判断该月统计是否已生成或锁定
未生成则加分布式锁
锁内再次判断是否已生成
仍未生成才执行统计
```

这个地方很有价值，因为月度统计是重任务，重复执行可能导致：

- 重复写入
- 统计结果覆盖
- 数据不一致
- 数据库压力大

## 薪资模块适合用的地方

### 1. 薪资批次计算防重复触发

这是薪资模块最适合用 Redisson 分布式锁的地方。

比如 HR 连续点击“开始计算”，或者多个 HR 同时操作同一个薪资批次。

锁 key：

```
salary:batch:calculate:lock:{batchId}
```

双重判定：

```
先查 Redis / DB 批次状态
如果不是 DRAFT 或 PENDING_CONFIRM，不允许计算
如果允许，则加锁
锁内再次查询批次状态
仍允许计算才执行薪资核算
```

这个点非常适合写成高级设计，因为薪资计算涉及：

- 考勤月度汇总
- 薪资档案
- 社保公积金
- 个税
- 异常检测
- 批量写入薪资明细

重复执行风险非常高。

### 2. 工资条查看二次验证结果短期缓存

员工查看工资条时需要二次验证。验证通过后可以给一个短 TTL 的 Redis 令牌。

比如：

```
salary:payslip:verify:{employeeId}:{month}
```

流程：

```
员工验证短信/密码
验证通过后写 Redis，TTL 5 分钟
查看工资条时先查 Redis 验证标记
没有则要求重新验证
```

这里不一定需要 Redisson 锁，但可以作为 Redis 安全设计亮点。

如果你一定要用双重判定锁，适合放在“工资条详情首次构建”：

```
salary:payslip:detail:{employeeId}:{month}
```

但注意工资条属于敏感数据，不建议长时间缓存明细。可以只缓存短时间摘要或验证状态。

### 3. 薪资可视化数据集生成

薪资看板图表数据可能需要聚合：

- 应发 / 实发趋势
- 部门薪资分布
- 社保公积金对比
- 薪资构成占比
- 异常数量

适合缓存：

```
salary:visualization:{batchId}
```

逻辑：

```
先查 Redis 图表数据
为空则加锁
锁内再次查 Redis
仍为空则查薪资明细聚合图表数据
写入 Redis
```

这个场景非常典型：**查询频繁、计算成本高、结果相对稳定**。

### 4. 员工薪资档案缓存

薪资核算时会批量读取员工薪资档案。

可以缓存：

```
salary:profile:{employeeId}
```

但这里要注意：薪资档案是敏感数据，缓存需要控制 TTL 和权限。更适合服务端内部核算使用，不建议前端查询链路长期缓存。

## 我最推荐你写进系分 / 简历的 3 个点

如果你想显得“高级但不乱用”，我建议重点写这三个：

1. **员工考勤组解析缓存**
    
    - Redis 缓存员工所属考勤组
    - Redisson 分布式锁防止打卡高峰缓存击穿
    - 锁内二次判空避免重复查库
2. **月度考勤统计生成幂等锁**
    
    - 使用 Redisson 按月份加锁
    - 防止定时任务和 HR 手动触发重复执行
    - Redis / DB 双重状态判定保证统计任务幂等
3. **薪资批次核算分布式锁**
    
    - 按 `batchId` 加锁
    - 防止重复点击、多人并发、定时补偿重复计算
    - 锁内再次检查批次状态，只允许合法状态进入计算

这三个点最自然，也最容易在面试里讲清楚。

## 不建议用的地方

这些地方不太适合强行上 Redisson：

- 普通分页列表查询
- 简单详情查询
- 新增 / 编辑普通表单
- 删除、启停这种低频操作
- 工资条明细长时间缓存

尤其是薪资金额类数据，能不长缓存就不长缓存，避免安全风险和一致性问题。

你可以把这个设计命名为：

> Redis 缓存空值判定 + Redisson 分布式互斥锁 + 锁内二次校验的缓存击穿防护方案。

如果写在系分里，最漂亮的落点是：**考勤组解析、考勤统计生成、薪资批次核算、薪资看板数据生成**。
