我看了一下你这份后端分析里“入转调离”的范围：**入职、转正、调岗、离职、合同到期提醒、审批超时催办**。这个模块其实特别适合接入前面讨论的 RabbitMQ 和 Redis，只是用法和考勤 / 薪资不太一样。

一句话总结：

> 入转调离模块最适合用 RabbitMQ 做“审批后异步联动”和“定时任务拆分处理”，用 Redis 做“流程状态缓存、待办数量缓存、防重复提交、分布式锁、延迟提醒辅助、组织员工数据缓存”。

下面给你按功能拆。

## 一、RabbitMQ 可以用在哪些功能

### 1. 入职审批通过后的异步后置处理

入职确认是一个典型的“主流程 + 多个后置动作”。

你的后端文档里确认入职要做：

```
更新入职申请状态
生成工号
创建系统账号
创建员工档案
发送欢迎邮件和确认通知
```

这里不建议全部同步堵在接口里。可以设计成：

```
HR 确认入职
-> 主事务更新入职申请状态、创建员工主档
-> 投递 MQ：personnel.entry.confirmed
-> 消费者异步创建账号、发送欢迎通知、初始化考勤组、初始化薪资档案提醒
```

适合消息：

```
{
  "messageId": "ENTRY_CONFIRMED_10001",
  "entryApplicationId": 10001,
  "employeeId": 20001,
  "phone": "13800000000",
  "operatorId": 1
}
```

可以异步做的动作：

- 创建系统账号
- 发送入职欢迎邮件 / 短信
- 通知 HR 完成材料归档
- 通知考勤模块刷新员工考勤组缓存
- 通知薪资模块检查是否已设置薪资档案
- 初始化个人中心数据

这个是入转调离模块最自然的 RabbitMQ 落点。

### 2. 转正审批通过后异步联动

转正通过后，员工状态从“试用期”变为“正式”。

可以发消息：

```
personnel.regular.approved
```

消费者处理：

- 更新员工状态
- 通知薪资模块使用正式薪资比例
- 删除员工薪资档案缓存
- 通知考勤 / 个人中心刷新员工简要信息
- 发送转正通知

业务价值：

```
转正流程和薪资计算解耦
避免薪资模块直接侵入转正流程
```

### 3. 调岗审批通过后异步更新关联模块

调岗是最适合异步联动的功能之一，因为它影响很多模块：

- 员工档案部门 / 岗位
- 数据权限范围
- 考勤组归属
- 薪资账套或薪资档案
- 审批链路中的上级关系
- 组织架构相关缓存

流程：

```
调岗审批通过
-> 更新调岗申请状态
-> 投递 MQ：personnel.transfer.approved
-> 消费者更新员工部门/岗位
-> 删除员工相关 Redis 缓存
-> 通知考勤模块重新解析考勤组
-> 通知薪资模块检查薪资账套是否变化
```

消息体：

```
{
  "messageId": "TRANSFER_APPROVED_30001",
  "transferApplicationId": 30001,
  "employeeId": 20001,
  "oldDeptId": 10,
  "newDeptId": 20,
  "oldPostId": 101,
  "newPostId": 202,
  "effectiveDate": "2026-07-20"
}
```

这个非常适合讲成：

> 调岗结果通过领域事件异步广播给考勤、薪资、权限等模块，实现模块解耦和最终一致性。

### 4. 离职审批通过后的异步生效处理

离职不一定审批通过立刻生效，可能有一个离职日期。

可以拆成两段：

```
离职审批通过
-> 设置员工状态为待离职
-> 投递 MQ：personnel.leave.approved
-> 到达离职日期时，定时任务 / 延迟消息触发生效
-> 投递 MQ：personnel.leave.effective
```

离职生效后异步处理：

- 禁用系统账号
- 员工状态改为已离职
- 回收权限角色
- 删除登录 token
- 从考勤组成员缓存移除
- 停止后续薪资批次纳入
- 生成离职交接提醒
- 发通知给 HR / 主管 / 财务

消息：

```
{
  "messageId": "LEAVE_EFFECTIVE_40001",
  "leaveApplicationId": 40001,
  "employeeId": 20001,
  "leaveDate": "2026-07-31",
  "operatorId": 1
}
```

这个点很强，因为离职是典型的跨模块联动场景。

### 5. 待转正提醒异步通知

后端分析里有：

```
待转正提醒：每日 02:00 扫描试用期员工，到期前 7 天提醒 HR
```

可以这样做：

```
定时任务扫描待转正员工
-> 每个员工投递 MQ：personnel.regular.remind
-> 消费者发送站内信/邮件/待办
```

好处：

- 扫描和通知解耦
- 通知失败可重试
- 不阻塞定时任务
- 可记录通知日志

### 6. 合同到期提醒

合同到期提醒和待转正提醒类似。

```
每日扫描近 30 天到期合同
-> 投递 MQ：personnel.contract.expire.remind
-> 通知 HR / 员工 / 主管
```

消息：

```
{
  "messageId": "CONTRACT_EXPIRE_20001_20260731",
  "employeeId": 20001,
  "contractExpireDate": "2026-07-31",
  "daysLeft": 18
}
```

### 7. 审批超时催办与升级

后端文档里也有：

```
审批超时催办与升级：每小时扫描，超时 48h 催办，超时 72h 自动升级
```

RabbitMQ 可以用来异步处理催办：

```
定时任务扫描超时审批
-> 投递 MQ：approval.timeout.remind
-> 消费者发送催办通知
```

升级也可以投递：

```
approval.timeout.escalate
```

虽然这是审批中心相关，但入转调离是主要使用方之一。

## 二、Redis 可以用在哪些功能

不算 Stream 和 Pub/Sub，入转调离模块还能用不少 Redis 能力。

### 1. 流程详情缓存

入转调离的申请详情会被频繁查看：

- HR 看申请详情
- 员工看流程进度
- 主管审批时看详情
- 审批中心待办进入详情

可以缓存：

```
personnel:entry:detail:{applicationId}
personnel:regular:detail:{applicationId}
personnel:transfer:detail:{applicationId}
personnel:leave:detail:{applicationId}
```

适合缓存内容：

- 申请基础信息
- 申请人信息
- 当前审批状态
- 关键字段快照
- 审批实例 ID

状态变化时删除缓存：

- 提交审批
- 审批通过 / 拒绝
- 确认入职
- 离职生效
- 调岗生效

### 2. 待办数量缓存

首页和个人中心经常要展示：

```
我的待审批数量
我的入转调离申请数量
待转正员工数量
待离职员工数量
```

可以缓存：

```
personnel:todo:count:{userId}
approval:pending:count:{userId}
personnel:regular:pending:count
personnel:leave:pending:count
```

这个能明显减少数据库 count 查询压力。

审批动作发生后删除或刷新：

```
审批通过 / 驳回
提交新申请
转交审批人
审批超时升级
```

### 3. 防重复提交 Token

入职、转正、调岗、离职申请都适合用 Redis 防重复提交。

比如：

```
submit:token:personnel:entry:{userId}
submit:token:personnel:transfer:{userId}
submit:token:personnel:leave:{userId}
```

流程：

```
进入表单页 -> 后端生成 submitToken 写 Redis
提交表单 -> 校验并删除 token
重复提交 -> token 不存在，拒绝
```

适合：

- 创建入职申请
- 提交入职审批
- 发起转正
- 创建调岗申请
- 创建离职申请
- 确认入职

这个实现简单，效果很实在。

### 4. Redisson 分布式锁：确认入职

确认入职最适合加分布式锁。

原因：

- 会生成工号
- 会创建员工档案
- 会创建系统账号
- 重复点击风险高
- 并发执行会导致脏数据

锁 key：

```
lock:personnel:entry:confirm:{entryApplicationId}
```

逻辑：

```
确认入职前先查状态是否已通过
加锁
锁内再次查状态
如果已经已入职，直接返回
否则生成工号、创建档案、创建账号
更新状态为已入职
释放锁
```

再配合数据库唯一索引：

```
employee_no 唯一
phone/account 唯一
entry_application_id 唯一关联
```

这个点非常值得写进系分。

### 5. Redisson 分布式锁：调岗 / 离职 / 转正生效

这些状态流转也适合锁。

```
lock:personnel:regular:apply:{employeeId}
lock:personnel:transfer:effect:{transferApplicationId}
lock:personnel:leave:effect:{leaveApplicationId}
```

避免：

- 重复发起转正申请
- 同一员工同时调岗
- 离职生效任务重复执行
- 审批回调重复处理

### 6. 员工简要信息缓存

入转调离大量依赖员工信息：

- 发起调岗时选员工
- 发起离职时查员工
- 流程详情展示员工姓名、部门、岗位
- 审批列表展示申请人信息

可以缓存：

```
employee:brief:{employeeId}
```

内容：

```
{
  "employeeId": 1001,
  "employeeName": "张三",
  "employeeNo": "2026BE005",
  "deptId": 10,
  "deptName": "技术部",
  "postId": 20,
  "postName": "后端工程师",
  "employmentStatus": 1
}
```

调岗、转正、离职、档案更新后删除缓存。

### 7. 部门树 / 岗位字典缓存

入转调离表单大量使用：

- 部门选择
- 岗位选择
- 职级选择
- 入职类型
- 离职原因
- 审批状态

可以缓存：

```
dept:tree
post:list:{deptId}
dict:personnel:entry_status
dict:personnel:leave_reason
dict:employment_status
```

这是管理系统里非常常见、也很合理的 Redis 缓存点。

### 8. Set：待转正员工集合

每日扫描待转正员工时，可以用 Set 或 ZSet 辅助。

Set 简单版：

```
personnel:regular:pending:{yyyyMMdd}
```

存员工 ID。

更推荐 ZSet，因为可以按转正日期排序。

```
personnel:regular:zset
score = probationEndDate 时间戳
member = employeeId
```

查询 7 天内待转正：

```
ZRANGEBYSCORE personnel:regular:zset now now+7days
```

当员工入职时加入 ZSet，转正通过后移除。

这个比每天扫全表高级很多。

### 9. ZSet：离职生效队列

离职生效也非常适合 ZSet。

```
personnel:leave:effective:zset
score = leaveDate 时间戳
member = leaveApplicationId
```

每日定时任务只查到期数据：

```
ZRANGEBYSCORE personnel:leave:effective:zset 0 now
```

处理成功后移除：

```
ZREM personnel:leave:effective:zset leaveApplicationId
```

适合替代“每天全表扫描待离职员工”。

### 10. ZSet：合同到期提醒

合同到期提醒也可以用 ZSet：

```
personnel:contract:expire:zset
score = contractExpireDate 时间戳
member = employeeId
```

查 30 天内到期：

```
ZRANGEBYSCORE personnel:contract:expire:zset now now+30days
```

入职创建合同、合同续签、离职时更新或移除。

这个点特别适合入转调离，因为它就是员工生命周期管理。

### 11. Bitmap：流程办理日历 / 入离职统计

Bitmap 在入转调离里没考勤那么核心，但可以用于统计类功能。

比如统计某天是否有人入职：

```
personnel:bitmap:entry:{yyyyMM}
```

某天有入职：

```
SETBIT personnel:bitmap:entry:202607 12 1
```

但这个只能表示“当天是否有”，不能表示人数。更适合做快速判断，不是核心。

如果要统计人数，ZSet / Hash / DB 更合适。

### 12. Redis 幂等状态标记

审批回调和 MQ 消费都适合你前面那套：

```
idempotent:personnel:approval-callback:{approvalInstanceId}
idempotent:personnel:entry-confirm:{entryApplicationId}
idempotent:personnel:leave-effective:{leaveApplicationId}
```

value：

```
0 = 处理中
1 = 已完成
```

用于防止：

- 审批中心重复回调
- MQ 重复投递
- 定时任务重复执行
- 用户重复点击确认入职

## 三、三个模块之间的联动点

你现在负责：

```
4 入转调离
5 考勤管理
6 薪资管理
```

这三个模块之间其实可以设计一套很漂亮的“员工生命周期事件流”。

### 入职确认后

RabbitMQ：

```
personnel.entry.confirmed
```

影响：

```
员工档案：创建员工
考勤模块：初始化考勤组缓存 / 工作日状态
薪资模块：提示 HR 设置薪资档案
权限模块：创建账号并分配角色
```

Redis：

```
删除 dept / employee brief 缓存
写入 employee:brief:{employeeId}
```

### 转正通过后

RabbitMQ：

```
personnel.regular.approved
```

影响：

```
薪资模块：试用期比例失效，后续按正式工资计算
员工档案：状态改为正式
个人中心：刷新员工状态
```

Redis：

```
DEL employee:brief:{employeeId}
DEL salary:profile:{employeeId}
```

### 调岗生效后

RabbitMQ：

```
personnel.transfer.effective
```

影响：

```
考勤模块：重新解析考勤组
薪资模块：重新判断薪资账套
权限模块：刷新数据权限
审批模块：更新直属上级链路
```

Redis：

```
DEL employee:brief:{employeeId}
DEL attendance:employee:group:{employeeId}
DEL salary:profile:{employeeId}
DEL data-scope:{userId}
```

### 离职生效后

RabbitMQ：

```
personnel.leave.effective
```

影响：

```
权限模块：禁用账号，清理登录态
考勤模块：移出考勤组，不再参与统计
薪资模块：停止纳入后续批次
个人中心：隐藏部分操作入口
```

Redis：

```
DEL employee:brief:{employeeId}
DEL attendance:employee:group:{employeeId}
DEL salary:profile:{employeeId}
DEL login:token:{userId}
```

## 四、我最推荐你写进设计里的点

如果你要把“入转调离”包装得高级，但实现又不难，我建议选这几个：

### RabbitMQ

```
1. 入职确认后异步创建账号、发送通知、初始化关联模块数据
2. 调岗审批通过后异步刷新考勤组、薪资账套和数据权限缓存
3. 离职生效后异步禁用账号、清理缓存、通知考勤和薪资模块
4. 待转正 / 合同到期提醒通过 MQ 异步发送通知
5. 审批回调消息使用 messageId + Redis SETNX + 消费日志保证幂等
```

### Redis

```
1. Redisson 锁保证确认入职、离职生效、调岗生效不重复执行
2. ZSet 维护待转正员工、待离职员工、合同到期提醒队列
3. Redis 缓存员工简要信息、部门树、岗位字典、流程详情和待办数量
4. Redis submitToken 防止入职、调岗、离职、转正申请重复提交
5. Redis 幂等状态标记防止审批回调和 MQ 消息重复消费
```


最值得你重点讲的其实是这条主线：

> 入转调离是员工生命周期源头，它通过 MQ 发布入职、转正、调岗、离职事件，考勤和薪资模块订阅事件刷新自己的规则缓存、统计范围和薪资档案，从而形成模块解耦和最终一致性。
