可以，而且你这两个模块里**能合理用 Redis 缓存减少 MySQL 压力的点很多**。但要注意：薪资模块涉敏金额数据多，不适合什么都缓存；考勤模块读多、规则类数据多，更适合大胆用 Redis。

下面按模块说。

## 考勤模块

### 1. 员工所属考勤组缓存

这是考勤模块最值得缓存的点。

打卡时需要判断员工属于哪个考勤组，可能要查：

- 员工表
- 部门表
- 职位表
- 考勤组成员表
- 考勤组规则表

缓存 key：

```
attendance:employee:group:{employeeId}
```

适合场景：

- 员工每天进入打卡页
- 上下班高峰并发高
- 考勤组配置变化低频

缓存内容：

```
{
  "groupId": 1,
  "groupName": "标准工时组",
  "shiftType": "FIXED",
  "workStartTime": "09:00",
  "workEndTime": "18:00"
}
```

### 2. 考勤组规则缓存

考勤组规则是典型读多写少数据。

缓存 key：

```
attendance:group:rule:{groupId}
```

缓存内容：

- 上班时间
- 下班时间
- 午休时间
- 弹性时间
- 迟到阈值
- 早退阈值
- IP 白名单
- GPS 范围
- 每月补卡上限

用处：

- 打卡校验
- 补卡次数判断
- 工作日判断
- 考勤统计

### 3. 工作日 / 节假日配置缓存

每天打卡都要判断当天是否工作日。

缓存 key：

```
attendance:calendar:{groupId}:{date}
```

或者按月缓存：

```
attendance:calendar:{groupId}:{yyyyMM}
```

按月缓存更省查询：

```
{
  "2026-07-01": "WORKDAY",
  "2026-07-04": "REST_DAY",
  "2026-07-05": "HOLIDAY"
}
```

适合场景：

- 打卡页初始化
- 打卡提交校验
- 月度考勤统计

### 4. 员工当天打卡状态缓存

员工进入打卡页时要展示今天是否已打上班卡、下班卡。

缓存 key：

```
attendance:daily:record:{employeeId}:{date}
```

缓存内容：

```
{
  "clockInTime": "2026-07-11 09:02:11",
  "clockInStatus": "LATE",
  "clockOutTime": null,
  "clockOutStatus": null
}
```

适合场景：

- 打卡页频繁刷新
- 前端实时展示当天状态
- 上下班高峰减少 MySQL 查询

打卡成功后要主动更新或删除这个缓存。

### 5. 个人月度打卡日历缓存

个人考勤日历按月查询，读多写少。

缓存 key：

```
attendance:calendar:personal:{employeeId}:{yyyyMM}
```

适合场景：

- 员工查看“我的考勤”
- 切换月份
- 移动端或前端频繁加载

注意：

- 员工打卡后删除当月缓存
- 补卡审批通过后删除当月缓存
- 请假审批通过后删除当月缓存

### 6. 请假类型缓存

请假类型配置变化很少。

缓存 key：

```
leave:types:enabled
```

适合场景：

- 请假申请页加载
- 请假记录筛选
- 审批详情展示

### 7. 假期余额缓存

这个可以缓存，但要谨慎，因为余额会变化。

缓存 key：

```
leave:balance:{employeeId}:{year}
```

适合场景：

- 请假申请页展示余额
- 员工查看假期余额

注意：

- 请假提交预扣减后要更新或删除缓存
- 审批通过 / 拒绝 / 撤回后要更新或删除缓存
- 最好 TTL 短一点，比如 5-30 分钟

### 8. 月度考勤统计结果缓存

统计结果适合缓存。

缓存 key：

```
attendance:month:stat:{employeeId}:{yyyyMM}
attendance:month:stat:dept:{deptId}:{yyyyMM}
```

适合场景：

- 个人统计页
- 部门统计页
- 薪资模块读取考勤汇总前的高频查询
- 可视化看板

统计生成后写入缓存；补卡 / 请假影响历史月份时删除或重算缓存。

### 9. 考勤可视化数据缓存

AntV 图表数据聚合成本高，很适合缓存。

缓存 key：

```
attendance:visualization:{deptId}:{yyyyMM}
```

缓存内容：

- 部门出勤率趋势
- 迟到早退柱状图
- 请假类型占比
- 日历热力图

## 薪资模块

薪资模块能缓存，但要克制。**规则、配置、聚合结果可以缓存；员工个人薪资明细慎重缓存。**

### 1. 薪资账套缓存

薪资账套配置读多写少，很适合缓存。

缓存 key：

```
salary:template:{templateId}
```

缓存内容：

- 账套名称
- 适用范围
- 生效日期
- 状态
- 工资项目列表

用处：

- 员工薪资档案设置
- 薪资批次核算
- 工资条项目展示

账套编辑、启停、删除后删除缓存。

### 2. 工资项目缓存

也可以和账套一起缓存，或者单独缓存。

缓存 key：

```
salary:template:items:{templateId}
```

适合场景：

- 薪资计算引擎读取工资项目
- 工资条按项目排序展示
- 薪资模板编辑页回显

### 3. 员工薪资档案缓存

可以缓存，但建议只用于服务端内部核算，不建议长 TTL。

缓存 key：

```
salary:profile:{employeeId}
```

适合场景：

- 薪资批次核算时批量读取员工薪资档案
- 试用期薪资计算
- 社保公积金计算

注意：

- 涉及敏感金额
- TTL 要短
- 调薪后必须删除缓存
- 不建议前端直接依赖这个缓存

### 4. 未设置薪资档案员工列表缓存

这个很适合缓存。

缓存 key：

```
salary:missing-profile:{scopeType}:{scopeValue}
```

适合场景：

- 创建薪资批次前阻断检查
- HR 查看未设置档案员工

员工薪资档案新增或更新后删除相关缓存。

### 5. 薪资批次详情缓存

批次详情查询频繁，状态变化有限，可以短期缓存。

缓存 key：

```
salary:batch:detail:{batchId}
```

缓存内容：

- 批次编号
- 月份
- 状态
- 总人数
- 应发总额
- 实发总额
- 异常汇总

注意：

批次状态变化时必须删除或刷新：

- 开始计算
- 计算完成
- 提交审批
- 审批通过 / 驳回
- 确认发放

### 6. 薪资预览分页缓存

这个可缓存但要谨慎。

缓存 key：

```
salary:batch:preview:{batchId}:{pageNum}:{pageSize}:{filterHash}
```

适合场景：

- HR 反复查看薪资预览列表
- 财务审批前查看批次明细

注意：

- 手动调整薪资明细后必须删除该批次预览缓存
- 涉敏金额，TTL 要短，比如 1-5 分钟
- 权限不同缓存 key 要带角色或用户维度

### 7. 薪资异常列表缓存

异常列表适合短期缓存。

缓存 key：

```
salary:batch:exceptions:{batchId}:{filterHash}
```

适合场景：

- HR 查看异常员工
- 批次详情页展示异常汇总
- 提交审批前检查阻断异常

异常处理后删除缓存。

### 8. 薪资可视化数据缓存

这是薪资模块最适合缓存的点之一。

缓存 key：

```
salary:visualization:{batchId}
```

缓存内容：

- 薪资成本趋势
- 部门薪资分布
- 薪资构成占比
- 薪资变动分布
- 异常汇总

适合场景：

- HR 看板
- 财务看板
- 批次详情图表

计算完成或确认发放后生成缓存。

### 9. 工资条验证状态缓存

工资条二次验证通过后，可以缓存一个短期令牌。

缓存 key：

```
salary:payslip:verify:{employeeId}:{month}
```

TTL：

```
5 分钟
```

适合场景：

- 员工二次验证通过后查看工资条
- 短时间刷新页面不用重复验证

注意：

- 缓存验证状态，不缓存密码或验证码
- 不建议长时间缓存工资条明细

### 10. 工资条详情缓存

这个我不太建议长时间缓存，但可以短 TTL。

缓存 key：

```
salary:payslip:detail:{employeeId}:{month}
```

适合场景：

- 员工验证后短时间重复查看
- 减少工资条详情查询压力

注意：

- TTL 建议 1-5 分钟
- 必须带员工 ID
- 工资条不可见时不能缓存明细
- 员工退出或验证状态失效后不能继续访问

## 最推荐你写进设计里的缓存点

如果想显得高级又合理，我建议选这些：

### 考勤模块

```
1. 员工所属考勤组缓存
2. 考勤组规则缓存
3. 工作日 / 节假日配置缓存
4. 员工当天打卡状态缓存
5. 月度考勤统计与可视化数据缓存
```

### 薪资模块

```
1. 薪资账套和工资项目缓存
2. 薪资批次详情缓存
3. 薪资异常列表短期缓存
4. 薪资可视化数据缓存
5. 工资条二次验证状态缓存
```

## 可以在系分里这么写

```
为降低 MySQL 在高频读取和复杂聚合场景下的压力，考勤与薪资模块引入 Redis 缓存。

考勤模块重点缓存员工所属考勤组、考勤组规则、工作日配置、当日打卡状态、月度考勤统计和可视化数据。打卡成功、补卡审批通过、请假审批通过后主动删除或刷新相关缓存，保证数据最终一致。

薪资模块重点缓存薪资账套、工资项目、批次摘要、异常汇总、薪资看板数据和工资条二次验证状态。涉薪明细类数据仅允许短 TTL 缓存，并按用户、角色和权限维度隔离缓存 key，避免敏感数据串读。
```

一句话总结：**考勤缓存偏业务规则和状态，薪资缓存偏配置、批次摘要和图表聚合，涉薪个人明细要短 TTL、强权限、慎缓存。**
