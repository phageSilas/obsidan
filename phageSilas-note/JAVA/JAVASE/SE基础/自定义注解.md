在 Java 中自定义注解非常简单，核心就是使用 `@interface` 关键字，并结合**元注解**来限定它的作用范围和行为。
## 介绍
### 第一步：定义注解（使用 @interface）

假设我们要定义一个用于**标记接口是否需要记录日志**的注解 `@Loggable`：

```java
import java.lang.annotation.*;

// 1. 元注解：定义作用目标（这里指只能用在类上）
@Target(ElementType.TYPE)
// 2. 元注解：定义生命周期（这里指运行时保留，以便反射读取）
@Retention(RetentionPolicy.RUNTIME)
// 3. 元注解：让该注解包含在 Javadoc 中（可选）
@Documented
public @interface Loggable {
    // 4. 定义属性（注意：这里看起来像方法，实际上是属性）
    String value() default ""; // 默认值为空字符串

    int level() default 1;     // 默认级别为 1
}
```

---

### 第二步：认识关键的元注解（必须掌握）

在定义时，最常用的是以下三个元注解：

-   **`@Target`**：限制注解可以贴在哪里。
    -   `ElementType.TYPE`（类/接口）
    -   `ElementType.METHOD`（方法）
    -   `ElementType.FIELD`（字段）
    -   `ElementType.PARAMETER`（参数）
    -   支持多个：`@Target({ElementType.METHOD, ElementType.TYPE})`
-   **`@Retention`**：限制注解保留到什么时候（**重要**）。
    -   `RetentionPolicy.SOURCE`：仅源码阶段（如 `@Override`），编译后丢失。
    -   `RetentionPolicy.CLASS`：编译时保留，JVM 加载时丢失（默认）。
    -   `RetentionPolicy.RUNTIME`：**运行时保留**，可以通过反射读取（**90% 的自定义注解都用这个**）。
-   **`@Documented`**：生成 API 文档时是否包含该注解。

---

### 第三步：注解属性的数据类型

注解支持的数据类型有限，必须是以下几种：

1.  基本类型（`int`, `double`, `boolean` 等）
2.  `String`
3.  `Class` 类型（如 `Class<?>`）
4.  枚举（`Enum`）
5.  其他注解
6.  以上类型的**数组**（例如 `String[] names()`）

> **注意**：属性可以有默认值（使用 `default` 关键字），也可以没有默认值（使用时必须赋值）。如果属性名为 `value` 且只有一个属性，使用时可以省略 `value=`。
> 
> 1. **不要在这个属性定义里加参数**：写成 `String message(String str)` 会直接报语法错误，注解属性不能有参数。
> 2.  **默认值必须是常量**：不能是 `new String(...)` 或调用方法，只能是字面量、枚举常量或 Class 常量。
> 3.  **空字符串作为默认值**：如果你想表示“没有默认消息”，通常写 `default ""`，然后在解析时判断 `isEmpty()`。


---

### 第四步：使用注解

将注解贴到目标类上：

```java
// 使用了 value 属性，level 采用默认值 1
@Loggable(value = "UserService", level = 2)
public class UserService {
    // 业务逻辑...
}

// 如果只有一个 value 属性，可以简写为 @Loggable("UserService")
```

### 第五步: 自定义注解结合 AOP（Spring 常用）

在 Spring Boot 项目中，你通常不会手动写反射代码，而是结合 **AOP（面向切面编程）** 使用。

1.  **定义注解**（同上）。
2.  **编写切面类**，使用 `@Around` 环绕通知，通过 `joinPoint.getSignature()` 获取方法上的注解，实现无侵入式的权限校验、日志打印或接口限流。
3. 自定义注解中的参数通常需要在AOP中配置对应的使用逻辑

示例:
1.创建注解@IdempotentSubmit
``` java
/**  
 * 幂等注解，防止用户重复提交表单信息  
 */  
@Target(ElementType.METHOD) // 元注解表示该注解只能用于方法  
@Retention(RetentionPolicy.RUNTIME) // 表示该注解在运行时仍然有效 
public @interface IdempotentSubmit {  
  
    /**  
     * 通过 SpEL 表达式生成的唯一 Key，优先级高于默认幂等逻辑  
     */  
    String key() default "";  
  
    /**  
     * 触发幂等失败逻辑时，返回的错误提示信息  
     */  
    String message() default "您操作太快，请稍后再试";  
}
```
2.在AOP中配置注解@IdempotentSubmit的使用逻辑
``` java
@Aspect  
@Component  
@RequiredArgsConstructor  
public final class IdempotentConsumeAspect {  
  
    private final StringRedisTemplate stringRedisTemplate;  
  
    private static final String LUA_SCRIPT = """   
   local key = KEYS[1]            
   local value = ARGV[1]            
   local expire_time_ms = ARGV[2]            
   return redis.call('SET', key, value, 'NX', 'GET', 'PX', expire_time_ms)            
   """;  
  
 /**  
  * 增强方法标记 {@link IdempotentConsume} 注解逻辑  
  */  
    @Around("@annotation(com.nageoffer.ai.ragent.framework.idempotent.IdempotentConsume)")  
    public Object idempotentConsume(ProceedingJoinPoint joinPoint) throws Throwable {  
        IdempotentConsume idempotentConsume = getIdempotentConsumeAnnotation(joinPoint);  
        String uniqueKey = idempotentConsume.keyPrefix()  
                + SpELUtil.parseKey(idempotentConsume.key(), ((MethodSignature) joinPoint.getSignature()).getMethod(), joinPoint.getArgs());  
        long keyTimeoutSeconds = idempotentConsume.keyTimeout();  
  
        String absentAndGet = stringRedisTemplate.execute(  
                RedisScript.of(LUA_SCRIPT, String.class),  
                List.of(uniqueKey),  
                IdempotentConsumeStatusEnum.CONSUMING.getCode(),  
                String.valueOf(TimeUnit.SECONDS.toMillis(keyTimeoutSeconds))  
        );  
  
        // 如果已有消费中状态，提示延迟消费；已完成则直接跳过  
        boolean errorFlag = IdempotentConsumeStatusEnum.isError(absentAndGet);  
        if (errorFlag) {  
            log.warn("[{}] MQ repeated consumption, wait for delayed retry.", uniqueKey);  
            throw new ServiceException(String.format("消息消费者幂等异常，幂等标识：%s", uniqueKey));  
        }  
        if (IdempotentConsumeStatusEnum.CONSUMED.getCode().equals(absentAndGet)) {  
            log.info("[{}] MQ consumption already completed, skip.", uniqueKey);  
            return null;  
        }  
  
        try {  
            Object result = joinPoint.proceed();  
            stringRedisTemplate.opsForValue().set(  
                    uniqueKey,  
                    IdempotentConsumeStatusEnum.CONSUMED.getCode(),  
                    keyTimeoutSeconds,  
                    TimeUnit.SECONDS  
            );  
            return result;  
        } catch (Throwable ex) {  
            stringRedisTemplate.delete(uniqueKey);  
            throw ex;  
        }  
    }  
  
    /**  
     * @return 返回自定义防重复消费注解  
     */  
    public static IdempotentConsume getIdempotentConsumeAnnotation(ProceedingJoinPoint joinPoint) throws NoSuchMethodException {  
        MethodSignature methodSignature = (MethodSignature) joinPoint.getSignature();  
        Method targetMethod = joinPoint.getTarget().getClass().getDeclaredMethod(methodSignature.getName(), methodSignature.getMethod().getParameterTypes());  
        return targetMethod.getAnnotation(IdempotentConsume.class);  
    }  
}
```

### 第五步：通过反射解析注解（核心逻辑）

如果不写代码去读取，注解本身不会产生任何作用。我们通过 **Java 反射机制** 来获取注解信息并执行逻辑：

```java
import java.lang.reflect.AnnotatedElement;

public class AnnotationProcessor {
    public static void main(String[] args) {
        // 获取 UserService 的 Class 对象
        Class<UserService> clazz = UserService.class;
        
        // 判断该类是否贴了 Loggable 注解
        if (clazz.isAnnotationPresent(Loggable.class)) {
            // 获取注解实例（本质上是 JVM 生成的动态代理对象）
            Loggable loggable = clazz.getAnnotation(Loggable.class);
            
            // 读取属性值并执行逻辑
            String module = loggable.value();
            int level = loggable.level();
            
            System.out.println("正在记录日志: 模块=" + module + ", 级别=" + level);
            // 这里可以真正调用 Log4j 或 SLF4J 打印日志
        }
    }
}
// 输出结果：正在记录日志: 模块=UserService, 级别=2
```

### 避坑指南（重点提醒）

1.  **Retention 忘了写**：默认是 `CLASS`，如果你用反射 `getAnnotation` 去拿，拿到的会是 `null`。**一定要检查是否写了 `@Retention(RetentionPolicy.RUNTIME)`**。
2.  **Target 限制不匹配**：如果你把注解定义成只能用在 `METHOD` 上，却贴在了类上，编译时会直接报错。
3.  **注解不能继承**：注解本身不支持 `extends`，但可以利用 `@Inherited` 元注解让子类继承父类的注解（仅限于类上的注解，方法上的不继承）。

## 以你说的@RateLimiter为例,编译器是怎么知道"maxCount"意味着"最大次数","timeUnit"意味着"时间窗口,并且单位还是秒"
这个问题问得非常犀利，直接戳中了**“语义”与“语法”**的根本区别。

**编译器（javac）和 Spring 框架，根本不认识“maxCount”这个英文单词，更不知道“timeUnit”代表秒！**

它们只是**“盲人摸象”** ，机械地读取数据。**“最大次数”、“时间窗口”这些含义，完全是由你（开发者）在切面类里用 Java 代码“硬编码”赋予的。**

---

### 1. 编译器（javac）眼里看到的是什么？

当编译器扫描到 `@RateLimiter(maxCount = 5, timeUnit = 60)` 时，它脑子里只有极其机械的语法检查：

1. **检查语法**：`maxCount` 和 `timeUnit` 是不是这个注解里定义好的属性名？是 -> 通过。
2. **检查类型**：赋值的 `5` 是不是 `int` 类型？`60` 是不是 `int` 类型？是 -> 通过。
3. **存储数据**：把这组键值对 `{ "maxCount": 5, "timeUnit": 60 }` 打包塞进 `.class` 字节码的元数据区。

**编译器完全不知道“max”是“最大”，“unit”是“单位”**。对它来说，`maxCount` 和 `abc`、`x1` 没有任何区别，只要符合变量命名规则就行。

---

### 2. Spring（框架）眼里看到的是什么？

Spring 启动时通过反射读取注解，它只做了两件事：

1. 调用 `rateLimiter.maxCount()` 获取到数字 `5`。
2. 调用 `rateLimiter.timeUnit()` 获取到数字 `60`。

至于这两个数字叫什么名字、代表什么物理意义，**Spring 根本不关心**，它只是把这两个数字原封不动地作为参数，丢给你写的切面方法。

---

### 3. 真正“懂得”含义的地方：你写的 AOP 切面代码

**“最大次数”、“时间窗口（秒）”** 这些概念，只存在于 **你自己写的 .java 业务逻辑代码** 里！

假设你的切面类是这样写的（这才是决定含义的关键）：

```java
@Around("@annotation(rateLimiter)")
public Object check(ProceedingJoinPoint pjp, RateLimiter rateLimiter) throws Throwable {
    // 1. 【赋予含义的地方】你通过变量名 maxCount，告诉程序：这个数字代表“最大限制”
    int maxCount = rateLimiter.maxCount(); 
    
    // 2. 【赋予含义的地方】你通过变量名 timeWindow，告诉程序：这个数字代表“秒数”
    int timeWindow = rateLimiter.timeUnit(); 
    
    // 3. 真正执行业务逻辑（硬编码的规则）
    String key = "rate_limit:" + pjp.getSignature().toLongString();
    Long currentCount = redisTemplate.opsForValue().increment(key);
    
    // 如果是第一次访问，设置过期时间
    if (currentCount == 1) {
        // 【关键】你在这里把 timeWindow 当成了“秒”，传给 Redis 的过期时间 API
        redisTemplate.expire(key, timeWindow, TimeUnit.SECONDS); 
    }
    
    // 【关键】你在这里把 maxCount 当成“最大次数”去比较
    if (currentCount > maxCount) { 
        throw new BusinessException(rateLimiter.message());
    }
    
    return pjp.proceed();
}
```

---

### 4. 用“外卖”的例子帮你彻底形象化

-   **注解定义（`int maxCount()`）**：好比外卖 APP 上有一个**输入框**，名字叫“辣度”。
-   **你使用注解（`@RateLimiter(maxCount = 5)`）**：你在输入框里填了数字 **`5`**。
-   **编译器的工作**：APP 前端只负责检查你填的是不是纯数字（类型检查），然后把数字 `5` 传给后台。
-   **切面代码的工作（赋予含义）**：后厨的厨师（你写的 Java 代码）看到数字 `5`，**厨师心里知道**：“这个输入框虽然叫‘辣度’，但我们店是指‘放 5 个辣椒’。” 于是厨师往锅里丢了 5 个辣椒（`redis.expire(..., 5, SECONDS)`）。

---

### 5. 终极结论（请刻在脑子里）

-   **属性名（`maxCount`）**：只是**给程序员（你）看的注释**，方便你写代码时知道这个参数是干嘛用的。编译器视其为无意义的字符串 `String` 标识符。
-   **属性值（`5`）**：是**传进处理程序的裸数据**。
-   **处理程序（AOP 切面）**：是**唯一拥有“解释权”的地方**。你在切面里写 `if (count > maxCount)`，`maxCount` 才变成了“最大次数”；你在切面里写 `expire(key, timeUnit, SECONDS)`，`timeUnit` 才变成了“秒数”。

**如果你高兴**，你完全可以把注解定义成 `int a();`，使用时写 `@RateLimiter(a = 5)`，然后在切面里写 `if (count > a)`，程序照样完美运行。虽然代码可读性极差，但功能一模一样。

## 所以使用注解,还得写一个专门的aop@Aspect切面类么
**答案是：不一定非得用 `@Aspect`，但绝大多数业务场景下，用它是最标准、最省事的做法。**

注解就像一把“锁”，而 `@Aspect` 切面只是其中一种“开锁工具”。根据你想做的事情不同，Java 和 Spring 还提供了至少 **4 种不同的“开锁方式”**。

下面我把这 4 种方式列出来，你一看就明白什么时候必须用 AOP，什么时候不用。

---

### 方式一：运行时 AOP（`@Aspect`）—— **你的首选（90% 的场景）**

这就是你刚才提到的 `@Aspect` 切面类。利用 Spring 的动态代理，在方法执行前后“插一脚”。

- **适用场景**：**限流**、**日志记录**、**权限校验**（`@PreAuthorize`）、**事务管理**（`@Transactional`）、**接口耗时统计**。
- **为什么选它**：**无侵入性**。你只需要在方法上贴个标签，业务代码（Service 里的查数据库逻辑）完全干净整洁，不需要写任何 `if...else`。
- **代价**：底层有动态代理开销（虽然微乎其微），且只能作用于 Spring 容器管理的 Bean（Service/Controller）。

---

### 方式二：手动调用反射（`method.getAnnotation()`）—— **不用 AOP**

你完全可以不用 Spring AOP，直接在业务代码里手动读取注解。

```java
// 在你自己的业务方法里硬编码
public void doSubmit() {
    // 手动获取当前方法的注解
    Method method = this.getClass().getMethod("doSubmit");
    RateLimiter anno = method.getAnnotation(RateLimiter.class);
    
    if (anno != null) {
        int max = anno.maxCount(); // 拿到数据
        // 手动执行 if 判断，手动抛异常...
        System.out.println("限流值：" + max);
    }
    // 业务逻辑...
}
```

- **适用场景**：**工具类**、**简单的校验框架**，或者你不想引入 Spring AOP 的复杂依赖。
- **致命缺点**：**代码极度冗余**。如果你有 100 个方法都要限流，就得把这段 `getAnnotation` 复制粘贴 100 遍，违背 DRY（Don't Repeat Yourself）原则。所以基本没人这么干。

---

### 方式三：编译期注解处理器（`AbstractProcessor`）—— **根本不需要运行时代码**

如果你不需要在运行时“拦截方法”，而是想在**编译时**“生成新代码”，那就不需要 `@Aspect`。

- **代表选手**：**Lombok（`@Data`）**、**MapStruct（`@Mapper`）**。
- **原理**：它们在 `javac` 编译时直接读取注解，修改 AST（抽象语法树），**给你自动生成 `getter/setter` 或 `mapperImpl` 实现类**。
- **代价**：你写的处理器只在编译期运行，打包后的 JAR 包里完全没有处理器的踪迹。

---

### 方式四：拦截器/过滤器（`HandlerInterceptor` / `Filter`）—— **针对 Web 层特供**

如果你的注解只想用在 **Controller 接口** 上，你可以不用 `@Aspect`，而是用 Spring MVC 的拦截器。

- **原理**：在拦截器的 `preHandle` 方法里，通过 `handler` 对象获取 Method 上的注解。
- **适用场景**：只针对 HTTP 请求的权限校验、防刷限流（结合 IP）。
- **与 AOP 的区别**：AOP 可以拦截 Service 层、DAO 层的任何方法，而拦截器只能拦截 Web 请求。

---

### 给你一个最终的选型建议（决策树）

回到你的 `@RateLimiter` 场景，你可以这样判断：

1. **你要拦截的是 `Controller` 接口吗？** 
   - 是，且不想引入 AOP 依赖 -> 可以用 **`HandlerInterceptor`**。
   - 是，但以后可能想拦截 Service 方法 -> **用 `@Aspect`**（更通用）。

2. **你要拦截的是 Service 中的业务方法吗？** 
   - 是 -> **必须用 `@Aspect`**（因为拦截器管不到 Service）。

3. **你想在编译时自动生成代码吗？**（比如根据注解生成路由表）
   - 是 -> 用 **`AbstractProcessor`**。

---

### 结论

虽然不用 `@Aspect` 也能实现注解功能，但**使用 `@Aspect` 是让“注解”和“业务逻辑”彻底解耦的最佳实践**。

如果你现在正打算写 `@RateLimiter`，我**强烈建议你用 `@Aspect`**。因为这样你只需要写一次切面逻辑，以后在任何项目、任何类、任何方法上，只要贴一个 `@RateLimiter` 标签，限流功能就会自动生效，业务代码里完全看不到任何杂乱的 `if` 判断。


## 注解是怎么触发的,对类使用的注解和对方法使用的注解,触发方式和结果又有什么区别

**注解本身永远不会“自动触发”任何逻辑，它只是一块“贴在代码上的标签”。真正“触发”动作的，是外部程序（框架、编译器或工具）主动去“读取”这块标签。**

就像二维码本身不会响，必须是**扫码枪（处理器）**去扫它，才会弹出页面。

---

### 1. 注解的触发方式（谁来“扫码”）

根据注解的 `@Retention`（生命周期），触发它的“扫码枪”分为三种：

| 触发阶段 | 扫描工具 | 典型注解 | 触发结果 |
| :--- | :--- | :--- | :--- |
| **源码期（SOURCE）** | **编译器（javac）** | `@Override`、`@SuppressWarnings` | 编译时检查语法，编译后注解消失，不产生任何字节码影响。 |
| **编译期（CLASS）** | **注解处理器（APT）** | Lombok 的 `@Data`、MapStruct | 在编译时动态生成新的 `.java` 或 `.class` 文件，**运行时根本不存在这个注解**。 |
| **运行期（RUNTIME）** | **反射（Reflection）** 或 **AOP 动态代理** | Spring 的 `@Transactional`、`@RequestMapping` | **这是最常用的方式**。JVM 启动后，框架通过反射读取注解，在方法调用前后插入逻辑。 |

> **你平时自定义的限流、日志注解，99% 都是 RUNTIME 级别**，靠 Spring AOP 在运行时触发。

---

### 2. 触发机制的本质：不是“注解触发”，而是“拦截器匹配”

既然注解是被读取的，那么**类上的注解**和**方法上的注解**在触发逻辑上，区别不在于“怎么触发”（都是反射读取），而在于**拦截器（AOP切面）的匹配范围**和**生效优先级**。

#### 区别一：切面匹配的“粒度”不同（核心区别）

-   **方法注解**：属于**细粒度精准打击**。切面会精确拦截“贴了该注解的**具体某个方法**”的执行。
-   **类注解**：属于**粗粒度批量覆盖**。切面一旦检测到类上贴了注解，通常意味着**该类的所有公共方法**都会被拦截逻辑影响。

> **举例（Spring 事务）**：
> - 方法上贴 `@Transactional`：只有这个方法有事务。
> - 类上贴 `@Transactional`：**该类下所有 `public` 方法**都会被自动注入事务逻辑。

#### 区别二：生效的“时机”不同

-   **方法注解**：在**方法执行前/后/环绕**时触发（比如限流、日志、权限校验）。
-   **类注解**：很多时候在**Bean 实例化阶段**就触发了（比如 `@Component` 让类被扫描注册到 Spring 容器），或者在类初始化时设置全局默认属性（比如类上的 `@RequestMapping("/user")` 给所有方法加上 `/user` 前缀）。

#### 区别三：优先级和覆盖规则（类级是默认，方法级是覆盖）

在 Spring 中，如果**类上**和**方法上**都贴了同一个注解（比如都有 `@Transactional`）：

-   **触发结果**：**方法上的注解会覆盖类上的注解**（方法级优先级更高）。
-   这意味着，类注解提供了一个“默认配置”，方法注解可以针对个别接口进行“特殊微调”。

---

### 3. 实战图解：框架是如何“区别对待”它们的？

以 Spring AOP 的切点表达式（Pointcut）为例，你能直观看到触发目标的差异：

```java
// 1. 拦截所有【类上】标注了 @MyAnnotation 的类中的所有方法
@Pointcut("@target(com.demo.MyAnnotation)")
public void classPointcut() {}

// 2. 拦截所有【方法上】标注了 @MyAnnotation 的单个方法
@Pointcut("@annotation(com.demo.MyAnnotation)")
public void methodPointcut() {}
```

-   如果使用 `@target`，切面会扫描所有 Bean 的 Class 对象，一旦类上有注解，该类的**所有方法**都会被代理。
-   如果使用 `@annotation`，切面只在执行具体方法时，去检查**当前这个方法**上有没有贴标签。

---

### 4. 特殊案例：类注解如何影响“非直接调用”？

这里有一个容易踩坑的点：**类注解不会自动传递给子类或实现类**，除非子类也贴了，或者使用了 `@Inherited` 元注解。

-   **父类贴了注解，子类没贴**：默认情况下，Spring 扫描子类时**不会**继承父类的类注解（事务、RequestMapping 都不会继承）。
-   **接口方法贴了注解，实现类没贴**：Spring 默认**不会**通过接口方法上的注解触发事务（必须把注解写在实现类上，或者启用 CGLIB 代理并配置参数）。

---

### 总结一句话回答你的问题：

-   **触发方式**：注解**从不主动触发**，全靠**反射/AOP 拦截器被动读取**。
-   **类注解 vs 方法注解**：
    -   **触发范围不同**：类注解影响整个类的所有方法（批量生效）；方法注解只影响单个方法（精准生效）。
    -   **触发时机不同**：类注解可能影响 Bean 的加载生命周期；方法注解只在方法调用时触发。
    -   **触发结果不同**：如果同时存在，**方法注解的配置会覆盖类注解的配置**（就近原则）。

## 既然注解本身不会触发各种接口方法,那么@Override,@Transactional这种功能性注解,编译器是怎么知道注解所在的方法是重写/事务方法
这个问题问得非常深入，直击注解机制的核心**“处理者（Processor）”**。你的困惑在于：既然注解是“死”的数据，那计算机到底是怎么“知道”要干什么的？

答案很明确：**编译器或框架根本不“猜测”，而是由预先写好的“处理程序”主动去扫描这些注解，然后硬编码地执行相应逻辑。**

下面我把 `@Override` 和 `@Transactional` 分开讲，因为它们的**“处理者”**和**“处理时机”**完全不同，这恰好代表了注解的**两大核心流派**。

---

### 1. `@Override`：编译期的“代码警察”（处理者：javac 编译器）

`@Override` 的 Retention 是 `SOURCE`（源码期），这意味着**编译完成后，这个注解就消失了**。它存在的唯一意义，就是给编译器（`javac`）看的。

**编译器是怎么知道的？**

- 当你运行 `javac MyClass.java` 时，编译器内部有一个叫 **“注解处理器（Annotation Processing Tool）”** 的模块。
- 它解析 Java 源代码生成**抽象语法树（AST）**时，会检查每个方法上的注解。
- 当它看到 `@Override` 时，会立即执行一段**硬编码在编译器源码里的校验逻辑**：
  1. 拿着这个方法名、参数类型、返回类型。
  2. 去查找它的父类（或实现的接口）有没有一模一样的方法。
  3. **有** -> 通过，正常编译；**没有** -> 直接抛出编译错误（`error: method does not override or implement a method from a supertype`）。

**结论**：`@Override` 是给 **`javac.exe` 这个可执行程序**读的，读完之后做出“报错”或“通过”的动作。这与运行时反射无关。

---

### 2. `@Transactional`：运行期的“动态代理”（处理者：Spring 框架）

`@Transactional` 的 Retention 是 `RUNTIME`（运行时），注解会保留在 `.class` 字节码中，JVM 启动时能通过反射读到。

**Spring 是怎么知道的？**

- Spring 在启动时（比如 `ApplicationContext` 刷新时），会执行一个核心处理者：**`BeanPostProcessor`（后置处理器）**，具体实现是 `AnnotationTransactionAttributeSource`。
- 处理流程如下（硬编码逻辑）：
  1. Spring 扫描所有被 `@Component` 管理的 Bean。
  2. 利用**反射**遍历每个 Bean 的所有方法：`method.getAnnotation(Transactional.class)`。
  3. 如果发现某个方法（或类）贴了这个注解，Spring 就认为：“这个方法需要事务增强”。
  4. Spring **不会直接调用原方法**，而是利用 CGLIB 或 JDK 动态代理，**生成一个代理对象**。
  5. 当你调用这个方法时，代理对象会先执行硬编码的事务逻辑（`beginTransaction()`），再调用你的原方法，最后执行 `commit()` 或 `rollback()`。

**结论**：`@Transactional` 是给 **Spring 框架的 Java 代码**读的，框架作者在源码里写死了“看到这个注解就开事务”的指令。

---

### 3. 图解两派本质区别

| 对比维度 | `@Override`（编译时） | `@Transactional`（运行时） |
| :--- | :--- | :--- |
| **处理者** | `javac` 编译器（C++/Java 编写） | Spring 框架（纯 Java 编写的 BeanPostProcessor） |
| **读取方式** | 读取源代码的 AST（抽象语法树） | 读取编译后的 `.class` 字节码（反射） |
| **处理结果** | 修改编译结果（报错或通过），**不生成新代码** | 生成动态代理对象，**注入新功能（开启事务）** |
| **生命周期** | 源码阶段（SOURCE） | 运行时阶段（RUNTIME） |

---

### 4. 补充一种“狠角色”：编译期生成代码（Lombok 的 `@Data`）

既然问到了编译器，再带你看看第三种流派——**编译期代码生成**（Lombok、MapStruct）。

- **处理者**：同样是 `javac`，但用的是 JSR 269 标准 API（Pluggable Annotation Processing）。
- **怎么知道的**：Lombok 在编译时会“劫持”编译器的 AST 树。
- **做了什么**：看到 `@Data` 后，它**不是报错，也不是动态代理**，而是**直接修改 AST 语法树**，在 `.java` 文件中硬生生“凭空”塞进去 `getter`、`setter`、`toString` 等方法的字节码。等编译结束，你的 `.class` 文件里就真的有了这些方法。

---

### 回到你的核心困惑

你问“编译器怎么知道”，回答就是：

1.  **对于 `@Override`**：编译器本身就内置了对这个注解名的**硬编码识别规则**。只有 `java.lang` 包下的这几个注解（Override, Deprecated, SuppressWarnings）才享有这种“编译器原生特权”。
2.  **对于 `@Transactional`**：编译器**完全不知道**它是什么，编译器只负责把它的信息存进 `.class` 文件。**是 Spring 框架的启动代码**在 JVM 里通过反射把它读出来的。

**一句话总结**：没有任何“魔法”或“自动触发”。总是**某个主动运行的代码（编译器进程或 Spring 主线程）**在执行过程中，主动去**看了一眼**方法上的注解，然后根据注解里的字符串数据（比如 `isolation` 级别），执行了对应的 `if...else...` 分支逻辑。

## 那既然注解的功能是通过注解名本身,那么自定义注解中的各种注解元素是干什么的
你这个追问极其精准，直接触及了注解设计的**灵魂**。

如果注解名代表了**“做什么”**（比如限流、事务、缓存），那么**注解元素（属性）** 代表的就是**“做多细”、“做成什么样”**。

你可以把**注解名**当成**“函数名”**，把**注解元素**当成**“函数的参数”**。没有参数的函数功能是锁死的，而有了参数，同一个注解才能适配千变万化的业务场景。

具体来说，注解元素在运行时承担着以下**三大核心使命**：

---

### 1. 让“同一个注解”产生“不同的执行结果”（参数化配置）

这是注解元素最根本的作用。如果没有元素，`@Transactional` 只能有一种死板的行为。但有了元素，它就能千变万化：

-   不写元素：`@Transactional` 默认捕捉 `RuntimeException` 回滚。
-   写了元素：`@Transactional(rollbackFor = Exception.class)` —— **告诉处理程序**：“虽然是同一个注解名，但这次遇到所有 `Exception`（包括受检异常）都要回滚。”
-   再比如：`@Cacheable(cacheNames = "users", key = "#id")` —— 元素告诉 Spring 缓存到哪个区域、用什么做键。

**结论**：**注解名决定“拦截哪类方法”，注解元素决定“拦截后具体怎么干”。**

---

### 2. 作为“数据载体”，传递给处理程序（AOP/反射）使用

你在代码里写的字符串、数字，会被切面类读取，并参与到业务逻辑的计算中。

**实战推演（你之前的限流注解）：**

-   **没有元素**：`@RateLimiter` 只能写死 1 秒内限制 5 次，提示语固定。
-   **有了元素**：
    ```java
    @RateLimiter(maxCount = 10, timeWindow = 60, message = "系统繁忙")
    ```
    当 AOP 切面拦截到时，它会读取这三个值：
    1.  拿着 `timeWindow=60` 去查 Redis 统计 60 秒内的次数。
    2.  拿着 `maxCount=10` 判断是否超过阈值。
    3.  如果超了，拿着 `message="系统繁忙"` 抛给前端。

如果没有元素，你的切面代码就只能写死 `if (count > 5)`，毫无复用价值。

---

### 3. 提供“默认值”，实现优雅的约定大于配置（`default` 关键字）

你可以把最常用的配置设为默认值，这样调用方可以极简使用，只关注最重要的参数。

```java
public @interface MyCache {
    // 必须填，没有默认值 —— 强迫调用者思考缓存哪里
    String cacheName(); 
    
    // 有默认值 —— 大部分场景下调用者根本不用写这一行
    long timeout() default 60; 
}
```

调用时：
```java
// 你只写了缓存名，超时时间自动取默认的 60 秒
@MyCache(cacheName = "user") 
public User get(){...}
```

---

### 补充一个极易误解的点（坑）

**注解元素不是动态属性，必须是“编译期常量”。**

这意味着，你不能写成：
```java
// 错误！不能读取运行时的随机数
String key() default UUID.randomUUID().toString(); 
```
因为注解元素的值在**编译期间**就被硬编码进 `.class` 文件了，运行时通过反射取出来的永远是那个固定的字面量。

---

### 最终结论（帮你打通任督二脉）

如果把注解机制比作**“点外卖”**：

- **注解名（`@RateLimiter`）**：就是你在 APP 上点的**“商家（肯德基）”**——决定谁来处理你的请求。
- **注解元素（`message="x"`, `time=60`）**：就是你点的**“具体餐品（香辣鸡腿堡+可乐）”**——决定商家送来的到底是什么东西。
- **处理程序（AOP 切面）**：就是**“后厨和骑手”**——他们看到商家名（肯德基）就开始做，看到具体餐品（注解元素）就按配方备料，最后把成品（抛出异常或提交事务）送到你手里。

**所以回答你的问题**：注解元素不是为了“触发”逻辑，而是为了**“喂养”**逻辑。没有它们，处理程序就像空锅做饭——能做，但没内容。
